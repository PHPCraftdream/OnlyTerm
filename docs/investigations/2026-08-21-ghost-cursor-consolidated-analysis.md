# Фантомный курсор после возврата к окну: итоговая перепроверка гипотез

Исходные отчёты:

## Итог

В коде действительно есть самостоятельный дефект `retained rows`: строка, в quad-ах которой
остался старый курсор, может получить `EmitRetained` после перемещения настоящего курсора.
Это способно дать одновременно свежий курсор в новой позиции и фантомный курсор в старой.

Однако второй отчёт слишком широко связал этот дефект с исходным сценарием «вернуть фокус
окну, затем переключить вкладку». Если перед переключением вкладки реально пришёл оконный
`FocusChanged`, глобальный `quad_generation` уже изменён. Скрытая вкладка не рендерилась и
сохранила старый `RetainedStamp`; при первом кадре после переключения штампы не совпадут,
retained-строки будут очищены, и `EmitRetained` старого курсора станет невозможен.

Поэтому окончательный статус двух утверждений различается:

1. **Дефект cursor-bearing retained row подтверждён статическим анализом.** Его стоит
   исправить независимо от воспроизводимости исходного случая.
2. **Причина конкретного наблюдения после реального refocus пока не установлена.** Для него
   retained-механизм подходит только если между последним рендером целевой вкладки и её
   возвратом не было фактического bump-а поколения либо порядок событий оказался иным, чем
   следует из словесного описания.

Это важное уточнение: «в коде найден настоящий баг» не равнозначно «доказано, что именно он
создал конкретный кадр пользователя».

## 1. Что доказано про retained-строки

### 1.1. Курсор является частью quad-ов строки

Отдельного финального cursor-overlay нет. `render_screen_line` выбирает строку курсора по
`stable_line_idx == cursor.y` и добавляет `cursor_sprite` в quad-ы этой строки
(`render/screen_line.rs:71,108-123,318-430`).

`LineQuadCacheKey` также содержит `cursor: Option<CursorProperties>`
(`render/mod.rs:76-101`). Поэтому строка A «с курсором» и та же строка A «без курсора» —
разные записи content-cache.

### 1.2. `RetainedRow` теряет семантику сохранённых пикселей

`RetainedRow` (`render/mod.rs:145-148`) хранит только:

```text
quads
expires
```

Он не хранит признак того, что в этих quad-ах был нарисован курсор. В `paint_pane` наличие
retained-содержимого схлопывается до одного `bool has_retained` (`render/pane.rs:586-592`).
Для `RowSweep` понятия «есть что показать» и «это безопасно показывать устаревшим» становятся
неразличимы.

### 1.3. Минимальный контрпример

Пусть в последнем реально показанном кадре курсор находился в visual slot A:

| Состояние | Slot A | Slot B |
|---|---|---|
| Последний retained-кадр | quad-ы с курсором | quad-ы без курсора |
| Новый кадр | курсора уже нет | здесь настоящий курсор |

В новом кадре:

- ключ строки A меняется `cursor: Some -> None`, поэтому старый cursor-bearing cache entry не
  является свежим попаданием;
- `has_retained(A) == true`;
- `cursor_row == B`, поэтому A не защищена правилом «current cursor row always builds»;
- если A не является rotation target, политика может вернуть `EmitRetained`;
- строка B строится либо эмитится из подходящего свежего cursor-key cache entry.

Результат: настоящий курсор виден в B, а сохранённый cursor quad ещё один кадр виден в A.
Это логически допустимый путь в текущем коде, без UB, panic или нарушения типов.

### 1.4. Превышение 40 мс не обязательно

`RowSweep::decide` (`render/budget.rs:95-120`) возвращает `EmitRetained` не только после
дедлайна. Для cache-miss строки со `slot < work_start`, которая имеет retained-данные и не
является текущей cursor row, ветка `Build` недостижима независимо от времени кадра.

Следовательно:

- истёкший `tab_frame_build_budget_ms` расширяет окно проявления;
- `resume_row > 0` способен дать stale-строку и в быстром кадре;
- баг относится к инварианту прогрессивного sweep, а не только к «медленной debug-сборке».

### 1.5. Вкладка не обязательна

Тот же контрпример возможен внутри одной активной панели при перемещении курсора A → B.
Неактивная вкладка лишь делает retained-состояние старше и увеличивает число cache miss после
возврата. Поэтому исправление должно защищать cursor-bearing retained row вообще, а не
специально очищать кэш при переключении вкладок.

## 2. Почему `quad_generation` не создаёт фантом

`RetainedStamp` содержит `quad_generation` (`render/mod.rs:155-169`). Перед обходом строк
`paint_pane` сравнивает сохранённый и текущий stamp (`render/pane.rs:424-471`). При
несовпадении вся запись панели заменяется на:

```text
rows = vec![None; viewport_rows]
resume_row = 0
```

После этого `has_retained == false` у каждой строки. В `RowSweep::decide` условие
`!has_retained` входит в `must_build` и обходит дедлайн. Старые quad-ы не могут попасть ни в
`EmitRetained`, ни в `EmitCached`, потому что тот же новый `quad_generation` входит и в
`LineQuadCacheKey`.

Таким образом, bump поколения создаёт дорогой полный rebuild, но одновременно является
защитой от stale retained pixels.

## 3. Противоречие со сценарием «refocus → tab switch»

В Windows backend `WM_SETFOCUS` и `WM_KILLFOCUS` диспетчеризуют
`WindowEvent::FocusChanged(true/false)` (`crates/window/src/os/windows/window.rs:2954-2981`).
Обработчик `TermWindow::focus_changed` безусловно выполняет
`self.quad_generation += 1` и `window.invalidate()`
(`termwindow/window_handler.rs:29-51`).

Переключение вкладки само поколение не меняет (`actions.rs:629-657`), но это не отменяет
уже случившийся глобальный bump фокуса. Получается следующая последовательность:

1. Вкладка T скрыта и хранит stamp с поколением G.
2. Окно теряет и/или получает фокус: глобальное поколение становится G+1 либо G+2.
3. Пока T скрыта, её stamp остаётся G.
4. Пользователь активирует T.
5. Первый `paint_pane(T)` сравнивает G с новым поколением и полностью очищает retained rows.

При такой последовательности refined-механизм второго отчёта не может нарисовать старый
курсор целевой вкладки. Фраза «переключение вкладок не бампает поколение» сама по себе верна,
но недостаточна: необходимо учитывать все события между двумя рендерами этой вкладки.

Retained-гипотеза всё ещё подходит к следующим вариантам:

- вкладка долго была неактивна, но окно всё время оставалось сфокусированным;
- пользователь переключил вкладку до фактического `WM_SETFOCUS` либо наблюдаемая
  последовательность событий отличалась от словесной;
- визуальный дефект возник до refocus-bump и лишь был замечен после возвращения;
- в конкретном запуске событие фокуса почему-либо не дошло до `TermWindow`.

Без журнала событий конкретного кадра выбирать один из этих вариантов нельзя.

## 4. Следующий сильный кандидат: несогласованный render snapshot

Даже когда stamp mismatch гарантирует полный свежий rebuild, `paint_pane` не получает
состояние терминала одним атомарным снимком:

1. `pos.pane.get_cursor_position()` вызывается около `render/pane.rs:100`;
2. `pos.pane.get_dimensions()` вызывается позже, около `render/pane.rs:108`;
3. строки клонируются через `pos.pane.get_lines(...)` только около `render/pane.rs:839`.

Для `LocalPane` каждый из этих методов независимо берёт и отпускает
`Mutex<Terminal>` (`mux/src/localpane.rs:364-422`). PTY parser может изменить screen и
стабильную позицию курсора между вызовами.

Значит один кадр способен совместить:

- курсор из момента t0;
- размеры/`physical_top` из момента t1;
- строки из момента t2.

При быстром фоновом выводе старый stable cursor row может к моменту снимка строк оказаться
около верхней границы нового viewport, тогда как новые строки уже содержат prompt внизу.
Это уже непосредственно соответствует картине «курсор сверху, содержимое/приглашение
снизу» и не зависит от `EmitRetained`.

Статически подтверждено наличие окна несогласованности; не подтверждено, что PTY реально
успел пройти нужное число строк именно в наблюдавшемся кадре. Тем не менее после учёта
focus-bump это более подходящее направление следующей проверки, чем повторное объяснение
через совпавший `RetainedStamp`.

Архитектурно сильное лечение этого класса — единый render snapshot, который под одним
кратковременным `terminal.lock()` получает cursor, dimensions и клон нужных lines, а затем
отпускает lock до shaping/GPU-работы. Это сохраняет уже принятую цель не держать terminal
lock во время тяжёлого рендера, но убирает смешение трёх версий состояния. Реализовывать
такое изменение до runtime-подтверждения преждевременно: оно затрагивает `Pane` и overlay-
реализации шире минимального cursor-retained фикса.

## 5. История появления подтверждённого retained-дефекта

- `31595257a` (`gui: fix frame-build-budget degradation with retained rows + progressive
  sweep`, task #457) ввёл `RetainedRow`, `RetainedStamp`, `RowSweep::decide`, запись и
  `EmitRetained`. `git blame` относит ключевые строки дефекта к этому коммиту.
- `8192d69ac` исправил starvation rotation, но не добавил семантику сохранённого курсора.
- `2c4006622` исправил вычисление **текущего** cursor row slot относительно реального
  viewport. Он не может защитить **предыдущую** строку курсора, потому что её идентичность
  уже утрачена в `RetainedRow`.
- Текущий `HEAD` и staged-изменения по GPU/host-process не меняют описанную политику:
  `render/budget.rs` и `render/pane.rs` не модифицированы, а изменения `render/mod.rs` не
  затрагивают поля `RetainedRow`/`RetainedStamp`.

Следовательно, cursor-bearing retained bug, вероятнее всего, существует с `31595257a`.
Это вывод об истории кода, а не доказательство даты первого пользовательского проявления.

## 6. Рекомендуемый минимальный фикс подтверждённого дефекта

Наиболее узкий вариант:

1. Добавить в `RetainedRow` консервативный признак вроде `contains_cursor`.
2. Заполнять его в обеих ветках, которые обновляют retained row: `EmitCached` и `Build`.
3. На cache miss принудительно выбирать `Build`, если retained row содержит курсор, даже
   когда этот slot больше не равен текущему `cursor_row`.
4. Сохранить существующее правило, принудительно строя текущую строку курсора.

Это даёт ограниченную цену: при перемещении курсора дополнительно перестраивается максимум
его прежняя retained-строка, а не вся панель. Признак лучше делать консервативным: ложный
`true` стоит одного лишнего row build, ложный `false` сохраняет фантом.

Не рекомендуются как основной фикс:

- добавление cursor y в `RetainedStamp` — полный rebuild панели при вертикальном движении;
- bump `quad_generation` на каждом tab switch — скрывает частный сценарий дорогой глобальной
  инвалидацией, но не лечит внутрипанельный A → B;
- безусловная очистка всех retained rows вкладки — та же потеря назначения frame budget;
- сужение `quad_generation` — полезная отдельная оптимизация, но не исправление cursor-bearing
  retained row.

## 7. Обязательные проверки будущего фикса

Минимальный набор regression-тестов:

1. Старый slot A содержит cursor-bearing retained quads, текущий cursor row — B, cache miss,
   deadline истёк: A обязан получить `Build`.
2. Та же ситуация при `A < work_start` и неистёкшем deadline: A также обязан получить
   `Build`.
3. Обычная retained-строка без курсора по-прежнему может получить `EmitRetained` — иначе
   будет незаметно выключена исходная оптимизация task #457.
4. Текущая cursor row никогда не откладывается.
5. Rotation сохраняет forward progress и после добавления нового must-build условия.
6. Stamp mismatch по `quad_generation` очищает retained rows и не допускает
   `EmitRetained` ни для одного slot.

Для установления причины исходного пользовательского кадра нужен отдельный контролируемый
runtime trace:

- последовательность `FocusChanged`, tab activation и paint с pane/tab id;
- текущий `quad_generation` и сохранённый `RetainedStamp.quad_generation`;
- был ли выполнен reset retained rows;
- cursor stable y, viewport top, returned `stable_top` и terminal seqno для каждого снимка;
- `work_start`, старый `contains_cursor` и выбранный `RowAction` для подозрительного slot.

Существующие логи `onlyterm-gui.exe-log-*.txt` таких trace-полей не содержат: поиск по
`Setting focus`, `quad_generation`, `RetainedStamp` и `EmitRetained` результата не дал.

## 8. Уровень уверенности

| Вывод | Уверенность |
|---|---|
| Bump `quad_generation` очищает retained и не может сам породить старый cursor quad | Высокая, прямое следствие кода |
| Cursor-bearing retained row может быть ошибочно переэмитирован после A → B | Высокая, построен достижимый путь через `RowSweep::decide` |
| Этот путь объясняет tab switch без промежуточной смены поколения | Высокая |
| Этот путь объясняет именно `refocus → tab switch` при реально пришедшем FocusChanged | Низкая; код ему противоречит |
| Несогласованный cursor/dimensions/lines snapshot возможен | Высокая, методы берут lock раздельно |
| Snapshot race создал наблюдавшийся кадр | Средняя/низкая до runtime trace |

Финальный инженерный вывод: cursor-aware retained fix обоснован и локален, но помечать им
исходный инцидент как окончательно закрытый нельзя. Для точной причины refocus-сценария
следующая проверка должна различить две ветки: stamp match с `EmitRetained` либо stamp reset
с несогласованным terminal snapshot/другим источником курсора.
