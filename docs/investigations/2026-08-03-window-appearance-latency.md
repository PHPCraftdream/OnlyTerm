# Расследование: окно долго не появляется после запуска

Дата: 2026-08-03.

Связанное расследование: `2026-08-03-startup-latency.md`.

## Короткий вывод

Исправление `9d2b72026` сработало: прежняя пауза ConPTY после создания окна
исчезла, и уже появившийся терминал становится рабочим практически сразу.

Оставшаяся задержка имеет другую причину. На Windows OnlyTerm по умолчанию
выбирает WebGpu/DX12 и **не показывает уже созданное native-окно, пока полностью
не закончатся выбор GPU-адаптера, создание device/surface, компиляция shader/
pipeline и создание `RenderState`**. На исследуемой машине это занимает около
трёх секунд. При принудительном OpenGL тот же бинарник показывает окно примерно
за полсекунды.

Это не ConPTY, не shell, не пользовательский конфиг и не обход каталога
шрифтов. Главный источник задержки найден и подтверждён A/B-замером.

## Что изменилось в git-истории

Последние относящиеся к исходной задержке коммиты:

- `226c962d6` — перестали вызывать `wsl.exe` на каждый spawn pane;
- `9d2b72026` — исправили потерю уже разобранных terminal actions при
  coalescing; ответы на стартовые DSR/DA1 теперь своевременно доходят до
  ConPTY;
- `3e650afb1` — записали результат первого расследования;
- `ab7f6074c`, `87af28fbd` — удалили WSL domains и связанные предупреждения.

Новый симптом появился не из этих правок. Его ключевой предшественник —
`e9d4ff97e` от 2026-07-30:

> `onlyterm-gui: WebGpu->OpenGL fallback, enable render thread by default on Windows`

Этот коммит намеренно изменил Windows-default с OpenGL на WebGpu, чтобы по
умолчанию заработал отдельный render thread и зависший GPU-driver call не мог
заморозить весь GUI-процесс. До этого `FrontEndSelection` по умолчанию был
OpenGL; upstream также вернул OpenGL как default коммитом `1e552d7643` в январе
2024 года.

Последующие оптимизации сократили цену WebGpu, но не убрали её:

- `10bdacbfc` вынес дорогую инициализацию WebGpu с GUI thread. Message loop
  больше не считается зависшим, но `new_window` всё ещё ждёт результат перед
  `show()`;
- `834e9acf3` перестал сразу платить одновременно за DX12 и Vulkan. На этой
  машине один DX12 `request_adapter` всё равно занимает около 2 секунд;
- `6eccefb12` и `c85d0e13b` ускорили работу со шрифтами. По новой трассе шрифты
  готовы задолго до основной паузы.

## Методика

Измерялось время от запуска нового процесса до появления ненулевого
`MainWindowHandle`. Запускался непосредственно `onlyterm-gui.exe`, а не
CLI-launcher `onlyterm.exe`; использовались `--always-new-process` и
`--skip-config`. После каждого прогона закрывался только запущенный процесс по
его точному PID. Пользовательские экземпляры терминала не затрагивались.

Исследованный локальный бинарник сообщает версию
`20260803-112629-3e650afb`. Текущий HEAD — `87af28fbd`; два более новых коммита
рендерер и порядок показа окна не меняют.

## A/B-результаты

### OnlyTerm, текущий Windows-default (WebGpu)

Пять обычных запусков без конфига:

| прогон | окно появилось через |
|---:|---:|
| 1 | 3814.8 мс |
| 2 | 2955.3 мс |
| 3 | 2838.6 мс |
| 4 | 2865.5 мс |
| 5 | 2909.0 мс |

Медиана: **2909 мс**. На момент показа процесс успевал израсходовать примерно
1.8 с CPU time и занимал около 491 MiB working set.

Отдельный запуск с явным `front_end="WebGpu"` дал **3553 мс**, 1875 мс CPU и
493 MiB working set.

### Тот же OnlyTerm, принудительный OpenGL

Команда эквивалентна:

```powershell
onlyterm-gui.exe --skip-config --config 'front_end="OpenGL"' start --always-new-process
```

| прогон | окно появилось через |
|---:|---:|
| 1 | 554.5 мс |
| 2 | 535.9 мс |
| 3 | 543.3 мс |
| 4 | 596.8 мс |
| 5 | 573.6 мс |

Медиана: **554.5 мс**, среднее: 560.8 мс. Средние значения на момент показа:
494 мс CPU и 168 MiB working set.

То есть единственная смена renderer backend сокращает задержку окна примерно
в **5.2 раза**, или на **2.35 секунды по медиане**.

Для контроля установленный upstream WezTerm 20240203 (OpenGL) показал окно за
835–1085 мс, медиана **851 мс**. Он не так быстр, как текущий OnlyTerm на
OpenGL, но у него нет трёхсекундной DX12-паузы.

Запуск OnlyTerm с обычным поиском конфига, но с CLI override на OpenGL, дал
864–1190 мс. Значит поиск/проверка конфигурации добавляет некоторую стоимость,
но не объясняет основную трёхсекундную задержку.

## Почему окно невидимо всё это время

Порядок в `crates/onlyterm-gui/src/termwindow/mod.rs` сейчас такой:

1. `Window::new_window(...).await` создаёт native window (строки около 859–872).
2. Для WebGpu вызывается и ожидается `WebGpuState::new(...).await` (около
   892–908).
3. Создаётся `RenderState` (около 940–942; сама функция — 586–610).
4. Запускается render thread.
5. Только затем вызывается `window.show()` (строка около 970).

Таким образом, `10bdacbfc` действительно освободил GUI thread во время выбора
адаптера, но пользователь не может увидеть пользу: native window до окончания
этого await остаётся скрытым.

## Практический обходной путь

Для мгновенного старта достаточно добавить в `%USERPROFILE%\.onlyterm.ktav`:

```text
front_end: OpenGL
```

Это подтверждённый способ убрать основную задержку. Но у него есть осознанная
цена: отдельный per-window render thread реализован только для WebGpu. OpenGL
рендерит синхронно на GUI thread, поэтому зависший вызов драйвера снова может
заморозить все окна процесса. Именно ради устранения этого класса зависаний
`e9d4ff97e` сделал WebGpu Windows-default.

## Рекомендуемое продуктовое исправление

Если приоритет — скорость сейчас, самый маленький патч: вернуть OpenGL как
Windows-default. Измерения обещают окно примерно за 0.5–0.9 с, но это отменяет
default-защиту render thread.

Если нужно сохранить архитектурную цель WebGpu/render-thread, правильнее
разделить **появление native window** и **готовность renderer**:

1. После расчёта geometry создать и сразу показать top-level window.
2. Пока `WebGpuState` строится в фоне, безопасно рисовать native placeholder
   цветом фона терминала либо хотя бы гарантированно очищать client area.
3. События `NeedRepaint` до готовности renderer должны оставаться no-op с
   повторным invalidate после установки `RenderState`.
4. После `WebGpuState::new` установить `RenderState`, запустить render thread и
   принудительно запросить первый repaint.
5. Сохранить существующий WebGpu→OpenGL fallback.

Просто перенести `window.show()` выше недостаточно безопасно: у Windows window
class сейчас `hbrBackground = null`, поэтому до первого GPU frame client area
может содержать мусор или давать неприятную вспышку. Кроме того, ранний показ
открывает окно для resize/focus/input events в состоянии без renderer; основной
`NeedRepaint` уже умеет ничего не делать при отсутствии `gl`, но весь этот
переходный state надо закрепить тестами.

## Итог

Сейчас есть две независимые истории startup latency:

1. **После создания окна:** трёхсекундное ожидание ConPTY DSR/DA1 — исправлено
   в `9d2b72026`; по наблюдению пользователя результат хороший.
2. **До появления окна:** Windows-default WebGpu/DX12 — подтверждённая текущая
   причина. На этой машине OpenGL сокращает медиану с 2.91 с до 0.555 с.

Следующая задача должна быть не про PTY и не про shell, а про политику выбора
renderer либо про ранний показ окна до готовности WebGpu.

## Результат: ранний показ окна реализован (2026-08-03, вечер)

Выбран второй путь — окно показывается сразу, рендерер догоняет. Итоговые
коммиты: `c68084a25` (кисть-заглушка), `8fdaf8cf7` (перенос `show()` до
инициализации WebGpu), `faf8ea0b6` (закрепление переходного состояния),
`59c473153` (заливка заглушки на самом деле стала видимой).

### Замер

Методика прежняя: время до ненулевого `MainWindowHandle`,
`--always-new-process --skip-config`, закрывается только свой PID.

| прогон | было (`87af28fbd`) | стало (`59c473153`) |
|---:|---:|---:|
| 1 | 3814.8 мс | 313.9 мс |
| 2 | 2955.3 мс | 244.4 мс |
| 3 | 2838.6 мс | 260.6 мс |
| 4 | 2865.5 мс | 268.4 мс |
| 5 | 2909.0 мс | 248.7 мс |

Медиана: **2909 мс → 260.6 мс**, то есть в 11 раз быстрее и заметно лучше,
чем принудительный OpenGL (554.5 мс), при сохранённом render thread.

### Переходное состояние

Проверено вручную на release-сборке. Окно появилось на 297 мс; двойной resize
выполнен ещё через 205 мс; набор с клавиатуры начат на 245 мс и закончен на
1259 мс — всё это до готовности WebGpu (~3.4 с). Набранная команда дошла до
shell и выполнилась (создан файл-маркер), процесс остался жив. Клавиши
слались через `keybd_event` с настоящими скан-кодами от `MapVirtualKey`:
`SendKeys` шлёт `VK_PACKET` и даёт ложноотрицательный результат.

### Заливка фона: три ошибки подряд

Заглушка из `c68084a25` не покрасила ни одного пикселя, и приёмка это
вскрыла. Мешали три независимые вещи:

1. `WM_ERASEBKGND` приходит синхронно из `BeginPaint`, который `wm_paint`
   вызывает, уже держа `borrow_mut()` на том же `RefCell`. Добавленный ранее
   `try_borrow` убирал панику, но вместе с ней и саму заливку. Красим теперь
   прямо в `wm_paint`.
2. Показ окна не инвалидирует клиентскую область. Всё, что нарисовано, пока
   окно скрыто, на экран не попадает, а простаивающее окно не получает нового
   `WM_PAINT` до первого кадра рендерера. Добавлен принудительный `RedrawWindow`
   сразу после `ShowWindow`.
3. Дочернее окно под WebGpu создаётся заранее, `WS_VISIBLE`, и закрывает всю
   клиентскую область — заливка родителя оказывается под ним. Нужен
   `RDW_ALLCHILDREN`, а само дочернее окно теперь красится кистью родителя.

### Чего стоят измерения цвета

Три метода проб оказались негодными, и это стоит помнить:

* **снимок экрана** — снимает то окно, что сверху; на загруженном рабочем столе
  дважды поймал чужое окно, причём `WindowFromPoint` при этом возвращал наше
  (дочернее окно прозрачно для хит-теста);
* **`PrintWindow(PW_RENDERFULLCONTENT)`** — возвращает `True` и белую картинку:
  содержимое, отрисованное GPU, он не снимает. То же ограничение у `GetPixel`
  по DC окна после подъёма рендерера;
* **`GetPixel` по DC окна** — читает и то, что было нарисовано в скрытое окно,
  поэтому не отличает «нарисовано» от «нарисовано и видно».

Единственное надёжное доказательство — порядок событий в trace-сборке:
`applying ShowWindowCommand Normal`, а следом заливка родителя и дочернего окна
заведомо неслучайным цветом (в контроле — красным).

### Что осталось непроверенным

Настоящий путь WebGpu→OpenGL fallback на машине без DX12 (RDP-сессия) не
воспроизводился. Проверено лишь, что принудительный `front_end=OpenGL` даёт
живое окно нужного размера за 241.9 мс.

По дороге найден отдельный дефект, к задержке отношения не имеющий:
`color_scheme` в OnlyTerm молча не действует, потому что непустой дефолт поля
`colors` (светлая GitHub-палитра) накладывается поверх разрешённой схемы.
