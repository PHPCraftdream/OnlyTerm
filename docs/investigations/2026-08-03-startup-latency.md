# Расследование: медленный старт OnlyTerm

Дата: 2026-08-03. Задача в трекере: #328.

## Симптом

Пользователь: «терминал запускается очень долго, потом ещё внутри cmd очень долго
запускается», «таб висит с белым экраном; если открыть ещё один таб, то может в
нём откроется cmd, но открывается долго — секунды 2–5».

«Белый экран» — это не отдельный дефект. Фон `#ffffff` берётся из цветовой схемы
пользователя, и пустая панель выглядит белой ровно до тех пор, пока оболочка не
выдала первый вывод. То есть «белый экран» и «долго открывается» — один и тот же
симптом.

## Как мерить (важно: прежняя метрика врала)

Сначала я мерил не то. Смотрел на момент первой отрисовки окна (`Resized`) и на
первый `read_pty` — и получал 0.5 с и 0.9 с, что не сходилось с жалобой. Обе
метрики наступают задолго до того, как оболочка стала пригодна к работе.

Честная метрика: время до момента, когда оболочка **реально выполнила команду**.
Реализуется через файл-маркер:

```
## D:/probe_c.ktav
default_prog: [cmd.exe, /c, echo probe-ok> D:/probe_mark.txt]
```

Запускается GUI, секундомер тикает до появления `D:/probe_mark.txt`.

Готовый инструмент: `D:/loop_hidden.ps1` — 4 прогона, прячет окно через
`ShowWindow(MainWindowHandle, 0)`, печатает время до маркера.

Зависшие процессы обязательно убивать фильтром по пути, иначе они держат
`OpenConsole.exe`:

```powershell
Get-Process onlyterm-gui,OpenConsole -ErrorAction SilentlyContinue |
  Where-Object { $_.Path -like 'D:\dev\rust\.cargo-target*' } | Stop-Process -Force
```

Фильтр по `Path` обязателен: у пользователя параллельно работает свой экземпляр
из `C:\Program Files\OnlyTerm`, его убивать нельзя.

## Опорный замер

Одна машина, одна и та же команда:

| | время до выполнения команды оболочкой |
|---|---|
| апстрим `C:/Program Files/OnlyTerm/onlyterm-gui.exe` | **0.56 / 0.67 / 0.72 с** |
| наш `D:/dev/rust/.cargo-target/release/onlyterm-gui.exe` | **3.50 / 3.56 / 3.65 с** |
| установленный `C:/Program Files/OnlyTerm/onlyterm-gui.exe` | **4.04 / 3.85 / 3.92 / 3.97 с** |

С `cmd /k` вместо `/c` цифры те же — дело не в интерактивности.

Вывод: разница около 3 секунд, и она наша, а не свойство машины.

## Разбивка спавна панели

Временные `log::error!` с `Instant` вокруг ключевых точек (после замера убраны):

```
build_command ....... 845 мс
CONPTY lazy load ...... 1.7 мс
CreatePseudoConsole .. 14.6 мс
openpty .............. 21.3 мс
CreateProcessW ....... 24.7 мс
```

Сам путь pty стоит около 60 мс. Значит основное время лежит вне `spawn_pane`.

## Что исправлено

### `wsl.exe` на каждый спавн панели — коммит `226c962d6`

`LocalDomain::resolve_wsl_domain` вызывался из `build_command` на каждый спавн.
`Config::wsl_domains()` при отсутствии явной настройки падал в
`WslDomain::default_domains()`, который синхронно запускает `wsl.exe -l -v`. То
есть открытие обычной панели домена `local` оплачивало перечисление WSL, с
которым по имени совпасть не могло в принципе.

Правка: не звать перечисление, если пользователь не задал `wsl_domains` явно и
имя домена не начинается с `WSL:`.

Замер: было 3.4–4.0 с, стало **3.23 / 3.25 / 3.28 / 3.29 с**.

### Перечисление WSL на старте

Отдельно замерено: наличие строки `wsl_domains: []` в конфиге экономит ~0.6 с.

| конфиг | время |
|---|---|
| без `wsl_domains: []` | 4.04 / 4.04 / 3.94 / 3.95 с |
| с `wsl_domains: []` | 3.36 / 3.34 / 3.46 / 3.48 с |

У пользователя эта строка есть (перенесена из старого Lua-конфига, где стояла с
комментарием «wsl.exe -l висит, пока WSL сломан»). Полное удаление поддержки WSL
ведётся в задаче #329.

### Прочие правки старта, сделанные по ходу

- `10bdacbfc` — инициализация WebGpu унесена с GUI-потока. Сторож
  `gui-watchdog` фиксировал зависание на 4.06 с; после правки — ноль.
- `6eccefb12` — каталог шрифтов обходился дважды за старт. Первая отрисовка:
  1.686 с → 0.924 с.
- `834e9acf3` — `Backends::all()` платил и за DX12 (`request_adapter` ~2.0 с), и
  за Vulkan (`Instance::new` ~2.2 с). Сузили до DX12 с расширением при неудаче.
  Готовность адаптера: 4.615 с → 2.981 с.
- `c85d0e13b` — шрифтовые файлы читались целиком ради заголовка (в
  `C:/Windows/Fonts` лежат коллекции по 20–37 МБ). Перешли на отображение в
  память. `ls-fonts --list-system`: 1125 мс → ~600 мс при неизменных 1102
  строках вывода. Первая отрисовка: 0.906 с → 0.495 с.

## Отвергнутые гипотезы

Все проверены фактами. Повторять не нужно.

1. **Дорогой ConPTY/pty.** Опровергнуто разбивкой: `openpty` 21 мс,
   `CreatePseudoConsole` 15 мс, `CreateProcessW` 25–42 мс, `spawn_command` 38 мс.

2. **Виновата версия ConPTY.** У нас `conpty.dll` 109 104 Б и `OpenConsole.exe`
   1 153 064 Б (2026-07-23); у апстрима наоборот — `conpty.dll` 1 395 712 Б и
   `OpenConsole.exe` 99 328 Б (2024-02-03). Подложил апстримовскую пару в нашу
   сборку — оболочка не стартует **вообще** (4 прогона из 4 по таймауту 15 с).
   Наш код требует более новой версии. Файлы возвращены.

3. **Антивирус.** Пользователь добавил `C:\Program Files\OnlyTerm` в исключения
   Defender (подтверждено чтением списка). Замер после: 4.16 / 4.62 / 4.58 /
   3.96 с — без изменений. Более того, в списке исключений **уже был** `D:\dev`,
   то есть каталог сборки был исключён всё время, а апстрим работает из
   неисключённого `C:\Program Files\OnlyTerm` за 0.7 с.

4. **Спавн панели ждёт готовности рендерера.** Опровергнуто по коду:
   `domain.spawn()` вызывается в `async_run_terminal_gui`
   (`crates/onlyterm-gui/src/main.rs`, ~строка 348) **до** создания окна
   `TermWindow`.

5. **Неподписанный dev-бинарник провоцирует поведенческий мониторинг.**
   Опровергнуто: `Get-AuthenticodeSignature` даёт `NotSigned` **и** для нашего
   `onlyterm-gui.exe`, **и** для апстримовского `onlyterm-gui.exe`. Апстрим при
   этом укладывается в 0.7 с.

6. **Отдельный процесс `OpenConsole.exe` на каждую панель.** Опровергнуто: при
   запуске и нашего, и апстримовского бинаря процессов `OpenConsole.exe` не
   появляется вовсе, оба используют уже существующие `conhost.exe`. Картина
   процессов идентична.

7. **Медленный разбор `.fon`-шрифтов** (побочная гипотеза, задача #313).
   Опровергнуто: все 192 файла `.fon` отбрасываются меньше чем за 3 мс каждый.
   Пауза в 182 мс между строками лога про `modern.fon` и `roman.fon` — это
   чтение лежащих между ними по алфавиту CJK-гигантов (`mingliub.ttc` 36 МБ,
   `simsunb.ttf` 21 МБ, `msjh.ttc` 21 МБ, `msyh.ttc` 19 МБ).

## Что установлено твёрдо и осталось необъяснённым

Диагностический поток, не связанный с нашим кодом (`OpenProcess` +
`WaitForSingleObject` по PID дочернего `cmd.exe`), показал: дочерний процесс
реально завершается через **3.0–3.9 с после того, как `CreateProcessW` уже
вернул хендл**.

Контрольный запуск того же `cmd.exe /c echo x> file` обычным `Start-Process`,
без ConPTY — **0.43 с**.

При этом апстрим создаёт дочерний процесс так же под ConPTY и этих секунд не
платит. Значит различие в том, **как именно** мы это делаем.

## Следующий шаг

Сравнить параметры создания процесса у нас и у апстрима:

- флаги `CreateProcessW` (`EXTENDED_STARTUPINFO_PRESENT`,
  `CREATE_UNICODE_ENVIRONMENT`, `CREATE_NO_WINDOW` и прочие);
- состав `PROC_THREAD_ATTRIBUTE_LIST`
  (`crates/pty/src/win/procthreadattr.rs`);
- передаваемый блок окружения — не раздут ли он;
- рабочий каталог;
- размер псевдоконсоли, передаваемый в `CreatePseudoConsole`.

Файлы: `crates/pty/src/win/conpty.rs` (функция `spawn_command`),
`crates/pty/src/win/pseudocon.rs`, `crates/pty/src/win/procthreadattr.rs`.

Полезный инструмент для окна между `CreateProcessW` и первым исполнением:
Process Monitor или ETW-трассировка.

## Отдельная находка, не связанная с ConPTY

`build_command` занимал 845 мс, из которых основное — тот самый вызов `wsl.exe`
(исправлено). Стоит перепроверить остаток после фикса: если там останутся сотни
миллисекунд, разобрать, что ещё делает `LocalDomain::build_command`
(`crates/mux/src/domain.rs`).

## РАЗВЯЗКА (дополнено 2026-08-03, позже)

Причина найдена и устранена коммитом `9d2b72026`. Ключ дало внешнее ревью
(`2026-08-03-startup-latency-review.md`): константа 3000 мс совпадает с
`WaitUntilDA1(3000)` в ConPTY 1.22 — при старте ConPTY шлёт запросы DSR/DA1
(`ESC[6n ESC[c`) и ждёт ответа до 3 секунд.

Диагностический прогон с таймстампами в четырёх точках рукопожатия показал:

```
0.437 с  read_pty прочитал "ESC[6n ESC[c ESC[?1004h ESC[?9001h"
3.462 с  обработчик CPR вызван      <- через 3 секунды!
3.465 с  обработчик DA1 вызван
3.465 с  pane-writer записал ответы
```

Запросы читались мгновенно, но парсер-поток придерживал распарсенные actions.
Баг в цикле коалесинга `parse_buffered_data` (`crates/mux/src/lib.rs`):
после `recv_timeout` с успешно полученным вторым чанком стоял `continue` на
вершину цикла — а там **блокирующий** `rx.recv()`. Уже распарсенные ответы
лежали неотправленными, пока pty не выдаст ЕЩЁ байты. ConPTY же молчал,
ожидая именно эти ответы. Взаимное ожидание, которое разрывал только его
3-секундный таймаут — на каждом спавне панели.

Регрессия внесена коммитом `0ba6e9b68` (замена socketpair на канал): в
исходном коде `poll()` только проверял готовность и данные оставались в
сокете для внешнего чтения, а `recv_timeout` сообщение забирает — и внешний
`recv` повисал на пустом канале.

Замеры после фикса: **0.25–0.69 с** (было 3.4–4.0 с; апстрим на той же
машине — 0.56–0.72 с).

Поправка к разделу «отвергнутые гипотезы», по замечанию ревью: эксперимент с
подменой пары ConPTY доказал только несовместимость старой пары с текущим
клиентом, но не невиновность версии — окончательный ответ дал
диагностический прогон, а не подмена файлов.
