# Устойчивое обнаружение Codex для Ctrl+J / Ctrl+Enter

## Что установлено

В журналах одной установленной сборки OnlyTerm разные окна отправляли разные
Win32-записи для одного сочетания: `UnicodeChar=106` (поправка Codex включена)
и `UnicodeChar=10` (выключена). Привязка Ctrl+J находилась в обоих случаях;
Ctrl+Enter привязан к тому же `SendChar(CTRL, 'j')`.

Диагностическая сборка работала при прямом запуске и запуске через `--start-conf`.
Поэтому конкретный длительный отказ старого окна пока не воспроизведён.
Изменения ниже закрывают воспроизводимые по коду сценарии, а не доказывают,
что именно один из них произошёл в старом процессе.

## Устранённая зависимость

Раньше `LocalPane::get_process_tree_exe_names(AllowStale)` использовал общий
асинхронный кэш подробных сведений о процессах:

- холодный кэш возвращал `None` на первом нажатии;
- старый снимок без Codex выключал поправку после его запуска;
- старый снимок с Codex сохранял поправку после его выхода;
- незавершившееся фоновое обновление могло сохранять такое состояние.

GUI превращал недоступность данных в `false` и сразу выбирал кодирование.
Уже отправленное нажатие после обновления кэша не исправлялось.

На Windows проверка теперь получает свежие PID, PPID и имена из Toolhelp.
Она не читает командные строки/память процессов, не открывает каждый процесс
и не зависит от фонового кэша рабочих каталогов и заголовков.
Обход по индексу родительского PID итеративный, с защитой от циклов,
ожидаемая сложность O(N) по числу записей снимка.

Проверка вызывается только для сочетаний, которым нужна совместимость
с конкретным приложением. Обычный текст не требует снимка.
Это синхронный вызов Windows: абсолютной гарантии задержки ОС нет.
Диагностика `diag: key-compat` указывает `source=fresh-snapshot` и `elapsed_us`.

## Ошибки снимка

Исправлена проверка отказа `CreateToolhelp32Snapshot`: API возвращает
`INVALID_HANDLE_VALUE`, а не `NULL`. При перечислении только
`ERROR_NO_MORE_FILES` считается нормальным завершением; остальные ошибки
отклоняют неполный снимок. Общий кэш заголовков сохраняет последний полный
снимок при ошибке, не обновляя его время получения.

Контракты Windows:

- [CreateToolhelp32Snapshot](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot)
- [Process32NextW](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-process32nextw)

## Регрессии

- Реальная панель с корнем PID тестового процесса: холодный кэш и навсегда
  выставленный флаг cold-fetch не мешают получить имена сразу.
- Реальная панель с устаревшим ложным `codex.exe` и `updating=true`:
  возвращается действительный процесс, ложный Codex исключён.
- Цепочка оболочек `cmd/powershell/node/codex/node_repl`: Codex виден,
  Claude из соседней панели не попадает в результат.
- Запуск/выход Codex между снимками, отсутствующий корень, цикл и цепочка
  из 10 000 процессов.
- Существующие тесты Win32/Kitty продолжают проверять отличия кодирования
  Codex от обычного управляющего символа, необходимого другим приложениям.

Первые два теста не проходят на прежнем пути через `AllowStale`:
он возвращает соответственно `None` и устаревший `codex.exe`.

## Границы и декомпозиция

Изменение относится к локальным Windows-панелям. `ClientPane` по-прежнему
не передаёт дерево удалённых процессов; его поддержка требует отдельного
решения на стороне владельца панели/протокола. При отказе самой ОС получить
новый снимок возвращается `None` с предупреждением — без глобального
включения несовместимой с Claude Code подмены.

Реализация `Pane`, обнаружение процессов, тесты кэша и таблицы клавиш
выделены в отдельные модули. Все изменённые и добавленные Rust-файлы этой
доработки ограничены 1000 строками; остальной репозиторий не декомпозирован.

## Проверка реализации

- `cargo build -p onlyterm-gui` — успешно.
- `cargo clippy -p onlyterm-gui -p mux -p procinfo --all-targets -- -D warnings` — успешно.
- `cargo fmt --all -- --check` — успешно, с прежними предупреждениями об unstable imports_granularity.
- `cargo test -p onlyterm-gui` — 140 passed, 4 ранее помеченных ignored.
- `cargo test -p mux --lib localpane::tests` — 15 passed.
- `cargo test -p procinfo` — 9 passed.
- `cargo test -p onlyterm-input-types` — 26 passed.

Rust/Cargo 1.97.0, Windows x86_64 MSVC. Новых unsafe-блоков и зависимостей
нет: добавлена только возможность `winerror` существующего winapi 0.3.9.
Существующие вызовы Toolhelp теперь проверяют ошибку до передачи handle
в RAII-обёртку и не отдают частичный результат перечисления как полный.
Нативный путь проверен тестами панели с реальным PID; Miri не запускался
(эти проверки обращаются к Win32).
