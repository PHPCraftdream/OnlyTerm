# Глюк рендера: курсор вверху экрана вместо строки промпта

Дата: 2026-08-21
Задача: #658
Среда: система-установленная сборка `C:\Program Files\OnlyTerm\onlyterm-gui.exe`,
`v0.0.14-alpha-5-g7cd27f37e` (коммит `7cd27f37e`, == текущий HEAD репозитория на момент
разбора — баг не связан с незакоммиченной работой этой сессии по `HostProcessBackend`).
PID живого процесса: 15072 (`--start-conf dev-forge.ktav`, окно `D:\dev_forge`).

## Симптом

Пользователь: «ввод переехал в верх экрана, хотя приглашение внизу». Скриншот показывает
окно терминала, где текстовый промпт шелла корректно находится внизу видимой области, но
курсор (место, куда фактически попадает вводимый текст) отображается ближе к верху экрана —
визуально оторван от промпта.

Триггер, названный пользователем: **баг проявился после долгого отсутствия** (окно долго
было в фоне/свёрнуто), после чего пользователь **вернул окну фокус и переключился на другую
вкладку**.

## Что исключено

- Не крах и не зависание: лог `onlyterm-gui.exe-log-15072.txt` не содержит ни одной паники,
  VEH-события или разрыва потока событий за всё время жизни процесса (с 08:50 до текущего
  момента) — только обычные `keyevent`/`keyboard_layout` diag-строки.
- Не два уже исправленных класса багов той же природы («курсор не на своей строке»),
  оба подтверждены как предки коммита `7cd27f37e` (`git merge-base --is-ancestor` → yes):
  - `a8e027f76` — cursor в колонке 0 при расширении окна ошибочно уезжал на предыдущую
    строку (`Screen::rewrap_lines`, `crates/term/src/screen.rs`).
  - `2c4006622` — слот курсора для `RowSweep`-исключения из бюджета считался от
    `physical_top` вместо реального `current_viewport`, что давало неверный слот при
    скролл-бэке (`crates/wezterm-gui/src/termwindow/render/budget.rs`,
    `crates/wezterm-gui/src/termwindow/render/pane.rs`).
- Не связано с сегодняшней работой над `HostProcessBackend` — установленный бинарник не
  содержит этого кода вообще (собран из того же коммита, что сейчас HEAD, до всех
  незакоммиченных изменений этой сессии).

## Правдоподобный механизм (одна цепочка, подтверждена чтением кода)

1. **`quad_generation` — это одно поле на всё окно**, не per-строка и не per-панель
   (`crates/wezterm-gui/src/termwindow/mod.rs:368`). Оно входит в
   `LineQuadCacheKey.quad_generation` (`render/mod.rs:80`) — ключ кэша построенных
   quad-ов для КАЖДОЙ строки терминала. Любое изменение этого поля разом делает
   cache-miss ВСЕ строки ВСЕХ панелей окна одновременно, а не одну строку.

2. **Оно бампается на каждой смене фокуса окна**, в обе стороны (потеря и получение):
   `focus_changed()`, `crates/wezterm-gui/src/termwindow/window_handler.rs:32`
   (`self.quad_generation += 1;`). То же самое происходит и на любой смене
   `window_state`/размера — `resize.rs:51` и `resize.rs:153` (`apply_dimensions`).
   Оба события естественно случаются ровно в описанном пользователем сценарии:
   окно свернули/увели из фокуса надолго, затем «открыл окно» — оконный фокус
   вернулся → `focus_changed(true)` → массовый bump.

3. **Бюджет перестройки строк по кадру ограничен по умолчанию** —
   `tab_frame_build_budget_ms` = 40 мс (`crates/config/src/config.rs:1305`), это
   рабочий дефолт, не выключен. Логика — `RowSweep::decide`
   (`crates/wezterm-gui/src/termwindow/render/budget.rs:88`): при cache-miss
   гарантированно перестраивается (`RowAction::Build`) только (а) строка, на которой
   реально сейчас курсор (`cursor_row_slot`, вычисляется каждый кадр заново и, после
   фикса `2c4006622`, корректно), и (б) одна "ротационная" строка, продвигающая
   прогресс перестройки. Все остальные cache-miss строки, если для них уже есть что
   показать (`has_retained == true`), при нехватке бюджета получают
   `RowAction::EmitRetained` — **повторно эмитятся их же quad-ы из прошлого
   реального рендера этой панели**, взятые из `RetainedPaneRows` (тот же файл,
   структура `RetainedPaneRows` в `render/mod.rs:123` — «what is currently on
   screen at visual row N», ключ по слоту, не по содержимому).

4. **Смыкание**: вкладка, которая долго простаивала в фоне (не активная — фоновые
   вкладки, по уже задокументированному в этой сессии факту, вообще не рендерятся),
   в момент последнего реального рендера могла иметь курсор на каком-то конкретном
   визуальном ряду. Этот ряд был закэширован в `RetainedPaneRows` вместе с
   отрисованным на нём курсором. Когда пользователь: (1) возвращает окну фокус
   (массовый bump `quad_generation`, все строки этой вкладки становятся cache-miss
   одновременно) и сразу (2) переключается на эту вкладку — рендер этой вкладки
   впервые за долгое время строит целый кадр разом, но бюджет в 40 мс не может
   перестроить все строки за один проход. Гарантированно свежими будут только
   истинная строка курсора (сейчас — внизу, у промпта: правильно) и одна ротационная
   строка; все прочие cache-miss строки — в том числе та, где раньше физически
   стоял курсор, — временно повторно показывают свои старые quad-ы из
   `RetainedPaneRows`, включая ранее нарисованный туда курсорный блок. На экране
   это выглядит ровно как «курсор наверху» (устаревший, зафиксированный до
   простоя) при полностью корректном промпте внизу (свежая, форсированная
   перестройка).

Ряд должен самоисправиться в течение следующих нескольких кадров, по мере того как
`RowSweep`'овская ротация дойдёт до него (`next_resume`, `budget.rs:116-119`) — то
есть баг ожидаемо визуально кратковременный / самоисчезающий, а не постоянный,
что соответствует тому, что пользователь не сообщал о зависшем навсегда фантомном
курсоре.

## Опровергнуто при более внимательном чтении

Первая версия этого документа утверждала, что причина — `RowSweep::decide` отдаёт
`RowAction::EmitRetained` (повтор старых quad-ов, включая устаревший курсор) для строки,
где раньше стоял курсор. Это неверно: перед циклом по строкам `paint_pane`
(`render/pane.rs:439-471`) сравнивает `current_stamp` (в него входит `quad_generation`)
с сохранённым `existing.stamp` **на уровне всей панели**. При несовпадении — а оно
гарантированно происходит после bump-а `quad_generation`, описанного выше — весь
`RetainedPaneRows` для этой панели немедленно сбрасывается в `rows: vec![None; ...]`
(`pane.rs:447-454`), **до** того как per-row цикл успевает что-либо прочитать. Дальше
`has_retained` (`pane.rs:586-592`) читает уже сброшенное состояние — то есть `false`
для абсолютно каждой строки в этом кадре. А в `RowSweep::decide`
(`budget.rs:100-104`) `!has_retained` безусловно форсирует `RowAction::Build`,
**в обход бюджета** (`must_build || ...` — бюджет проверяется только во второй ветке
условия). Тот же bump `quad_generation` делает `quad_generation`-часть ключа глобального
`line_quad_cache` иной, так что и там промах, а не старое попадание
(`RowAction::EmitCached` в этом кадре недостижим для затронутых строк).

Итог: кадр, следующий сразу за реактивацией долго простаивавшей вкладки, **обязан**
целиком перестроить каждую строку заново, используя один и тот же (корректный,
текущий) снимок `self.cursor` (`pane.rs:100`, `self.cursor: &cursor` в `LineRender`) —
то есть курсор в этом кадре физически не может оказаться не на своей строке через
описанный путь. Ни `EmitRetained`, ни устаревшее попадание в `line_quad_cache` не
объясняют симптом. Проверено также, что оба недавних фикса гонок в GPU-пути
(`de96bdd02`, `0e9807e0d`) уже входят в установленную сборку (`git merge-base
--is-ancestor` → yes для обоих) — это тоже не объяснение.

**Статус: причина не установлена.** Правило из личных инструкций пользователя —
не переходить к правке кода без одного убедительного, подтверждённого чтением кода
механизма — здесь не выполнено. Нужны дополнительные данные, а не ещё одна
непроверенная гипотеза.

## Что могло бы дать реальные данные (следующий шаг, не выполнено)

- Точечное trace-логирование в тестовой сборке (не трогая `D:\dev_forge`): значение
  `self.cursor.y` и `quad_generation` в момент каждого `paint_pane`, плюс момент
  сброса `RetainedPaneRows` — сравнить с тем, что реально появляется на экране.
- Управляемое воспроизведение: свернуть/увести фокус тестового окна на длительное
  время, вернуть фокus, переключить вкладку — с включённым логированием выше.
- Проверить, не связан ли симптом с оверлеями (copy-mode/quickselect —
  `overlay/copy/render.rs`, `overlay/quickselect.rs` — у них свой `set_viewport` и,
  возможно, отдельная, не проходящая через `LineQuadCacheKey` отрисовка курсора),
  если в момент ухода в фон в той вкладке был активен такой оверлей.

## Что не сделано

- Живое воспроизведение с контролируемым сценарием (свернуть окно на N минут → вернуть
  фокус → переключить вкладку → скриншотировать) не проводилось — сознательно,
  чтобы не трогать реальную рабочую сессию пользователя (`D:\dev_forge`, PID 15072)
  никакими вводами, только read-only захват экрана.
- Фикс не реализован. Обсуждается ниже как кандидат, требует подтверждения перед
  правкой кода (Investigation-паттерн: сначала одна credible-причина, правка — по
  запросу).
