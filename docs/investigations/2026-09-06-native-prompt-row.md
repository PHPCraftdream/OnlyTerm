# Первая строка CMD: независимая проверка ConPTY

## Результат

Переключение первой строки приглашения между 1 и 0 воспроизведено без
OnlyTerm, его модели экрана, GUI и пользовательского конфига.
На проверенном ConPTY стартовое приглашение CMD находится на строке 1;
уменьшение высоты на одну строку переносит его на строку 0.
Наша модель сейчас воспроизводит это поведение и сохраняет ввод рядом
с приглашением. Это не повторное обнаружение исправленного расхождения
между текстом и курсором.

Гарантия «первое приглашение всегда на строке 0» **не реализована**.
Добавлять для неё ещё один сдвиг координат в рендерер или Screen::resize
не следует. Требуется отдельная политика оболочки, а не исправление
эмуляции корректно полученного CRLF.

## Независимый эксперимент

- Библиотека из сборки: conpty.dll, FileVersion `1.22.2502.04002`,
  ProductVersion `1.22.250204002`.
- Отдельный процесс PowerShell/C# создаёт ConPTY напрямую, без GUI.
- Дочерняя команда: `cmd.exe /d /q /k "chcp 65001>nul & color f8"`.
- Только в окружении стенда задаётся `PROMPT=PROBE$G`.
- Выходной pipe постоянно читается; на запрос начальной позиции курсора
  стенд отвечает `ESC[1;1R`.
- Готовность определяется получением известного тестового приглашения,
  а не задержкой. Таймауты ограничивают зависание, не измеряют скорость.
- Через AttachConsole к собственному дочернему CMD читаются
  GetConsoleScreenBufferInfo и ReadConsoleOutputCharacterW.
  Это независимый источник координат и текста, не разбор нашей модели.
- После ResizePseudoConsole отправляется `xyz`; после его появления
  в выходном потоке повторно читается нативный буфер.
- Ввод удаляется Backspace, собственный CMD завершается через `exit`.
  Рабочие окна пользователя и его конфиг не изменялись.

Локальный экспериментальный стенд и полный вывод оставлены в игнорируемых
`.scratch/conpty-startup-probe.ps1` и `.scratch/conpty-startup-results.txt`.
Это диагностический прототип, не добавленный в CI интеграционный тест;
он должен запускаться отдельным процессом, поскольку использует AttachConsole.

| Флаги CreatePseudoConsole | Размеры | До resize: курсор | После resize и `xyz` |
|---|---|---|---|
| 0 | 80×24 → 80×23 | (6, 1), `PROBE>` на строке 1 | (9, 0), `PROBE>xyz` на строке 0 |
| 0 | 80×53 → 80×52 | (6, 1), `PROBE>` на строке 1 | (9, 0), `PROBE>xyz` на строке 0 |
| 7, как в OnlyTerm | 80×24 → 80×23 | (6, 1), `PROBE>` на строке 1 | (9, 0), `PROBE>xyz` на строке 0 |
| 7, как в OnlyTerm | 80×53 → 80×52 | (6, 1), `PROBE>` на строке 1 | (9, 0), `PROBE>xyz` на строке 0 |

Во всех четырёх случаях viewportTop равен 0. Нулевые индексы здесь
не следует путать с единичными параметрами ANSI CUP.

Начальный поток содержит цветовую заливку с DECSC/DECRC, затем
`CR LF PROBE>`. Поток после уменьшения во всех случаях:

```text
ESC[1;7Hxyz ESC[1;10H
```

Пробел между `xyz` и вторым ESC выше только разделяет запись:
реальный поток его не содержит. Приглашение повторно не передаётся.
Следовательно, оставить его на старой строке в нашей модели означало бы
снова отделить его от редактируемого ввода.

## Что это доказывает и чего не доказывает

Доказано происхождение наблюдаемого перехода 1 → 0 при уменьшении,
независимость этого воспроизведения от наших флагов 7 и соответствие
нынешней модели данному нативному сценарию.

Не доказано, что все варианты открытия вкладки проходят в точности эту
последовательность. В частности, порядок начального resize и первого
вывода в GUI в этом эксперименте не трассировался. Эксперимент также не
покрывает другие версии ConPTY, PowerShell, многострочные приглашения
и произвольные стартовые команды.

## Почему автоматический ClearPseudoConsole не принят

В проверенной ветке Microsoft `v1.22.10352.0` обработчик сигнала ClearBuffer
вызывает `ProcessString(L"\x1b[H\x1b[2J")`: переход домой и очистку экрана.
Это нельзя считать общим недеструктивным API «переместить приглашение».
Ранее предложенный план использовать его для автоматической нормализации
нуждается в пересмотре. Проверка исходника этой ветки не заменяет проверку
поведения конкретного DLL и его ABI.

Источники:

- [Нативный обработчик ClearBuffer](https://github.com/microsoft/terminal/blob/v1.22.10352.0/src/host/PtySignalInputThread.cpp#L182).
- [Вызов ClearBuffer из Windows Terminal](https://github.com/microsoft/terminal/blob/v1.22.10352.0/src/cascadia/TerminalConnection/ConptyConnection.cpp#L486).
- [Сигнатуры API ветки 1.22](https://github.com/microsoft/terminal/blob/v1.22.10352.0/src/inc/conpty-static.h#L35).

Одних маркеров OSC 133 тоже недостаточно: они обозначают границы prompt,
но не дают гарантии отсутствия уже набранного текста, фонового вывода
и не обеспечивают транзакцию между оболочкой, ConPTY и терминалом.

## Правильная граница решения

Эмулятор должен сохранять вывод и совпадать с координатами ConPTY.
Внешне одинаковая стартовая позиция — отдельная функция интеграции
оболочки: оболочка должна участвовать в выборе места первого prompt
и его безопасной перерисовке. Неизвестные оболочки, баннеры, команды
пользователя и многострочные prompt нельзя очищать по эвристике.

Для штатного CMD в этом исследовании такой безопасный протокол
не установлен. Поэтому производственный код не менялся, автоматическая
очистка, скрытие CRLF и подгонка координат не добавлялись.
