# DXGI adapter enumeration: research plan for avoiding the hybrid-graphics wake-up cost

Дата: 2026-08-11
Диапазон исследования: `wgpu` 25.0.2 / `wgpu-hal` 25.0.2 и 29.0.1 (обе версии проверены)

## Контекст

Профилирование холодного старта (см. `startup:`-чекпоинты в `crates/onlyterm-gui/src/main.rs` и
предыдущее расследование `docs/investigations/2026-08-03-startup-latency.md`, пункт `834e9acf3`)
показало, что после сужения перебора бэкендов до одного DX12 (было `Backends::all()`, тратившее
и на DX12 ~2.0с, и на Vulkan ~2.2с; стало — только DX12) остаётся необъяснённый разрыв ровно в
эти же ~2 секунды внутри самого `request_adapter` на DX12.

Причина найдена и подтверждена по исходникам `wgpu-hal`, не предположительно:

- `ProcessGpuContext::new` (`crates/onlyterm-gui/src/termwindow/webgpu/context.rs`) в общем случае
  (без `webgpu_preferred_adapter`) вызывает `instance.request_adapter(&wgpu::RequestAdapterOptions
  { power_preference, ... })`.
- Внутри `wgpu-core` 25.0.2 `request_adapter` перечисляет **все** DXGI-адаптеры через
  `wgpu_hal::dx12::instance::enumerate_adapters` →
  `auxil::dxgi::factory::enumerate_adapters` (`wgpu-hal-25.0.2/src/auxil/dxgi/factory.rs:67-94`),
  которая использует наивный `IDXGIFactory1::EnumAdapters1` — **не**
  power-preference-aware `IDXGIFactory6::EnumAdapterByGpuPreference`.
- Для **каждого** найденного адаптера вызывается `Adapter::expose(...)`
  (`wgpu-hal-25.0.2/src/dx12/adapter.rs:53`), которая создаёт временное `ID3D12Device` только
  ради опроса возможностей адаптера (`library.create_device(&adapter, D3D_FEATURE_LEVEL_11_0)`,
  строка 60-65 того же файла). Именно этот пробный `CreateDevice` выводит из энергосберегающего
  сна дискретную GPU на Optimus-ноутбуках.
- На тестовой машине 3 адаптера: Intel UHD Graphics (интегрированная, реально выбираемая),
  NVIDIA GeForce RTX 3050 Ti (дискретная, спит), Microsoft Basic Render Driver (программная).
  Пробуждение NVIDIA обходится в ~2 секунды и происходит впустую — она никогда не используется
  при `LowPower` (дефолт).
- То же самое подтверждено в `wgpu-hal` 29.0.1 (более новая версия, уже лежит в локальном кеше
  cargo) — идентичный код в `auxil/dxgi/factory.rs`. Апгрейд версии wgpu не решает проблему.

Путь с явным `webgpu_preferred_adapter` (фильтрация по имени/типу/бэкенду) тоже не спасает: он
использует `instance.enumerate_adapters(backends)` — тот же самый медленный путь, применяемый
ДО фильтрации по имени.

## Результаты исследования по пунктам

### 1. Публичный API `wgpu` для обхода полного перечисления

`wgpu` 25.0.2 действительно предоставляет hal-уровневые точки входа:

- `Instance::from_hal<A: HalApi>(hal_instance: A::Instance) -> Self`
  (`wgpu-25.0.2/src/api/instance.rs:160`) — построить `wgpu::Instance` из уже готового
  hal-инстанса.
- `Instance::as_hal<A: HalApi>(&self) -> Option<&A::Instance>`
  (`wgpu-25.0.2/src/api/instance.rs:179`) — получить ссылку на hal-инстанс из уже существующего
  `wgpu::Instance` (не нужно создавать второй).
- `Instance::create_adapter_from_hal<A: HalApi>(&self, hal_adapter: hal::ExposedAdapter<A>) -> Adapter`
  (`wgpu-25.0.2/src/api/instance.rs:257`) — обернуть уже готовый `wgpu_hal::ExposedAdapter` в
  `wgpu::Adapter`. Это именно то, что нужно было бы вызвать, если бы мы сами получили
  `ExposedAdapter` для одного конкретного адаптера.

Однако единственный способ получить `ExposedAdapter<Dx12>` — это `dx12::Adapter::expose(...)`, а
она объявлена **`pub(super)`** (`wgpu-hal-25.0.2/src/dx12/adapter.rs:53`) — видна только внутри
модуля `dx12` самого `wgpu-hal`, и **недоступна как внешний вызов** из кода, который зависит от
`wgpu-hal` как от обычного крейта. Ни `wgpu`, ни `wgpu-hal` не экспортируют публичной обёртки над
`expose()`, которая принимала бы один конкретный `IDXGIAdapter1` и не трогала остальные.

Сама `expose()` — это не только вызов `CreateDevice` (которого мы и пытаемся избежать для
ненужных адаптеров), но и ~150 строк опроса feature level, downlevel capabilities, workarounds,
architecture info — используя приватные хелперы (`auxil::dxgi::conv::map_adapter_name`,
`super::Workarounds` и др.), тесно привязанные к конкретной версии `wgpu-hal`.

**Вывод: тупик на уровне видимости модулей.** Публичного, безопасного способа получить
`ExposedAdapter` для одного заранее выбранного адаптера, минуя `enumerate_adapters`, у `wgpu`
25.0.2 нет.

### 2. Конкретные вызовы DXGI + конфликт версий `windows`

Даже если бы `expose()` была публичной, самостоятельный вызов
`IDXGIFactory6::EnumAdapterByGpuPreference` упирается во вторую проблему: `wgpu-hal` 25.0.2
зависит от `windows = "0.58"` (`wgpu-hal-25.0.2/Cargo.toml:406-410`), тогда как весь остальной код
репозитория (включая `onlyterm-gui`) закреплён на `windows = "0.33.0"` (корневой `Cargo.toml:246`).

Крейт `windows` не даёт бинарной/типовой совместимости между минорными версиями 0.x — тип
`IDXGIAdapter1` из `windows 0.33` и тип `IDXGIAdapter1` из `windows 0.58` это **разные,
несовместимые типы** на уровне компилятора, несмотря на то что оборачивают один и тот же
COM-интерфейс. Передать значение одного в API, ожидающее другой, нельзя без ручного unsafe
преобразования через сырые указатели (трансмьют по слою ABI COM, а не безопасный `From`/`Into`).

Чтобы состыковаться с `wgpu-hal`, пришлось бы либо:
- завести отдельную, дублирующую зависимость `windows = "0.58"` рядом с уже используемой `0.33`
  (Cargo это технически позволяет — крейты можно держать в разных мажорных версиях одновременно),
  что увеличивает объём кода/времени сборки и создаёт путаницу «какой версией пользоваться где»;
- либо писать сырые FFI-вызовы в обход обеих версий `windows` (`windows-sys`/ручные биндинги) —
  тяжелее и ещё больше unsafe-поверхности.

### 3. Нужно ли закрывать и путь `webgpu_preferred_adapter`

Да, в теории нужно — он страдает от той же причины (`instance.enumerate_adapters` перед
фильтрацией по имени). Но поскольку блокер (пункты 1-2) относится к **любому** способу получить
`ExposedAdapter` не через полное перечисление, единое решение закрыло бы оба пути одновременно —
отдельного решения именно для `webgpu_preferred_adapter` не требуется. Приоритет ниже: пользователь,
явно указавший конкретную видеокарту, статистически меньше заботится о паре секунд старта, чем
о том, что фолбэк вообще решён.

### 4. Требование безопасного фолбэка

Формально спроектировано (на случай, если пункт 1 когда-нибудь станет решаемым — например, после
патча/форка `wgpu-hal`, или апгрейда на версию, которая экспортирует нужный API публично):
быстрый путь оборачивается в `Result`/`Option`, и при любой ошибке (нет `IDXGIFactory6` —
старый Windows, ошибка `EnumAdapterByGpuPreference`, паника при построении `ExposedAdapter`)
код должен просто ничего не менять и передать управление в уже существующий
`instance.request_adapter(...)` — тот самый путь, что работает сегодня. Место в коде:
`ProcessGpuContext::new`, непосредственно перед текущим вызовом `request_adapter`
(`context.rs`, внутри `run_on_background_thread`'s closure, вокруг существующего блока
`if adapter.is_none() && may_settle_for_any_adapter { adapter = ...request_adapter... }`).
Эта часть плана остаётся зафиксированной здесь, реализовывать её сейчас не на чем.

### 5. Альтернатива: кэширование LUID между запусками

Идея: сохранить LUID успешно выбранного адаптера (например, в кэш-директории OnlyTerm) и на
следующих запусках запрашивать именно его напрямую — Windows действительно предоставляет
`IDXGIFactory4::EnumAdapterByLuid` для запроса по LUID без полного перечисления.

Это **не обходит блокер**, а лишь меняет то, ГДЕ мы находим нужный `IDXGIAdapter1`
(`EnumAdapterByLuid` вместо `EnumAdapters1` в цикле) — итоговый `IDXGIAdapter1` всё равно нужно
превратить в `wgpu::Adapter`, а единственный путь для этого — та же самая приватная `expose()`.
Кэширование LUID устранило бы **повторное перечисление** (сам `EnumAdapters1`/цикл поиска), но
не устранило бы главный источник задержки — пробное `CreateDevice` внутри `expose()`, которое
в любом случае должно быть вызвано хотя бы раз для выбранного адаптера. Поскольку сегодня
пробуждается НЕ выбранный адаптер (NVIDIA), а его пробуждает опрос ВСЕХ адаптеров, кэширование
LUID само по себе годится только вкупе с решением пункта 1 (чтобы кэшированный LUID использовался
для получения ОДНОГО `IDXGIAdapter1` в обход `EnumAdapters1`-цикла), а не как независимая замена.

Отдельно: жизнеспособность самого LUID со временем не гарантирована (переустановка/обновление
драйвера, отключение внешней GPU, докстанция — LUID адаптера может измениться), так что такой кэш
потребовал бы отдельной валидации и фолбэка на полное перечисление при промахе — то есть решает
проблему только частично и добавляет свою сложность.

## Рекомендуемый подход

**Безопасного, низкорискового способа сделать это через публичный API `wgpu` 25.0.2 (и 29.0.1 —
тоже проверено) сегодня не существует.** Оба реальных пути наружу требуют либо форка/патча
`wgpu-hal` (сделать `expose()` публичной или добавить свой публичный метод перечисления с
поддержкой `EnumAdapterByGpuPreference`), либо полного самостоятельного переписывания логики
`expose()` вне `wgpu-hal` (хрупко, привязано к приватным деталям реализации конкретной версии,
ломается при каждом апгрейде зависимости).

Практические варианты на выбор:

1. **Принять стоимость.** Затрагивает только пользователей с гибридной графикой (Optimus-подобные
   ноутбуки), и только при холодном старте процесса — прогретый путь (после наших фиксов
   `get_or_init`/`lost`-флага) переиспользует уже созданный контекст мгновенно для всех
   последующих окон в том же процессе.
2. **Завести issue/PR в `gfx-rs/wgpu`** с точным описанием проблемы (эта находка — готовый
   материал для баг-репорта: конкретные тайминги, конкретные строки кода, воспроизводится в двух
   версиях подряд). Так проблема решается один раз для всей экосистемы, а не патчем в форке.
   Не в нашем контроле по срокам, но наименее рискованный путь к настоящему исправлению.
3. **Форкнуть/патчнуть `wgpu-hal`** (via `[patch.crates-io]` в корневом `Cargo.toml`, с локальной
   копией крейта, где `expose()` помечена `pub`, плюс добавить свой публичный метод
   `enumerate_one_adapter_by_gpu_preference` или подобный). Технически осуществимо, но означает
   постоянное сопровождение форка зависимости — каждый апгрейд `wgpu` требует ре-патчинга и
   слежения за тем, не поменялась ли внутренняя структура `expose()`. Учитывая объём внутренней
   логики `expose()` (feature levels, downlevel caps, workarounds), риск тихо разойтись с
   апстримом и получить некорректные возможности адаптера — реальный, не гипотетический.

Ни один из вариантов 2-3 не рекомендуется реализовывать в рамках этой задачи без отдельного
явного решения пользователя — оба выходят за рамки «почитать код и предложить план», который
был целью этого расследования.

## Реализация и измерение (2026-08-12, отдельным решением пользователя)

Пользователь явно выбрал вариант 3 (форкнуть/патчнуть `wgpu-hal`) вопреки рекомендации выше.
Реализовано минимальным, аддитивным патчем — см. коммиты `c41df6b09` (реализация) и
`10a944467`/`a335c12d3`/`80c384484` (предшествующие в цепочке: миграция `windows` 0.33→0.58,
не связанный фикс Alt+V, не связанный фикс мерцания при старте).

**Патч** (`crates/wgpu-hal-vendored`, копия `wgpu-hal` 25.0.2 из crates.io, подключена через
`[patch.crates-io]`): вместо предложенного в пункте 1 варианта «сделать `expose()` публичной»,
использован более узкий и безопасный подход — новый метод
`dx12::Instance::fast_preferred_adapter` добавлен **внутри** модуля `dx12` (тот же модуль, где
уже объявлена `expose()`), поэтому существующая видимость `pub(super)` для `expose()` менять не
пришлось вообще. Единственные видимость-правки: `should_keep_adapter` расширена с приватной до
`pub(crate)`, добавлен `DxgiFactory::as_factory6` (аналог уже существующего `as_factory5`).
Проблема конфликта версий `windows` (пункт 2) к моменту реализации уже была снята отдельной
полной миграцией на `windows = "0.58"` (`10a944467`), так что второй блокер исчез сам собой.

**Интеграция** (`crates/onlyterm-gui/src/termwindow/webgpu/context.rs`,
`try_fast_dx12_adapter`): вызывается ДО обычного `request_adapter`, только когда нет
`webgpu_preferred_adapter`/`webgpu_force_fallback_adapter` (см. пункт 3 выше — эти пути
сознательно оставлены на медленном, но точно корректном пути). Любая неудача (нет
`IDXGIFactory6`, адаптер отфильтрован, что угодно) — `None`, и код падает обратно на
существующий `request_adapter` без каких-либо изменений поведения.

### Замеры (3 прогона патченной версии, 2 прогона baseline на том же коммите без патча,
через `git worktree` на `80c384484`, тот же процесс/машина, `startup:`-чекпоинты)

| | GPU init → Device ready | logger ready → first frame |
|---|---|---|
| baseline #1 | 2.916s | 4.007s |
| baseline #2 | 1.798s | 2.896s |
| patched #1 | 0.575s | 1.749s |
| patched #2 | 0.539s | 1.662s |
| patched #3 | 0.561s | 1.772s |

Во всех трёх патченных прогонах в логе присутствует строка `startup: fast DX12 adapter
selection (EnumAdapterByGpuPreference) succeeded` — быстрый путь действительно срабатывает на
этой машине, не проваливается в фолбэк. Сегмент "GPU init → Device ready" сократился
приблизительно в 3.5-5.4 раза (0.54-0.58с против 1.8-2.9с), полное время до первого кадра — в
1.6-2.3 раза (1.7-1.8с против 2.9-4.0с). Разброс baseline (1.8с vs 2.9с) правдоподобно связан с
переменным состоянием сна дискретной GPU между прогонами; патченная версия стабильна во всех
трёх измерениях (0.54-0.58с), что само по себе подтверждает, что причина разброса устранена —
дискретная GPU больше не пробуждается и не участвует в тайминге вообще.

В отличие от эксперимента с DXC этого же сессионного окна (тоже теоретически обоснованный,
но давший нулевой измеримый выигрыш), здесь эффект большой, воспроизводимый и однозначно
привязан к добавленному коду через саму лог-строку успеха быстрого пути.

**Не измерено:** поведение на машине без гибридной графики (там `fast_preferred_adapter`,
скорее всего, просто вернёт тот же единственный адаптер без выигрыша, но и без потерь — не
проверено фактическим прогоном); поведение при `HighPerformance`-предпочтении (замеры выше — все
при дефолтном `LowPower`); поведение на Windows без `IDXGIFactory6` (пре-1803, фолбэк не
прогонялся вживую, только прочитан по коду).
