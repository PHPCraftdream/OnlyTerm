# Checkpoint — 2026-07-28 08:19 [hebrew-bidi-font-scrollbar-fixes]

## Session summary
Continuation of the OnlyTerm (fork of onlyterm) project. This segment started right after the prior segment's amend+force-push of changelog/checkpoint docs, and covered a wide batch of user-requested improvements plus one serious, hard-to-pin-down crash investigation.

1. **Windows default font**: added a Windows-specific `default_font_style()` making `Lucida Console` the default font (JetBrains Mono kept as automatic fallback). Later in the session, after investigating with `onlyterm-gui ls-fonts --text "..."` and confirming Lucida Console resolves correctly but is legitimately narrow (`usWidthClass=4`/SemiCondensed per the font's own OS/2 table) and differs in `font_size` (12 default vs the user's other real OnlyTerm install's manual `14.0`), the user chose to **revert to JetBrains Mono as the default font** instead of chasing Lucida Console's sizing. This revert is applied (`default_font_style` function and its Windows-specific FontAttributes-based override were removed entirely; `pub font: TextStyle` field is back to plain `#[dynamic(default)]`, which resolves to `TextStyle::default()` = JetBrains Mono). Confirmed via `ls-fonts` after rebuild: `onlyterm.font("JetBrains Mono", {stretch="Normal"})`.
2. **Hebrew support added**: bundled `Noto Sans Hebrew` (SIL OFL 1.1, full niqqud/cantillation coverage, verified via fontTools cmap check covering all 55 codepoints in the Hebrew points block) as a new automatic fallback font, wired through a new `vendor-noto-hebrew` Cargo feature (mirroring the existing `vendor-noto-emoji` pattern) in `onlyterm-font`/`onlyterm-gui` Cargo.toml, `parser.rs`'s `load_built_in_fonts`, and `config/font.rs`'s `font_with_fallback()`. Considered bundling `Miriam Mono CLM` (Culmus project) but rejected it since it's GPL-2.0-or-later without a font exception, inconsistent with the project's MIT license and the existing OFL-only bundled-font convention.
3. **bidi enabled by default**: `bidi_enabled` now defaults `true`, `bidi_direction` defaults `AutoLeftToRight` (was `false`/`LeftToRight` upstream) — matches what the user's own now-dead `wezterm.lua` used to set manually. The underlying bidi algorithm itself (`crates/bidi`) is a complete, hand-rolled UAX#9 implementation already validated against the official Unicode `BidiTest.txt`/`BidiCharacterTest.txt` conformance suites (confirmed by running `cargo test -p onlyterm-bidi`) — nothing in the algorithm itself was touched, only the two config defaults.
4. **Scrollbar fixed and tuned**: root cause of "scrollbar disappeared" was simply that `enable_scroll_bar` defaults to `false` upstream, and the user's own manual enable (via the now-dead, pre-Rhai-migration `wezterm.lua`) no longer applies. Fixed by defaulting `enable_scroll_bar=true`, widening the auto-sized scrollbar from 1 cell to 1.75 cells (`effective_right_padding` in `resize.rs`), and raising `min_scroll_bar_height` default from `0.5cell` to `2cell`. No auto-hide-on-idle logic was found in the codebase, so "never hide it" is satisfied simply by the enable-by-default fix.
5. **Selection-after-mouseup bug fixed**: `CompleteSelectionOrOpenLinkAtMouseCursor` (the default left-click-release binding) was unconditionally clearing the selection right after copying it — a regression introduced in an earlier session's commit `42361b9fb` (which added it while fixing Ctrl+C, based on an incorrect belief that left-click already had this copy-then-clear pattern). Removed the erroneous `clear_selection` call; clicking elsewhere still clears naturally via `Selection::begin()` resetting `range=None` on the next mouse-down; right-click and Ctrl+C still explicitly copy-then-clear as the user wanted.
6. **Ctrl+V paste fixed**: `PasteFrom(Clipboard)`'s default `keys` only listed `SUPER+v` (macOS Cmd+V) and the OS "Paste" gesture; `permute_keys`'s SUPER-branch synthesis only expands into `CTRL+SHIFT+v` alternates, never plain `CTRL+v` — so on Windows, plain Ctrl+V silently did nothing. Added an explicit `(Modifiers::CTRL, "v")` key entry. New regression test `ctrl_v_pastes_from_clipboard` added and passing.
7. **App icon darkened**: the chevron/arrow logo (`assets/icon/terminal_master_1024.png`, a mint-green feather/arrow shape) had weak contrast against white. Darkened it via a Python/Pillow script (HSV value scaled down proportionally to saturation, leaving the white background and pale underline mark mostly untouched) and regenerated `terminal.png`, `terminal.ico` (all 7 sizes), and `terminal.icns`.
8. **Major, ultimately-unresolved crash investigation**: the user reported the GUI crashed while Claude Code (the CLI tool, not the user typing) printed Hebrew text to the terminal. The exact panic: `"end byte index 2 is not a char boundary; it is inside 'ם' (bytes 1..3 of string)"` inside `onlyterm-font`'s `RustybuzzShaper::do_shape` (`crates/onlyterm-font/src/shaper/rustybuzz.rs:601`, `ClusterResolver::build`/`get`). Spent very extensive effort trying to reproduce this via targeted `cargo test` cases in `onlyterm-font` (added `shapes_hebrew_text_with_niqqud_under_bidi`, still present in the codebase, all currently passing): tried plain Hebrew+niqqud text, niqqud combined vs. split into separate cells (simulating a base letter and its combining mark arriving via separate print/flush cycles), Hebrew mixed with an ASCII prefix (to force non-zero-start recursive font-fallback, since neither JetBrains Mono nor Lucida Console has ANY Hebrew coverage — confirmed 0/27 letters, 0/55 niqqud via fontTools), and the full realistic 5-font default stack (Lucida Console/JetBrains-Mono-as-primary-substitute, JetBrains Mono, Noto Color Emoji, Noto Sans Hebrew, Symbols Nerd Font Mono) with real on-disk Lucida Console loaded via `ParsedFont::from_locator`. **None of these reproduced the crash.** The root cause remains unconfirmed. One serious hypothesis (rustybuzz's `info.cluster` values being relative to the pushed sub-buffer `s[range]` during recursive fallback, while `ClusterResolver::build`/`do_shape`'s main body treat them as absolute offsets into the full `s` whenever `range.start != 0`) was investigated in depth and seemed very plausible on paper, but did not reproduce empirically even in a targeted test built specifically to trigger it.
9. Given the reproduction dead-end, pragmatically **hardened the crash site instead of full root-causing it**: added a `clamp_to_char_boundaries(s, range)` helper in `rustybuzz.rs` that walks `start`/`end` outward to the nearest real char boundary before slicing, with a `log::warn!` if it ever actually has to adjust anything (so if/when this fires in the field again, there will be a log line pinpointing it instead of a crash). This guarantees the specific panic can no longer occur, even though the underlying algorithmic mismatch (if any) is still not fully understood. This should be treated as **provisional** — if the crash recurs, the warning log from this defensive clamp is the next lead to chase.
