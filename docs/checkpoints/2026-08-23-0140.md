# Checkpoint — 2026-08-23 01:40 [oom-fixed-release-pipeline-unblocked]

## Session summary

Continuation of the GPU-crash-isolation thread. Started from the previous
checkpoint (`2026-08-21-1430.md`), which left `HostProcessBackend` shipped as the
unconditional default. This session's spine was a second, different production
crash and everything that unspooled from it.

Two real OnlyTerm windows died with `0xc0000409` while the user worked. That code
reads as a stack-buffer overrun, but the symbolized stack from the 5.3 GB dump
(`C:\CrashDumps\OnlyTerm\onlyterm-gui.exe.64440.dmp`, analysed with `cdb` from the
WinDbg Store package against the matching PDB) was unambiguous: it is Rust's OOM
abort path -- `alloc::raw_vec::handle_error` -> `handle_alloc_error` -> `rust_oom`
-> `abort` -- synchronous on the main GUI thread inside `WM_PAINT`, at
`paint.rs:143` (`paint_impl` -> `call_draw`). Note the PID: an early hex-to-decimal
misread sent me to 67704 (an unrelated, already-closed process) before the correct
64440.

The dump then answered *why*, which mattered because my first written hypothesis
(the `AtlasMirrorLog` 128 MiB budget added earlier that same day) was **wrong** --
its warning never fired in the crashed processes' logs. `!address` showed 4.22 GiB
of the 4.68 GiB committed sitting in 1081 dedicated 4 MiB arenas of the user's own
custom global allocator (`sefer-alloc` 0.2.1, their crate, repo at
`D:\dev\rust\sefer-alloc` / github.com/PHPCraftdream/sefer-alloc). Sampling arena
headers proved the shape: a monotonic per-arena serial (I sampled every 27th arena
and got serial deltas of exactly 27) and a steadily growing used-bytes field, 278 KB
early to 435 KB late -- one large allocation per arena, created frame after frame.
The payload decoded as `QuadInstance` data: byte stride exactly 84, matching
`size_of::<QuadInstance>()` (pinned by a test), fields reading correctly as
position / `fg_color=[1,1,1,1]` / `tex` in 0..1 / `hsv` / flag.

Those blocks could not have been live -- `call_draw_webgpu` returns early on
`is_in_flight()` before `build_wire_frame` runs at all -- so ~1079 were freed and
their arenas never reused. The user made the decisive observation that older builds
with the same allocator are fine, which correctly reframes it: **the allocator is
the amplifier (~10x), our code is the trigger.** Filed the allocator half as
PHPCraftdream/sefer-alloc#1.

Fixed in three layers: parent draw buffers pooled with a return path from the
writer thread (delegated to an `o3h` agent, its diff and test non-vacuity verified
here); the serialization body buffer reused (the user's own commit, closing a hole
I had missed -- `write_frame` was allocating a second ~400 KB buffer per frame);
and the child `gpu-tab-host`, which had the identical defect untouched, rewritten
to parse frames in place as borrowed slices (`read_message_into` / `WireFrameRef` /
`BorrowedAtlasImage`) since it never needed to own anything -- draws go straight
into a wgpu vertex buffer, atlas pixels straight into a texture write.

In parallel the user landed four commits splitting the build up
(`wezterm-gpu-protocol`, `wezterm-color-schemes-data`, `wezterm-gui-render-thread`)
and one removing Nerd Fonts entirely. The Nerd Fonts removal turned out to be a
real regression: those glyphs are used for **content** (the user's shell prompt
draws powerline separators), and the bundled `SymbolsNerdFontMono` was the universal
fallback. It surfaced as a "Font problem: no fonts contain glyphs for \u{e0cc}"
toast and a failing `ligatures_jetbrains` test. On request I rewrote history to
erase the deletion. Crucially, dropping that commit alone was not enough: the
removal had **leaked into the refactor commit**, which silently dropped
`vendor-nerd-font-symbols-font` from `wezterm-gui/Cargo.toml`. That feature is what
actually gates the font (the `#[cfg(any(test, feature = ...))]` in `parser.rs`;
`cfg(test)` does not apply when `wezterm-font` builds as a dependency), so the font
file alone would never have loaded. Amended that commit too.

Ended on CI. Tagging `v0.0.15-alpha` built nothing, and investigation found the
release pipeline had never worked in this fork for three independent reasons --
tag pattern `20*` (upstream's date scheme), an
`if: github.repository == 'wezterm/wezterm'` gate on the upload job, and artifact
naming derived from commit date rather than the tag. All three fixed, plus removal
of winget publication that would have pushed manifests under the `wez.wezterm`
identity once the gate opened. Tag was deleted and recreated on HEAD so the fixed
workflow would be the one used. `windows_tag` is running for the first time in this
repository's history; result unknown at checkpoint time.

## Decisions

- Treated the allocator as amplifier, not cause, on the user's evidence that older
  builds with the same allocator are stable. Fixed our allocation pattern in the
  repo and filed the allocator behaviour separately rather than blocking on it.
- For the child process, chose borrowed in-place parsing over a second buffer pool:
  it needs no owned copies at all (wgpu copies on both paths), so this removes three
  allocations instead of recycling them, at the cost of a parallel `WireFrameRef`
  type. Rejected pooling as more bookkeeping for a strictly worse result.
- Rejected serializing on the GUI thread (the alternative to the parent draw-buffer
  pool): it moves the ~400 KB memcpy onto the thread the current design deliberately
  keeps free.
- Erased the Nerd Fonts removal from history rather than reverting it, per explicit
  request; had to amend the *refactor* commit as well, since the feature-flag half of
  the removal had leaked there.
- Left `ci/tag-name.sh` untouched and used `github.ref_name` in the tag workflow
  instead. Changing that script would have broken `ci/tag.sh`, whose job is to create
  a new date-based tag.
- Removed winget publication outright rather than re-pointing it: it would have
  published this fork under upstream's package identity.
