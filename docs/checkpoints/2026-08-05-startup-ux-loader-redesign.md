# Checkpoint — 2026-08-05 [startup-ux-loader-redesign]

## Session summary

Продолжение большой сессии по OnlyTerm (Windows-форк onlyterm, конфиг ktav,
без Lua/rhai). Эта видимая часть сессии сфокусирована на цикле Startup UX
(#382-#385, полностью закрыт ранее) и его последующем практическом
тестировании пользователем, которое вскрыло СЕРЬЁЗНУЮ архитектурную
находку, а не мелкие баги.

**Главная находка этой части сессии: OnlyTerm использовал однопроцессную
модель GUI.** Обычный запуск (ярлык/меню, без флагов) подключался к уже
работающему GUI-процессу через `gui-sock` (Unix-домен) и просил ЕГО открыть
окно — вместо запуска независимого процесса. Пользователь месяцами держал
один и тот же старый процесс запущенным (не перезапускался), и каждое
"новое окно" на самом деле было новой вкладкой/окном В ЭТОМ старом процессе
— со старым кодом, без бандленных Noto Sans Symbols/Symbols 2 (#370) и без
фикса детерминизма fallback-резолвера (#381). Hot-swap install
(ci/dev-install.ps1) сознательно не обновляет уже запущенные процессы —
поэтому казавшийся WebGpu-специфичным баг с "тофу" (#395, долгое
расследование с диагностическим логированием, temp-тестами, изоляцией
конфига) на самом деле был просто "вы тестируете старый код". Пользователь
прямо потребовал: "надо раз и навсегда уйти от однопроцессной модели...
новый процесс должен сам себе создавать все свои обвязки, не зависеть от
ничего запущенного" — выполнено (#404): весь механизм `Publish::
TryPathOrPublish`/`try_spawn` (IPC-делегирование спавна другому GUI)
полностью удалён, заменён на простую `should_publish_gui_sock()`. Теперь
КАЖДЫЙ запуск — независимый процесс. #395 закрыта как "не баг, а
устаревший процесс".

**Побочные находки, тоже исправленные в этом же окне:**
- **#403**: fancy tab bar (`use_fancy_tab_bar=true` по умолчанию) читал
  цвета из сырого `config.colors` вместо `config.resolved_palette.tab_bar`
  — без явного конфига падал на старые тёмные upstream-дефолты, хотя весь
  остальной терминал уже светлый (форк-дефолт `default_colors()` в
  config_impl.rs). Исправлено чтением `resolved_palette.tab_bar`.
- **#406**: пользователь прислал скриншот с "буквы полумесяцем"/"корявый"
  лоадер — оказалось, это спиннер (#384) из 8 точек, чей радиус был жёстко
  ограничен потолком в 48px независимо от размера окна — на большом
  (1920x1080) окне превращался в нечитаемую кроху. Диагностировано ВИЗУАЛЬНО:
  написан временный `#[cfg(test)]` в window.rs, рендерящий
  `draw_placeholder_spinner` в offscreen DIB при разных размерах, сохранял
  как BMP → конвертировал в PNG через PowerShell (`Add-Type
  -AssemblyName System.Drawing`) для просмотра инструментом Read (BMP
  напрямую не читается). Подтверждено, исправлено (потолки подняты до
  120px/18px), тест убран, закоммичено.
- Пользователь затем попросил "красивые прогрессы" вместо точек — через
  `AskUserQuestion` с ASCII-превью выбрал вариант **"Loading..." с
  анимированными точками** (не индетерминированная полоса, не пульсирующий
  круг). Реализовано: `PlaceholderSpinner` struct переписан с
  `dot_brush`/`dot_pen` на `text_color`/`font` (HFONT, "Segoe UI", создаётся
  через `CreateFontW`), `draw_placeholder_spinner` теперь красит фон и
  рисует "Loading" + 0-3 точки (цикл ~1.4с, как и раньше) через `DrawTextW`
  с `DT_CENTER|DT_VCENTER|DT_SINGLELINE`. Имена структуры/функции оставлены
  как есть (не переименовывались) — задокументировано как сознательный
  компромисс против churn. Визуально перепроверено тем же offscreen-DIB
  методом (детерминированный форс конкретного количества точек через
  подмену `spinner.started` на бэкдейченный `Instant`) — текст читается
  чисто на обоих размерах (800x600, 1920x1080).

**Отдельная, ещё НЕ решённая задача (#405):** пользователь жалуется, что
лоадер появляется с заметной задержкой после старта процесса. Добавлена
временная диагностика (`TEMPDIAG_405_START: OnceLock<Instant>` в main.rs,
устанавливается первой строкой `main()`; два `log::info!` чекпоинта в
render_pipeline.rs — вход в `new_window()` + время `FontConfiguration::new`,
и непосредственно перед `window.show()`) — это ГОЛОВНОЕ число: всё время
от старта процесса до реального показа окна/лоадера. Ещё НЕ протестировано
пользователем (диагностика написана и должна собираться, но сборка,
запущенная непосредственно перед этим чекпоинтом, была вручную забэкграунжена
пользователем прямо перед `/checkpoint` — её результат НЕ подтверждён).

**Отдельная, ещё НЕ начатая задача (#407):** пользователь сообщил, что
если в фоне открыто ДРУГОЕ окно OnlyTerm (актуально теперь, когда #404
сделал каждое окно отдельным процессом), в текущем окне появляются "белые
прямоугольники и прозрачные фоны". Гипотеза (не проверена): классический
баг "не перерисовалось при открытии области, ранее перекрытой ДРУГИМ окном"
— WebGpu swap chain или GDI-путь заглушки/лоадера могут не обрабатывать
корректно этот случай (в отличие от #392's фикса, который был про resize/
rebuild САМОГО СЕБЯ, не про перекрытие чужим окном). Расследование не
начиналось — сначала доводилась работа над #405/#406.

Фоновый `/babysit` (интервал 15 минут, cron `5ab087e5`) активен и продолжает

## Decisions

- #404: убран весь механизм GUI-к-GUI IPC-делегирования спавна (не просто
  флагом отключён — физически удалён `Publish::TryPathOrPublish`/
  `try_spawn`), но публикация СВОЕГО gui-sock (`should_publish_gui_sock`)
  оставлена — используется отдельной, легитимной функциональностью
  (`onlyterm cli`-подобные инструменты находят запущенный GUI для
  управления им; `onlyterm-client/src/client/mod.rs:428`).
- #406/лоадер: имена `PlaceholderSpinner`/`draw_placeholder_spinner`
  оставлены без переименования при переходе с точек на текст "Loading..."
  — сознательный выбор против unrelated rename churn, задокументировано
  комментарием в коде.
- Дизайн лоадера выбран пользователем явно через `AskUserQuestion` с ASCII-
  превью трёх вариантов (полоса-прогресс / пульсирующий круг / текст с
  точками) — выбран текстовый вариант.
- Диагностика #405/#406 каждый раз реализовывалась как временный
  `#[cfg(test)]` модуль с offscreen-DIB рендерингом + конвертацией BMP→PNG
  через PowerShell для визуальной проверки (Read-инструмент не читает BMP
  напрямую) — использовано дважды (#406 находка, #406 подтверждение
  фикса), тест каждый раз убирался перед коммитом.
