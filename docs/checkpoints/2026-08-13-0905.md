But live testing (both my own scripted clicks and the user manually clicking on the visible test window)
surfaced two real, previously-undetected bugs in the merged Phase B code:

1. **Double-spawn / stray window**: `spawn_single_pane_tab` (`crates/wezterm-gui/src/spawn.rs`) called
   `domain.attach()` *and then* an explicit `mux.spawn_tab_or_window()` RPC. The `--single-pane` server
   already spawns its one-and-only pane at startup, and `attach()` alone already materializes that pane
   as a tab — the extra explicit spawn asked the server for a second pane it isn't designed to host,
   producing 2 tabs + 1 stray window per click (user directly observed and reported this). Fixed by
   removing the explicit spawn entirely and instead passing `--cwd`/`--priority`/prog-args as CLI args on
   the `--single-pane` child process (added a new `--priority` flag to `wezterm-mux-server`, parsed
   against `config::keyassignment::ProcessPriority`'s variant names).
2. **Visible console window**: `unix_connect_with_retry`'s `UnixTarget::Proxy` branch
   (`crates/wezterm-client/src/client/conn.rs`) spawned the `onlyterm-mux-server.exe` child via plain
   `std::process::Command` with no `CREATE_NO_WINDOW` — since it's a console-subsystem binary spawned
   from a console-less GUI parent, Windows allocated it a new visible console every time (user directly
   observed this too: "появляется cmd окно видимое"). Fixed with `cmd.creation_flags(0x0800_0000)` under
   `#[cfg(windows)]`.

Rebuilding and re-testing after those two fixes surfaced a **third** bug: opening a tab took 4-26s with a
raw technical "Connecting..." text log as a visible placeholder tab, which invited impatient repeat
clicks — each one spawning its own redundant `onlyterm-mux-server.exe` (confirmed live: 7-9 orphaned
child processes accumulated from a handful of clicks). User asked for a proper fix (not a workaround),
chosen explicitly via `AskUserQuestion`. Implemented:
- A **debounce** in `spawn_single_pane_tab` (`pending_single_pane_spawns`, a `Mutex<HashSet<MuxWindowId>>`
  + RAII `PendingSpawnGuard`) — a repeat "new tab" trigger for a window that already has one of these
  spawns in flight is silently dropped instead of piling up another hosting process.
- A new `ClientDomain::attach_with_spinner` (`crates/wezterm-client/src/domain/mod.rs`), refactored out
  of the existing `attach()` via a shared `attach_impl(window_id, ui, verbose: bool)`: reuses the exact
  same termwiztermtab-backed placeholder-tab mechanism `Domain::attach` already uses (so the tab appears
  immediately and becomes the window's active/focused tab automatically, for free, via
  `Window::save_and_then_set_active` inside `termwiztermtab::register_tab`) but shows a plain animated
  spinner instead of the raw connection log. First spinner attempt used Braille Patterns glyphs
  (⠋⠙⠹...), which rendered as tofu/missing-glyph boxes in the configured font (confirmed live by the
  user) — switched to a plain ASCII `|/-\` spinner, which any monospace font is guaranteed to have.

All three fixes were live-verified end-to-end by me (not just crush/code review): a single click now
produces exactly one new tab, immediately visible and focused, with a working ASCII spinner and no

**Thread 2: investigated and fixed a real crash the user noticed in one of their own long-running
production `onlyterm-gui.exe` sessions** (PID 13012, running the installed release build from
`C:\Program Files\OnlyTerm\`, config `wezterm.ktav`, uptime since Aug 11 23:37). Per-PID log at
`C:\Users\Computer\.local\share\onlyterm\onlyterm-gui.exe-log-13012.txt` (this project's authoritative
crash-diagnostics source per its own CLAUDE.md) showed a caught Rust panic, not an OS-level crash (no
Windows Event Log entry, no WER dump — confirmed by direct query). Root-caused fully, using a second,
more detailed crash log (`onlyterm-gui.exe-log-2732.txt`, from an earlier Aug 9 crash of the same kind,
found by grepping all per-PID logs for "wgpu"/"panic") that had a full symbolicated backtrace unlike the
`<unknown>`-only release-build trace from the immediate crash:

- wgpu's `Queue::write_buffer` / `Device::create_render_pipeline` returned an error (exact wgpu error
  variant unrecoverable — see the logging bug below) with **no `on_uncaptured_error` handler installed
  anywhere in this codebase** (confirmed via `grep`), so wgpu's own default behavior
  (`default_error_handler`, "Handling wgpu errors as fatal by default") panicked, killing the render
  thread that called into wgpu (`onlyterm_gui::renderthread::submit_one_frame` →
  `WebGpuState::submit_frame` → `get_render_pipeline`/`get_or_create_pipeline`).
- The full log showed the actual failure mode: the render-thread hang supervisor
  (`check_render_thread_hang_tick`/`attempt_renderer_rebuild_or_close` in
  `termwindow/render_pipeline.rs`) misdiagnosed the *dead* thread as merely *stuck*, rebuilt the renderer
  in place 3 times within 30 seconds (each logged "successfully rebuilt"), panicked again after each one,
  and finally tripped its own circuit breaker and closed the window. Root-caused why the rebuilds were
  pointless: `ProcessGpuContext::get_or_init` (`termwindow/webgpu/context.rs`) only builds a *fresh* GPU
  context if its `lost: Arc<AtomicBool>` flag is set, and *nothing* set that flag for an uncaptured
  error before this session's fix — only `install_device_lost_callback` did, for a genuine device-lost
  event, which real Windows Event Log data (checked exhaustively: 7-day window, zero TDR/display-reset
  events) confirmed never actually happened. So every "rebuild" reused the exact same already-broken
  device.
- Also root-caused why the misdiagnosis happened: `submit_one_frame` (`renderthread.rs`) set
  `submit_started_at = Some(start)` before calling `submit_frame`, and only cleared it back to `None`
  with a plain assignment placed *after* that call — which never runs if the call panics (confirmed via
  the log's own backtrace: the panic unwound through `catch_unwind` inside the thread-spawning glue, so
  the *process* survived but the *thread* died, leaving `submit_started_at` stuck at `Some(..)` forever).
- Separately, discovered and fixed a masking bug that had been silently discarding the actual crash
  diagnostics all along: `env-bootstrap`'s panic hook
  (`downcast_ref::<&str>().unwrap_or(&"!?")`) only handles `&'static str` panic payloads
  (`panic!("literal")`); any `format!`-built panic message (a `String` payload — including wgpu's own
  `default_error_handler`, which does `panic!("wgpu error: {err}")`) silently became the useless
  placeholder `"!?"` in every crash log, including the very first one investigated this session. This is
  why the exact wgpu `Error` variant (`OutOfMemory`/`Validation`/`Internal`) for the recent crashes could
  not be recovered even after finding the older, more detailed log.

User explicitly asked to fix all of this ("давай исправим"), not just diagnose it. Implemented three
coupled fixes, all live-verified via `cargo build`/`clippy -D warnings`/`fmt --check`/`cargo test` (all
clean; 9/9 renderthread unit tests pass including one new regression test):

1. `install_uncaptured_error_callback` (new, in `context.rs`) — installed on the same background thread
   immediately after `install_device_lost_callback`, on the same device. Reuses the *exact same*,
   already-tested recovery infrastructure device-loss uses (the `lost` flag + `device_lost_subscribers`
   + `handle_render_error_recovery`'s existing circuit breaker) instead of letting wgpu panic — this
   single change fixes both the panic itself and the "rebuild reuses the same broken device" bug, since
   marking `lost` is what makes `get_or_init` build a genuinely fresh context next time.
2. `ClearSubmitStartedAtOnExit` (new RAII guard, in `renderthread.rs`, extracted to module scope
   specifically so it's unit-testable) — clears `submit_started_at` on `Drop`, which fires during a
   panic's unwind as well as on normal return, unlike the old post-call assignment. Added regression test
   `clear_submit_started_at_on_exit_clears_on_panic`, which drives a panicking closure through
   `catch_unwind` and asserts the flag clears in both the normal and panicking paths.
3. `env-bootstrap`'s panic hook now tries `downcast_ref::<String>()` as a fallback when the `&str`
   downcast fails, so `format!`-built panic messages are no longer silently replaced with `"!?"` — the
   next real crash (of any kind, not just this one) will show its actual message in the log.
