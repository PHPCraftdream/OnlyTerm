Continuation of the multi-session OnlyTerm (fork of wezterm/wezterm) rebrand project. This segment picked up after the full onlyterm→onlyterm rename was complete and pushed, and focused on: (1) actually building, installing, and iterating on the real running application on this Windows dev machine, and (2) chasing down a serious Ctrl+C regression through several wrong hypotheses to the real root cause.

Key events in order:
1. **Installed OnlyTerm into the system directly** (no Inno Setup wizard) via Inno Setup once, then via elevated `copy /Y` for all subsequent updates — a repeatable pattern: `cargo build --release --bin onlyterm --bin onlyterm-gui --bin onlyterm-mux-server`, then a single `powershell Start-Process -Verb RunAs -Wait` elevated copy of the three `.exe` + three `.pdb` files into `C:\Program Files\OnlyTerm`, verified via mtime comparison. Discovered and fixed a real installer bug along the way: the `.iss` AppId was inherited unchanged from upstream wezterm, causing Inno Setup to mistake this machine's real, separate upstream WezTerm install (`C:\Program Files\OnlyTerm`, a genuine daily-driver install unrelated to this project) for an "existing OnlyTerm install" and start overwriting shared-name vendor DLLs there. Fixed with a fresh GUID, plus `CloseApplications=no` to stop false-positive "close this app" prompts against unrelated `OpenConsole.exe` processes.
2. **enable_kitty_keyboard whiplash**: flipped default true → broke Ctrl+C (every Ctrl+<letter> got CSI-u encoded once an app requests DISAMBIGUATE_ESCAPE_CODES) → reverted to false → user said Ctrl+C *still* didn't work → deep investigation with real automated pty-level tests (`cargo test`, no user interaction) ruling out `CREATE_NEW_PROCESS_GROUP` and `PSEUDOCONSOLE_WIN32_INPUT_MODE` as causes → dead end, since those tests exercised the wrong layer entirely.
3. **Real root cause found via `debug_key_events` log capture** (ran a fresh dev-profile `onlyterm-gui.exe` directly, unelevated, with `ONLYTERM_LOG=info --config debug_key_events=true`, asked the user to press Ctrl+C once, read the log): a pre-existing bug in `CommandDef::permute_keys` (from an earlier session's "keyboard-layout-independent keybindings" work) synthesized a **bare CTRL (no SHIFT) physical-key alias for every SUPER-bound single-letter command** — so plain Ctrl+C was unconditionally bound to `CopyTo(Clipboard)` and never reached the pty at all. Nothing to do with kitty-keyboard, ConPTY flags, or the process-tree-kill feature — all correctly ruled out first.
4. **Fixed properly**: removed the buggy bare-CTRL synthesis; added a new `KeyAssignment::CopySelectionOrInterrupt` (copy+clear selection if one exists, else pass a literal Ctrl+C through) as the new Ctrl+C default; discovered mid-fix that the surgical removal also broke CTRL+SHIFT+C/V (pre-existing, previously-passing tests) because `InputMap::lookup_key` **always strips SHIFT from the query** before searching (`key.normalize_shift(...)`), so a CTRL+SHIFT+<letter> binding is only ever reachable if *stored* as bare CTRL + the shifted/uppercase character — re-added that specific registration without its physical-key-fallback side effect (which is what caused the ambiguous collision with plain physical Ctrl+C in the first place). All pre-existing + 3 new regression tests pass (74/74 for onlyterm-gui's full suite).
5. **Also added, same session**: right-click now copies-and-clears a text selection (previously did nothing when there was no hyperlink under the cursor); `sefer-alloc` 0.2.1 (user's own crate) wired up as `#[global_allocator]` on all three binaries with the `production` feature; close-confirmation overlays removed entirely from the code (not just defaulted off); tab/window titles default to the cwd basename and update on `cd`; new windows start maximized by default; and — final item — a black window-frame/tab-bar chrome strip on the light theme was traced to a *separate* `WindowFrameConfig` (titlebar/button colors, used by the fancy tab bar which defaults on) that the earlier `default_colors()` light-theme work never touched; its per-field defaults were retargeted to match the light palette.
