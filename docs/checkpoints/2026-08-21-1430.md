# Checkpoint — 2026-08-21 14:30 [host-process-gpu-isolation-shipped]

## Session summary

Continuation of the long GPU-crash-isolation thread (see the earlier checkpoint `2026-08-21-1100.md` for everything before this). Picked up right after `/resume`, then the whole rest of this session built and shipped full per-window GPU-process isolation, replacing the earlier "per-tab, config-selectable" plan with something much simpler that the user explicitly chose along the way.

**Architecture arc:** started from the pre-refactor `RenderBackend` trait (already done, previous session) and the investigation doc's open question of per-tab vs per-window isolation. A Phase A spike (`.scratch/dcomp-spike/`, git-ignored, not committed) empirically proved DirectComposition composition-surface handles keep displaying their last presented frame even after the producer process dies — this became the load-bearing fact for the whole design. Delegated the granularity/architecture decision to a `@ox` agent (explicit user request, mid-session); its recommendation — one GPU-host child process **per window** (not per-tab, not one shared process for the app), silent respawn-in-place on death, **no epitaph screen**, reusing the existing `rebuild_backoff_for_attempt` schedule and 3-per-30s budget, demoting to the in-process `RenderThreadHandle` as a last resort — was adopted in full. The user then explicitly decided (after some back-and-forth) to make this the **unconditional default for every window, with no config toggle at all** — `webgpu_engine`/Phase C/Phase D tasks (#646, #647) and the GPU-device-pool idea (#643) were deleted as no-longer-applicable once that was decided.

**What got built, in order:** wire protocol v1 then v2 (`termwindow/webgpu/wire.rs`: `Frame`/`Resize`/`Shutdown`/`AttachSurface` parent→child, `Presented`/`Fatal` child→parent, all `bytemuck`-Pod framed, no serde); an atlas-write mirroring mechanism on `WebGpuTexture` (interior-mutable, `AtomicBool`-gated, zero cost when off); a `--gpu-tab-host` hidden subcommand (`gpu_tab_host.rs`) that owns a private `ProcessGpuContext`, attaches to a composition-surface handle via `WindowGpuSurface::new_from_composition_surface_handle` (uses `wgpu::SurfaceTargetUnsafe::SurfaceHandle`, which — contrary to an earlier-session assumption that vendoring `wgpu` itself would be required — already exists and is compiled by default on Windows in plain `wgpu = "25.0.2"`); a CPU-side `build_wire_frame` alongside the existing `build_webgpu_frame`, dispatched via a new `RenderBackend::frame_form()` method; and `host_process_backend.rs` (`HostProcessBackend: RenderBackend`) — the parent-side piece owning the DirectComposition device/target/visual, spawning/respawning the child (Job Object + `--supervise-pid` watcher, reusing the existing `per_tab_process_isolation` supervision primitives, the latter's `windows_job.rs` and a newly-extracted `parent_watcher.rs` made `pub` for cross-crate reuse), and implementing the full respawn/backoff/demotion state machine.

**Two real regressions found and fixed after going live**, both via a delegated `@ox` investigation using actual screenshots (not just log inspection) of a real running window:
1. The GDI startup placeholder was never cleared for `HostProcessBackend` windows (that only happened inside the in-process render thread's `submit_one_frame`) — fixed by wiring `Window::clear_placeholder_background` into `on_presented`'s first-ack handling.
2. `HostProcessBackend::spawn` initially attached its DirectComposition target to the *top-level* window HWND instead of the dedicated `webgpu_child_hwnd` (a `WS_CHILD` window the in-process path already targets, stacked in front of the top-level one) — content rendered one z-order layer behind an empty, opaque child window. Fixed to target `window.webgpu_child_hwnd()`.
3. The deeper, actual root cause of "still blank after both of the above": `TermWindow::wants_gpu_atlas_mirroring()` was left hardcoded `false` (a placeholder for the now-deleted Phase C) and never got wired to the real backend, so the child's glyph-atlas mirror stayed permanently empty — solid-color quads (tab bar, terminal background) rendered fine, but every glyph/cursor/underline (which samples the atlas) came out alpha-0, i.e. invisible on a light background. `@ox` fixed this end-to-end: a new `RenderBackend::wants_atlas_mirroring()` trait method, atlas-mirroring-enable moved to run *before* `UtilSprites::new` (both call sites in `renderstate.rs` — the ordering itself was a second latent bug), a proper `AtlasMirrorLog` (full CPU-side mirror + pending deltas, replacing a plain accumulate-forever `Vec`) so a respawned/freshly-attached child can get a full resync instead of only incremental deltas, and a real hang fix (`in_flight` was never reset when a child died mid-frame, freezing the window on every respawn after the first).

**Verified, not just claimed:** two real regression tests (`host_process_backend::tests`) that spawn a genuine `--gpu-tab-host` child against a bare Win32 test HWND, forcibly kill it by its own captured PID, and assert respawn-without-crash / budget-exhaustion-demotes-without-crash. Both pass. Also verified live twice this session: launched the real `onlyterm-gui.exe` (test builds, not the user's installed one), watched a real child process attach and present frames, killed the real child by captured PID, watched a real respawn in the log. After `@ox`'s atlas-mirroring fix, a screenshot (`onlyterm-fixed.png`) confirms real terminal content (tab titles, prompt text, cursor) render correctly — the visible bug the user reported twice ("не наладилось") is resolved. Independently re-ran `cargo build`/`clippy -D warnings`/`fmt --check`/`test` myself after `@ox`'s fix rather than trusting its report alone; 170/170 tests pass, zero warnings.

## Decisions

- Adopted `@ox`'s full architecture recommendation: per-window (not per-tab, not one-shared-process) GPU-host child process; silent respawn-in-place, no epitaph UI; reuse `rebuild_backoff_for_attempt`'s exact schedule and a 3-per-30s budget; demote to in-process `RenderThreadHandle` as the last resort, as a side effect of the *existing* renderer-rebuild path (no new demotion machinery needed).
- User then explicitly overrode the earlier "config-selectable, default off" plan: `HostProcessBackend` is now the **unconditional default for every window**, no `webgpu_engine` config key, no opt-out — because the respawn mechanism is proven resilient enough that a toggle was judged pointless. This is a materially bigger blast-radius decision than the original ask, made with the tradeoffs stated plainly and the user choosing to proceed anyway.
- Confirmed via reading the real `wgpu-25.0.2` source (not memory) that `wgpu::SurfaceTargetUnsafe::SurfaceHandle` already exists and is compiled by default on Windows — the earlier-session conclusion that vendoring `wgpu` itself would be required to reach `IDXGIFactoryMedia::CreateSwapChainForCompositionSurfaceHandle` was wrong; no vendoring needed.
- Parent process still builds a `WebGpuState` even for `HostProcessBackend` windows, but a new **device-only** variant (`WebGpuState::new_device_only`, `surface: Option<WindowGpuSurface>` now `None`) — needed because `RenderState`/`GlyphCache`'s atlas texture creation is backend-agnostic CPU-side work, but the parent must never create a real swapchain/call `Surface::configure` itself (exactly the calls behind every crash diagnosed earlier this session).
- Delegated twice to `@ox` this session (both explicit, both for genuinely open technical/architectural questions this agent hadn't resolved solo): once for the granularity/architecture decision, once to diagnose the invisible-content bug empirically (screenshots, a purpose-built repro spike, a real running-window probe) rather than guessing from logs alone.
