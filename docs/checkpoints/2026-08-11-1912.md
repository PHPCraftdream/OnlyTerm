### The flicker bug (#520) -- root cause, since it's the substantive find of this round

The WebGpu swapchain lives on a `WS_CHILD` window covering the parent's entire client area, and
that child is what the user actually sees. Two compounding causes:

- Its class was registered `CS_HREDRAW | CS_VREDRAW`, forcing a full invalidate-**with-erase** on
  every width/height change. But this window paints nothing in `WM_PAINT` (pixels come from the
  swapchain), and once the startup placeholder is retired its `WM_ERASEBKGND` paints nothing
  either, with a null background brush so `DefWindowProc` doesn't fill it. Every resize therefore
  blanked it to undefined pixels until the next present -- composited as a see-through flash.
  Note the asymmetry that made this specifically the child's bug: the *parent's* `wm_erasebkgnd`
  returns `Some(1)` unconditionally and never reaches `DefWindowProc`.
- It was created `WS_VISIBLE` up front, so it covered the parent's placeholder while having no
  pixels of its own.

Why it looked new and instance-dependent: on a cold start GPU init takes seconds, so the
placeholder outlived the whole startup resize burst and every erase repainted the spinner. With
another window already open, the new window is created **in the existing process**
(`always_new_process` defaults to false), where the process-wide GPU context is already warm --
so the renderer is ready almost immediately and the placeholder was torn down while resizes were
still landing. The ~5 flashes are the number of geometry changes in the startup burst. Earlier
work this session (making GPU context init async and reusing a cached context) is what made the
warm path fast enough to expose it.

Fix: drop the redraw styles, and create the child hidden, showing it from
`clear_placeholder_background` (i.e. once a frame has actually been presented to its swapchain) so
the GPU layer is never composited before it has content. `recreate_webgpu_child_window` shows the
new child immediately instead, preserving today's behavior on the renderer-rebuild path where the
placeholder is long gone and leaving it hidden would blank the window for the whole rebuild.

**Not yet confirmed by the user on real hardware** -- the fix is built/linted/tested clean but the
symptom is visual and needs a manual check (open OnlyTerm, launch a second one overlapping it).
