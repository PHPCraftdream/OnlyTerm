**Two serious regressions were found and fixed after the instanced-rendering task, both purely from live human visual testing, neither caught by build/clippy/fmt/test**: (1) task #447 — `QuadInstance`'s vertex-attribute locations collided with `CornerVertex`'s (both started at location 0), which made `create_render_pipeline` panic on the render thread; the panic was never visible to the user (GUI binary has no console, WER doesn't log a graceful self-close as a crash) — the window's own renderer-rebuild circuit-breaker just closed the window after 4 failed rebuild attempts in 30s, which is what the user actually saw ("процесс исчез"). Root-caused via OnlyTerm's own per-PID log file under `~/.local/share/onlyterm/`, not stderr, not Windows Event Log, not a crash dump. Fixed + added 5 regression tests that pin the Rust struct layout, the WGSL struct declarations (parsed via `include_str!`), and the corner-to-rect math against each other, so a location/field-order mismatch fails a test instead of only showing up on a real screen. (2) task #448 — even after #447, the window opened but rendered a flat black screen (correct mouse hit-testing, zero visible content): `MappedQuadsView` collected painted quads into its own owned Vec, but nothing ever merged that Vec back into the GPU-bound accumulator — `write_instances_to_gpu` existed but had no caller. Fixed by having `with_quad_allocator` merge each view's collected instances back after the paint closure returns, plus the same fix at a second direct call site in `background.rs`.

**Investigated a user-reported "hang" under Claude Code (task #449) and ruled out a bug**: confirmed via direct debug-vs-release A/B (same source, two builds, run side by side) that the freeze was purely debug-build (opt-level 0) slowness under heavy TUI redraw, not a regression — the release build had zero lag. Tried and then explicitly reverted (per direct user instruction) a `[profile.dev.package.wgpu]` opt-level=3 stopgap in the root `Cargo.toml` — the user wants the *actual algorithmic waste* fixed, not the compiler asked to paper over it faster.

**This led to a major architecture-review detour that reshaped the remaining task queue.** User asked "why do we redraw a frame that's identical, and why do we redraw the whole screen when only one line changed" and separately asked that a strong reviewer (`@oh`) design the fix before any more implementation. A full `@oh` design-review pass (report is in this conversation's tool-call history, not repeated here) found that **a per-line quad cache already exists** (`line_quad_cache`/`LineQuadCacheKey`) — the real problems are elsewhere:
1. `TripleVertexBuffer::map_instances` allocates full layer capacity fresh on every call, and `with_quad_allocator` is called once per UI element (reentrant recursion via `render_element`) — likely tens of MB/frame of Windows `VirtualAlloc`/`VirtualFree` churn, probably the actual cause of the debug "slideshow".
2. Every quad is copied twice per frame through a `BoxedQuad`→`QuadInstance` conversion with dynamic dispatch, even on cache hits — pure ceremony since the two types are already layout-identical and already transmuted between elsewhere.
3. `LineQuadCacheKey` bakes in **absolute screen Y position**, so scrolling (the actual Claude-Code workload) invalidates every visible line's cache entry every frame — no amount of dirty-row tracking fixes this, only a position-relative cache key does.
4. A separate latent bug found along the way: if a frame has zero non-empty draw layers, `submit_frame` never creates a render pass at all, so `present()` shows whatever garbage was already in that swapchain rotation slot — currently rare, but both of the new frame-skip/dirty-region tasks make empty-ish frames common, so it must be fixed first.
5. `@oh` marked real dirty-region rendering (rectangles/GPU-side scissor) as **explicitly wrong** for this architecture (swapchain back buffers rotate; `LoadOp::Load` would load 2-3-frames-stale content) and instead recommends a CPU-side retained-mirror-plus-splice design, reusing the *existing* `LineQuadCacheKey` (not raw line seqno alone — selection/cursor/hover/etc. change rendering without changing line content) as the dirty predicate, gated behind a debug-build self-check that rebuilds from scratch and compares against the incremental result every frame. `@oh` flagged this specific piece (#451) as **high risk of silent stale-pixel bugs** and listed 9 concrete failure modes (multi-pass paint_impl re-runs, resize/DPI invalidation, atlas identity, scroll-shift off-by-one, selection/cursor not seqno-visible, chrome/content draw-order dependence, overlay panes' own dirty semantics) that the eventual implementation must address, not just the happy path.

User accepted `@oh`'s full recommended sequencing and the TaskList was reordered accordingly (see below) — this is now the active plan, ahead of the original #439-441 and well ahead of the wrap-up tasks #443-446.
