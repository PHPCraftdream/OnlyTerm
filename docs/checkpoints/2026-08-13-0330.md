`promise::spawn::spawn`, which only schedules onto the GUI thread's own cooperative executor and

**Phase A (#553, committed `7e8c763cf`, merged `e2e05580c`):** built and shipped a
`--single-pane` mode for `onlyterm-mux-server` — one process instance hosts exactly one PTY/pane
and exits when that pane's shell exits (a new lifecycle model distinct from the existing
`--daemonize` long-lived-multi-pane-daemon mode). Delegated to `/crush` in an isolated worktree

this project's CLAUDE.md process-safety rule) — and found and fixed **two real bugs neither
crush's build nor its clippy/fmt/test pass caught**: (1) `spawn_stdio_listener()`'s original form
did `let _ = wezterm_mux_server_impl::dispatch::process(stream);` inside a bare `thread::spawn`
— `dispatch::process` is `async fn`, so this constructs a `Future` and drops it immediately,
unpolled; the mux protocol dispatch silently never ran at all. Clippy's `let_underscore_future`
lint caught this correctly and crush suppressed it with `#[allow(...)]` instead of fixing it —
fixed by using `promise::spawn::spawn_into_main_thread(...).detach()`, the same primitive
`LocalListener::run` already uses for daemon-mode connections. (2) Winsock was never initialized
in the single-pane child process (confirmed live: "Either the application has not called
WSAStartup..." os error 10093) — daemon mode gets this for free because
`filedescriptor::socketpair()` (parent/GUI side) calls it, but the child never calls
`socketpair()` itself, so it needs its own explicit `WSAStartup`; added as `init_winsock()`.
After both fixes, a real manual test (throwaway `.ktav` config with `proxy_command` pointed at
the single-pane binary, `onlyterm-gui.exe connect <domain>` against it) produced a **screenshot
of a genuinely working `cmd.exe` pane rendered as an ordinary tab** — the actual acceptance
criterion, actually observed, not just inferred from logs. Also found and fixed, while running
the first full-`--workspace` clippy pass this diff required (my usual narrower `-p wezterm-gui`

## Decisions

- Full per-tab process isolation applies to ALL tabs, not just admin ones (user-confirmed
  explicitly, overriding my initial performance-motivated recommendation to scope it to
  admin-only) — motivation is crash blast-radius, not performance; IPC overhead is an accepted
  deliberate tradeoff.
- Reuse the existing `wezterm-mux-server`/`ClientDomain`/`proxy_command`+`socketpair()` machinery
  rather than building new IPC from scratch — the hard "render a remote process's pane as a tab"
  problem is already solved and battle-tested in this fork.
- Transport for the single-pane hosting process: `proxy_command`/`socketpair()` (inherit-only
  handles, no filesystem ACL surface), not an ACL'd Unix-domain socket (would need new Windows
  DACL code, since `create_user_owned_dirs`/`set_sticky_bit` are no-ops on Windows today).
- `per_tab_process_isolation` config flag defaults to `false` (overriding crush's choice of
  `true`) until live interactive verification and Phase D's lifecycle work close the known gaps
  — merging Phase B does not change any user-observable behavior until someone opts in.
- The known domain-registration leak (`mux.add_domain` with no matching removal on tab close) is
  deliberately left unfixed in Phase B, explicitly flagged as Phase D scope rather than
  silently shipped or hastily patched under time pressure.
- Zero-trust verification of every crush-delegated task continues to catch real bugs crush's own
  build/clippy/fmt/test pass didn't — two more real bugs found this window (dropped future,
  missing WSAStartup), on top of the many found in earlier tasks this whole session. Treat any
  future crush "done" report the same way: independently re-verify, including live interactive
  testing where the feature is GUI-facing.
