**#407 was unblocked** once I personally investigated it fresh (via `@sh`) after correcting the record on the earlier `6984af94a` alpha_mode "fix" (confirmed a no-op on Windows by a prior `@oh` review, see `2026-08-06-0945.md`). The agent found the *real* mechanism, with a clean structural proof: `TermWindow::paint_impl` cleared the Windows GDI startup placeholder as soon as `call_draw()` returned `Ok`. With `webgpu_render_thread` enabled (the Windows default), `call_draw()` only *enqueues* the frame to a channel via `RenderThreadHandle::send_frame` and returns immediately -- the actual `WebGpuState::submit_frame()` (the real `Queue::submit`/`Present`) runs later, asynchronously, on the dedicated per-window render thread. So the placeholder could be torn down before the swapchain had ever actually presented a frame -- invisible against the desktop, but showing a second overlapping OnlyTerm window's real content through it when one was in the background. This explains both reported symptoms (startup flicker and "white/transparent rectangles") with one mechanism. Fixed by deferring the placeholder-clear to `renderthread.rs`'s `submit_one_frame`, right after its first successful `submit_frame`, via a one-shot flag local to the (single-threaded) render thread loop; the synchronous non-render-thread path is unaffected (there, `Ok` really does mean presented). Commits `9fd0ed57f` + a doc-comment follow-up `e992f4e44` I wrote myself after spotting a stale reference to the old (now only partially accurate) call-site description. **Caveat, preserved honestly**: the investigating agent could not get a visual screenshot confirmation (its shell environment is isolated from the interactive desktop), so the fix rests on a structural/timing proof rather than a before/after screenshot -- a real end-user retest on a fresh build would still be the strongest confirmation, though not currently blocking (the mechanism is sound and independently re-verified by me via direct code reading).

**#399** (fade cut short by *any* `WM_WINDOWPOSCHANGED`, not just an actual resize): real bug, found and fixed. `check_and_call_resize_if_needed()` called `finish_placeholder_fade()` unconditionally before computing `same` (whether the client area's actual pixel size/DPI changed), so a pure window *move* (the fade overlay is a `WS_CHILD` window with client-relative coordinates, so it tracks the parent automatically and needs no repositioning on a move) still cut the fade short. Fixed by moving the `finish_placeholder_fade()` call after `same` is computed and gating on `!same`. Commit `62e1d0808`.
