## Session summary

Two independent threads, both closed.

**Typing latency (#594, #597).** Landed the tab-bar rebuild fix from the previous window and
then corrected its scope. A full-screen TUI re-sets its title, cwd and progress on every
repaint, and each of those mux alerts forced a synchronous rebuild that resolved the active
pane's title/progress/cwd through the bounded terminal lock TWICE. Measured on real contended
`LocalPane`s: 93.5ms -> 46.2ms per rebuild, 2.02x, all 60 accessor calls confirmed to have
taken the timeout path. The agent's coalescing was then narrowed by me: it had been applied to
all 27 call sites including hover, resize and overlay-open, where a 100ms deferral is itself a
visible regression; it now covers only the mux-notification storm. The progress spinner keeps
the immediate path deliberately -- its own frame interval is also 100ms, so gating it would
drop every other frame rather than save work. Also fixed `cursor_row_slot`, which was measured
from `dims.physical_top` while the rows it indexes come from `current_viewport`; scrolled back,
RowSweep's one unconditional budget exemption was protecting the wrong row.

**Keyboard chords in Codex CLI (#598) -- the day's main work.** User report: under a Cyrillic
layout, Ctrl+J, Ctrl+Enter and Ctrl+C do nothing in Codex, while Claude Code is fine in the
same window. Six suspects were eliminated by measurement before the cause was found: our key
lookup, our encoding, ConPTY's byte channel, conhost's record channel, interrupt delivery, and
the user's own key bindings. Windows Terminal reproduced the failure, which ruled out
OnlyTerm as the origin. The cause is in `codex.exe`: it reads with `ReadConsoleInputW` and,
when the record's `UnicodeChar` is below 0x20, ignores it and re-derives the character from
`wVirtualKeyCode` via `ToUnicodeEx` under the *active* layout -- so VK_J becomes 'о' and VK_C
becomes 'с'.

The first writeup concluded "the terminal cannot fix this". That conclusion was **wrong and is
retracted in the document**: the re-derivation only fires for a control `UnicodeChar`, so
putting the plain letter (0x6A) in that field routes around it entirely. Verified live. It
cannot be global -- Claude Code reads the byte stream and immediately began typing a literal
'j' -- so it is scoped by process. Two failures along the way, both recorded in the code: the
scope first matched the pane's *foreground* process, which resolves to `node_repl.exe` because
Codex runs `codex.cmd` -> node -> `codex.exe`; and it was evaluated on every keypress rather
than only on chords, which put a process-tree walk on the ordinary typing path.

Claude Code's SHIFT+Enter turned out to be a separate, non-layout defect found in passing: a
faithful modified-Enter record is invisible to a byte-stream reader (conhost collapses it to a
bare `\r`), so the chord submitted instead of inserting a newline. Fixed with ESC CR, scoped
the same way. Both applications now work at both layouts, confirmed by the user.

**My own errors this session, all corrected in place:** I measured the byte channel first and
drew a confident conclusion from it, when an application using `ReadConsoleInputW` never sees
those bytes; I claimed the process check cost was paid "only for CTRL chords" when it ran on
every key; and I nearly reported that we fail to send modifier key records, when the truth was
a hole in my own logging predicate.

## Decisions

- Application-compatibility substitutions are scoped by process tree, never global, and both
  new config keys say in their doc comments which applications they must NOT reach. The cost
  of getting this wrong was observed directly: a global Ctrl+letter substitution fixed Codex
  and broke Claude Code in the same minute.
- Match the whole process tree, not the foreground process. The Windows foreground heuristic
  picks the youngest process sharing the console, which for a wrapped program is the wrapper.
- Title-rebuild coalescing covers only the mux-notification storm. Rebuilds driven by direct
  user action stay immediate, because deferring them by 100ms is a regression in itself.
- The keyboard diagnostics are kept, not removed after use. This was the fourth defect in this
  area; the layout-change log in particular was added only after its absence made a full
  capture session uninterpretable.
- The upstream defect is in `openai-oss-forks/crossterm`, `parse.rs`, not in Codex's own code.
  Our patch is a workaround; Gemini CLI works at every layout precisely because it trusts the
  character the terminal already sent.
