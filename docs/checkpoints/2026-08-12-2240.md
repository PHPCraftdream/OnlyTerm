(building/launching/closing many times, each time carefully verifying the closed PID was
one this session itself launched, per the project's onlyterm-gui.exe HARD CONSTRAINT) --
worth recording precisely what was found and fixed, since it's not visible from the diff
alone:

1. **Layout bug**: `box_model::Element`'s default `display` is `Inline`; none of the
   original crush-authored elements had `.display(DisplayType::Block)`, so every label
   and radio across all three groups rendered on one continuous horizontal line
   (confirmed via screenshot) instead of one row per group. Fixed by restructuring into
   per-group "row" wrapper elements (label + its radios as inline children) each tagged
   `.display(DisplayType::Block)`, matching the pattern `CommandPalette` uses for its own
   rows (`palette.rs`).
2. **Box too narrow / content clipped**: the original `desired_width = (cols/4).max(60)`
   heuristic under-sized the box for the widest row (Priority, with 6 options including
   "Below Normal"/"Above Normal"); "Realtime" was visibly cut off past the right border
   in a screenshot. Replaced with a computed width based on actual row content lengths.
3. **Right-click on "+" opened nothing**: root cause traced via `ONLYTERM_LOG=trace` +
   a `resolve_ui_item` diagnostic added to `mouseevent.rs` -- the user had been
   right-clicking "+" expecting it to trigger the dialog (this session had removed the
   old launcher menu from that gesture earlier), but the dialog was only bound to
   Ctrl+Shift+N. Fixed by wiring `do_new_tab_button_click`'s `MousePress::Right` arm to
   `KeyAssignment::ActivateNewTabOptions` (both triggers now work).
4. **`Ctrl+Shift+N` "opened a whole new OS window"**: traced via a `lookup_key`
   diagnostic added to `inputmap.rs` -- the captured key event's modifiers were
   `CTRL | LEFT_CTRL | LEFT_SHIFT`, missing the general `SHIFT` bit (only the positional
   `LEFT_SHIFT` survived), so the binding lookup (which normalizes away positional bits
   before matching) never saw `SHIFT` and the configured `CTRL.union(SHIFT)` binding
   never matched. This looks like a real, likely pre-existing modifier-tracking quirk
   unrelated to this session's own changes (not yet root-caused further; SpawnWindow's
   own default is SUPER+n, no collision found). Not fixed at the source -- worked around
   by adding the right-click trigger (point 3), which the user now uses instead. **Flag
   this as a possible latent bug worth its own investigation later** if Ctrl+Shift+<key>
   bindings matter elsewhere.
5. **Mouse click appeared to do nothing**: turned out, on the first two trace-log
   rounds, the user had only *hovered* (Move events) over radios without actually
   left-clicking (confirmed by grepping the trace log for `kind: Press` and finding none
   after the dialog opened). Once a real click happened, the trace showed
   `handle_selection` *was* being called and the state *was* updating -- but the visual
   selection didn't update, because the mouse handlers called `context.invalidate()`
   (a raw repaint request) instead of `self.invalidate_modal()` (which calls
   `Modal::reconfigure` to clear the modal's cached `computed_element` *before*
   repainting -- the keyboard path already did this correctly). Fixed by restructuring
   both mouse handlers to scope the `self.modal.borrow()` `Ref` tightly and call
   `self.invalidate_modal()` after dropping it (can't hold a `Ref` and call a `&mut self`
   method in the same scope).
6. **Polish requests from the user, all implemented**: hand cursor over interactive
   controls (`MouseCursor::Hand` instead of `Arrow` in the two mouse handlers); the
   *selected* radio's visual treatment (inverted bg/text) now applies consistently
   regardless of keyboard focus, instead of the original code conflating "focused" and
   "selected" into one color scheme; the *focused* item gets a separate thin 1px border
   instead. That border's box space is now reserved unconditionally (with an
   invisible/background-matching color when unfocused) -- an initial version only added
   the border when focused, which changed that item's (and its row's) size by 1px on
   every focus change, visibly "jumping" the whole dialog; the user caught this
   immediately and it's now fixed.

## Decisions

- Elevation = spawn a separate elevated `onlyterm-gui.exe` window (not an in-window
  ConPTY tab) -- user-confirmed after being shown that the alternative (in-window
  elevated tab) is not implementable on Windows at all, and that the mirrored-behavior
  precedent is Windows Terminal's own `elevate: true` setting.
- Right-click on "+" now opens the New Tab Options dialog (reusing the gesture this
  session freed up earlier by removing the old launcher-menu binding there), in addition
  to the Ctrl+Shift+N keybinding -- not a replacement for it.
- Selection state (radio's inverted colors) and keyboard-focus state (thin border) are
  deliberately two independent, simultaneously-visible visual signals, not one combined
  "highlight" style -- chosen after the user found the original single-scheme design
  confusing (couldn't tell "selected" from "just currently focused, unselected").
- Kept all diagnostic `log::trace!` additions from this debugging session permanently
  (mouseevent.rs, inputmap.rs) rather than reverting them after the bugs were found,
  consistent with this session's established `startup:`-log-style precedent.
- Continued using isolated per-worktree `CARGO_TARGET_DIR`s for all verification builds
  in this round, after repeatedly hitting the shared-target-dir cross-worktree cache
  race in earlier rounds this session.
