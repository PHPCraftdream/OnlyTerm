**Live bugfix cycle (the bulk of this window, still not fully closed):** once the user started
actually clicking through the UAC flow, a cascade of real bugs surfaced, each found from actual
log evidence rather than guessing:
1. Elevated attach failed immediately -- `GetCodecVersion`/`SetClientId` (unconditional attach-
   handshake PDUs) were wrongly rejected by the PDU allow-list. Fixed.
2. Typing did nothing in an elevated tab (paste worked) -- `SendKeyDown`/`SendMouseEvent` (the
   actual input path `ClientPane` uses) were wrongly rejected on the mistaken assumption they
   only flow server->client. Fixed, with regression tests.
3. `onlyterm-mux-server.exe` never exited when its client disconnected/failed to attach,
   orphaning a live (and for elevated tabs, unkillable-by-the-user) shell. Root cause, found by
   a delegated `@oh` investigation, was worse than expected: single-pane mode had *no* working
   exit path at all (an `Activity` guard held for the whole process life silently disabled the
   pane-death notification too). Fixed with a proper race between "pane exited" and "client
   gone", explicit pane-kill on the client-gone branch, and 5 new unit tests.
4. Ctrl+Enter/Shift+Enter/Ctrl+J didn't insert newlines in Codex CLI. Root cause (found by a
   second delegated `@oh` investigation): `ClientPane` (used for every tab since Phase B) never
   overrode `get_keyboard_encoding()`, always reporting "no protocol negotiated" regardless of
   what Codex actually negotiated with the real terminal. Fixed by syncing the real encoding
   through `GetPaneRenderChangesResponse` (a wire-protocol change, `CODEC_VERSION` 46->47).
5. Pasted text into an elevated tab rendered on a grey, unreadable background. Found live from
   the elevated child's own rejection log: `SetPalette`/`SetFocusedPane`/`WindowTitleChanged`
   were also wrongly rejected by the allow-list. Fixed.
6. Even after #4's fix, the *encoded* Ctrl+Enter sequence carried `UnicodeChar=0` -- confirmed
   via a new info-level diagnostic log line added specifically to stop guessing blind on this
   bug. Root cause: `ctrl_mapping('\r')` returns `None` (it only maps letter keys), and the
   fallback was `unwrap_or(0)`. A real Windows console reports `0x0d` for Ctrl+Enter (same
   control byte as bare Enter). Fixed to fall back to the literal character instead of 0.
7. After opening an elevated tab, the tab bar's "+" button stopped working. Found live from the
   GUI's own error log: it was trying to `SpawnV2` into the single-pane elevated domain (which
   the allow-list correctly rejects -- that rejection is doing its job) because
   `SpawnTabDomain::CurrentPaneDomain` blindly follows the active pane's domain. Fixed
   generally (affects non-elevated single-pane domains too, not just elevated) using the
   *existing* `Domain::spawnable()` trait method, now also consulted by
   `Mux::resolve_spawn_tab_domain`.

  switched to doing live-bugfix-cycle work directly myself (no delegation) once real user
  testing started surfacing bugs one at a time -- each fix needed live log evidence and tight

- For the two deep architectural bugs this window (single-pane lifecycle, keyboard-encoding
  sync), delegated research+implementation to a fresh `@oh` agent each time rather than
  attempting them solo, per the user's own explicit direction ("нужный полный продуманный
  архитектурный фикс" / "можешь запустить @oh"). Both were substantial (wire-protocol changes,
  cross-crate) and came back well-reasoned; I still independently re-verified every line before
  committing.
- Reused the *existing* `Domain::spawnable()` trait method for the "+" button fix rather than
  adding a new one, after accidentally adding a duplicate and hitting a compile error -- a
  useful reminder to grep for existing capability flags before inventing new ones.
- Chose to fix `ctrl_mapping`'s caller (fall back to the literal char) rather than either
  special-casing Enter in the encoder or extending `ctrl_mapping` itself to accept `'\r'` as
  input, since the fallback-to-literal-char behavior is more generally correct for any future
  Ctrl+<non-letter> case, not just Enter.
