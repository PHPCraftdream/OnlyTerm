Continuation of the long-running OnlyTerm (Windows-only wezterm fork) session. This window

The per-tab work finished as follows. **Phase E** (security review of the hosting-process
transport) found nothing to harden and that result was written down rather than left
implicit -- the decisive measurement was that the elevated child's rendezvous token, which
travels on its command line, is NOT readable from a medium-integrity process:
`PROCESS_QUERY_INFORMATION|PROCESS_VM_READ` is denied across the integrity boundary (err=5),
with the unelevated GUI as the control showing its own command line in full. **Phase F**
measured the cost (~46 MB and ~750 ms per hosted tab, debug profile) and produced a QA
matrix; it also turned up that `--start-conf` tabs bypassed `per_tab_process_isolation`
entirely, which was then fixed by routing them through the same path and teaching the
isolated path to carry a tab's `vars` as a real environment (`UnixDomain::proxy_env`) rather
than as command-line arguments, which would have published secrets to every process of the
same user. That fix crashed the GUI on the first attempt with a main-thread stack overflow --
an `async fn` keeps its state inside whichever future awaits it, and `Box::pin` was NOT
enough because a debug build still materialises the future on the stack before boxing it;
spawning it as its own task was the fix.

**Phase D was live-verified** for the first time (both mechanisms: six ordinary children
reaped by the Job Object, an elevated child by its watchdog, each within three seconds of
`TerminateProcess` on the GUI). One earlier "finding" -- that every `OpenConsole.exe` ran at
Idle priority -- turned out to be an artifact of the agent's own shell running at Idle and
was retracted; the consequence worth carrying is that **every performance number in these
docs was measured under Idle priority and is therefore a lower bound**.

The second half: the New Tab Options dialog got a centred title, a close cross in the
top-right, a rule under the header and a centred footer hint. The cross took five attempts
because the layout was predicted rather than measured each time -- a `Float::Right` child is
placed at `min_width + its own width` (so the float adds to, rather than fits inside, the
requested width), `max_width` on a text element is a clipping bound that deletes the glyph,
and the panel subtracts its own border/padding from the inside of its layout rect. All of
that is now written at the call site.

Then two real bugs from the user. Ctrl+I (ShowVersionOverlay) renamed the window to
"wezterm": an overlay pane never sets a title, so the terminal's default title -- the literal
`"wezterm"` -- reached the window title. And the version/commit/build-date stamped into the
binaries had been **frozen since 2026-08-12**: measured, a release build of a checkout at
`v0.0.8-alpha-88-g02613e522` still reported `alpha-33-g4148b3740`, fifty-five commits stale.
The cause is Windows-specific -- `wezterm-version/build.rs` emitted its `rerun-if-changed`
path after `canonicalize()`, which yields `\\?\D:\...`, which cargo never matches against the
plain path it tracks, so the script silently stopped running. Both fixed and committed as
`ca6b64d9c`, verified on the built binary (`onlyterm v0.0.8-alpha-88-g02613e522-dirty`).

**CORRECTION, written after reviewing the agent's finished work.** The diagnosis recorded
here originally said `update_title()` runs on every keystroke via `keyevent.rs:296,653`.
That is wrong. Those two sites fire only when a leader key activates or expires, and with
no leader configured they never fire from typing at all. Checked the rest of the keyboard
path too: `AdviseModifiersLedStatus` has no emitter in the Windows backend, and
`AdviseDeadKeyStatus` is dispatched only while a dead key is actually pending. On Windows,
ordinary typing does not call `update_title` even once.

The real driver is `render_pipeline.rs`: `MuxNotification::Alert` for `WindowTitleChanged |
TabTitleChanged | IconTitleChanged | CurrentWorkingDirectoryChanged | Progress |
OutputSinceFocusLost` calls `update_title()`. A full-screen TUI re-sets its title, cwd and
progress on every repaint, so each repaint forced a full rebuild. The part of the original
diagnosis that survives is the cost of that rebuild: `update_title_impl` called both
`get_tab_information()` and `get_pane_information()`, each running `pos_pane_to_pane_info()`
over the same active pane -- six 8ms bounded terminal-lock acquisitions where three suffice.
Measured under contention: 93.5ms per rebuild, 46.2ms after the fix (2.02x).

Either way the symptoms match what the user reported: only the pane running a busy TUI is
slow, neighbouring tabs are fast, and closing other tabs does not help. Note the duplicated
work is upstream behaviour, not something this fork introduced; the fork's contribution was
the 8ms bound itself (da3d7329e), which was a mitigation.

## Decisions

- Rebranding scope: **user-visible strings only**. The 22 package names and 19 crate
  directories keep the upstream names deliberately -- renaming them (2459 occurrences across
  327 files) would make merging upstream fixes permanently painful for no user-visible gain.
- Tab-drag cursor: reverted a hand-drawn closed-hand cursor back to the system `IDC_HAND`,
  at the user's call. A custom cursor ignores the user's cursor scheme, the "large cursors"
  accessibility setting and high-contrast inversion.
- `--start-conf` tabs with `vars` now travel as a real environment via `UnixDomain::proxy_env`
  rather than as CLI arguments; a command line is readable by every process of the same user
  and these values may be secrets.
- The tail-loss fix in the elevated transport bounds its drain with a 2s deadline and logs
  what it drops, rather than draining unbounded -- this crate has already shipped a pump that
  waited forever on a peer that never returned.
- The New Tab Options close cross reserves an over-stated width rather than a guessed exact
  one: the float is placed from its actual width, so over-stating only tucks it further
  inside, while under-stating hangs it off the edge.
