# Checkpoint — 2026-08-21 11:00 [gpu-crash-hunt-and-isolation-seam]

## Session summary

Long session chasing two real crash/hang incidents in `onlyterm-gui.exe` on the user's machine, using live crash dumps read with `cdb.exe` and matched PDB symbols (not guesswork). Diagnosed and fixed in code, three separate commits already pushed to `main`: (1) a render-thread death from an uncaught panic inside `Surface::present` was invisible to its own supervisor — fixed via `render_thread_has_died()` plus `catch_unwind` around `submit_frame`; (2) a crash reached from our own recovery path — rebuilding the renderer (which calls `CreateSwapChainForHwnd`) in response to an out-of-memory error, while the system was still out of memory, is what let the Intel driver's NULL deref actually happen — fixed by no longer rebuilding on `OutOfMemory`, and spacing any rebuild attempts that are still needed; (3) the GUI thread could freeze forever if a GPU driver was mid-reinstall while `begin_renderer_rebuild` tried to synchronously `Drop` GPU resources on it — fixed via `mem::forget`/background-thread drop. Also fixed, separately: `dev-install.ps1`'s symbol retention (a locked binary's PDB used to get pruned on its own, independent schedule and could vanish before the process that might crash on it exits — fixed with a "orphaned symbols only" rule); embedded the actual git tag/commit/date into the PE version resource (`FILEVERSION`/`PRODUCTVERSION` were hardcoded `1,0,0,0`, which is literally what Windows Error Reporting reads); and a startup log line printing the exact build provenance, to stop needing to hash a retired binary to figure out which commit it was.

Mid-session a NEW crash occurred live (PID 27376): a raw Windows SEH exception (`STATUS_NOT_IMPLEMENTED`) from inside DXGI/D3D12 during `Surface::configure`, which `catch_unwind` cannot intercept by design (foreign SEH passes through it) and which killed the entire process — every window and tab, not just one. The user pushed back hard on an earlier claim (task #640) that no per-tab isolation exists, recalling real work had gone into "each tab lives on its own." Delegated a `sx` agent to investigate against the actual code rather than take either claim on faith; it wrote `docs/per-tab-crash-isolation-investigation.md` (committed). Verified conclusion: task #640 was right — `per_tab_process_isolation` (real, shipped, Phase A–F) isolates the pty/shell child process, not GPU rendering; `ProcessGpuContext` is one `Instance`/`Device`/`Queue` for the whole `onlyterm-gui.exe` process, shared by every window. True per-tab crash containment would need GPU rendering in a genuinely separate OS process per tab (expensive, unprototyped — no `CreateSharedHandle` cross-process-surface code exists anywhere in this repo despite an earlier claim that it did) or per-window (cheaper, but siblings tabs in one window still die together). In-process SEH interception to keep the process alive was researched and ruled out as generally unsafe (Raymond Chen's writing, and Chromium's own choice of a real process boundary over exception interception, both cited in the doc).

Given that finding, the user chose NOT to commit to a granularity yet, and instead asked for a pre-refactor so the code depends on an abstraction, not a concrete solution — swappable later. Implemented as task #642: a `RenderBackend` trait in `renderthread.rs` covering exactly the GPU-submission surface implicated in all three crashes (`send_frame`/`send_resize`/`is_in_flight`/`set_repaint_pending`/`shutdown`/`render_thread_is_hung`/`render_thread_has_died`/`teardown_sentinel`), deliberately excluding CPU-side frame building (`RenderState`/`GlyphCache`/quad construction), which was never implicated in any of the three crashes and stays in-process under every future variant. `TermWindow.render_thread` is now `Option<Box<dyn RenderBackend>>`; the sole implementation today is an unchanged wrapper around the existing in-process `RenderThreadHandle` (159/159 tests, same count before/after — pure delegation, no new logic). Also implemented task #641, "Phase 0" from the investigation doc's own recommended plan: a diagnostics-only Vectored Exception Handler extension in `wgpu-hal-vendored` (the vendored/patched wgpu-hal fork, reached via `[patch.crates-io]`, deliberately NOT a workspace member) that logs exception code/address/module for a fault inside a newly-added `RiskyDriverCallGuard`-marked span (wrapped around `configure`'s and `present`'s DXGI calls in `dx12/mod.rs`) before letting the process die — never attempts recovery. Had to filter out the MSVC C++ EH exception code (`0xE06D7363`, verified via web search, not memory) so an already-`catch_unwind`-handled panic doesn't also get double-logged as a fresh "crash." Tested (5 tests) by temporarily giving the vendored crate its own `[workspace]` table to make `cargo test` reachable at all (reverted afterward, along with the `Cargo.lock` it generated — none of that is in the diff).

A new idea surfaced mid-session and was registered but explicitly NOT started: task #643, a background-warmed pool of GPU devices so a future per-tab-isolated world doesn't pay full device-creation cost per tab-open. Blocked on #640 (granularity decision) and #642 (done, but the pool needs to plug into whatever concrete backend eventually gets built behind it).

## Decisions

- Chose to fix the OOM→rebuild→crash cycle by *not rebuilding on OutOfMemory at all*, rather than just spacing retries further apart — the spacing (`rebuild_backoff_for_attempt`) is a secondary hardening on top, not the primary fix.
- Chose `mem::forget` over a background-thread drop for the old `RenderState` in `begin_renderer_rebuild`, because `RenderState` holds `Rc`/`RefCell` and is `!Send` (verified by trying to compile a background-thread drop, not assumed) — but chose a real background-thread drop for `WebGpuState` in the same function, since `Arc<WebGpuState>` compiled successfully as `Send`.
- Rejected in-process SEH interception ("catch and continue") as the answer to crash #3, based on this codebase's own existing VEH already only recovering a non-fault debug-string case, Raymond Chen's writing on SEH resumability, and Chromium's own architecture (real process boundary, not exception interception) — all independently converging on the same answer.
- Chose NOT to commit to per-tab vs. per-window GPU isolation granularity yet, despite the user's literal ask being per-tab; instead built a swappable-interface pre-refactor (#642) so the decision can be made later once a real `CreateSharedHandle` prototype produces cost numbers (per the investigation doc's own recommended Phase A/B sequencing).
- Kept `RenderBackend`'s trait boundary narrow (GPU submission only, not CPU frame-building) — deliberately, because that's exactly the boundary the three real crashes lived on, not a broader "everything render-related" abstraction.
- Reverted the temporary `[workspace]` table added to `wgpu-hal-vendored/Cargo.toml` (and its generated `Cargo.lock`) after using it to run the new VEH tests once — did not change the root workspace's `members` list, since that's a bigger structural/policy decision than this task warranted.
