Прямое продолжение чекпоинта `2026-07-28-1710.md`. В том чекпоинте была главная нерешённая проблема — "половинки строки переставлены местами" (иврит/русский) в реальном GUI; расследование было делегировано агенту `@ox`. В этой сессии агент завершил работу и нашёл РЕАЛЬНУЮ причину (три отдельных бага, не один): (1) запятая внутри ивритской фразы рвала её на два куска из-за слишком узкого `is_glue_cell` — расширено до "любой не-буквенно-цифровой символ, кроме псевдографики рамок"; (2) закрывающая ASCII-кавычка `'` ошибочно считалась герешем — сужено правило до "апостроф = гереш только если он первый в строке"; (3) фон/подчёркивание рисовались под чужим куском строки — добавлено поле `LineToElementShape::first_visual_cell_idx`, отрисовка декораций теперь использует его вместо "дореверсивного" `cluster.first_cell_idx`. Заодно закрыт старый апстримный `FIXME`: `Screen::resize`/`Line::wrap` теряли флаг `bidi_enabled`. Пользователь подтвердил на реальном скриншоте — все варианты кавычек/скобок теперь рендерятся верно.

Дальше пользователь протестировал уже собранный релиз и сообщил новый баг: Alt+V (вставка картинки в Claude Code CLI) не работает на русской раскладке. Расследование показало, что фикс из задачи #174 (физический код клавиши для CTRL/ALT в `window.rs`) реально работал на уровне определения клавиши, но отдельный протокол `win32-input-mode` (`encode_win32_input_mode` в `onlyterm-input-types`) кодировал символ через "сырой" `ToUnicode`-результат (кириллическую `м`), а не через уже определённый физический символ — это и чинили. По пути столкнулись с СЕРЬЁЗНОЙ, повторяющейся проблемой окружения: cargo несколько раз "успешно" завершал сборку, не пересобирая (или не релинкуя) реальный `.exe` — то из-за коррумпированного fingerprint (`invoked.timestamp` write error), то из-за файла, залоченного всё ещё запущенным процессом (`LNK1104`/`Access is denied` при удалении файла, тихо проглатываемая cargo с exit code 0!). Выработали железное правило: после каждой правки — `taskkill` запущенного процесса, ПОТОМ `cargo build`, ПОТОМ сверка `ls --time-style=full-iso` на бинарнике с текущим `date`, и только потом релонч. Без этой проверки тестирование бессмысленно.

После подтверждения Alt+V пользователь попросил сделать логотип круглым — сделано через Python/Pillow (окружность вписана в квадрат 1024×1024, прозрачность вне круга), пересобраны `terminal_master_1024.png`, `terminal.png` (128×128), `terminal.ico` (7 размеров).

Затем пользователь сообщил третий баг: в Codex CLI (не в Claude Code) не работает Ctrl+C и Shift+Enter/Ctrl+Enter (перевод строки), причём и на английской раскладке тоже — не связано с раскладкой. Расследование (через `docs/checkpoints/2026-07-27-2100.md` — прошлая сессия уже билась с этой же темой) нашло старый хардкод: `KeyAssignment::CopySelectionOrInterrupt` (дефолтный биндинг Ctrl+C) писал сырой байт `\x03` в обход любого согласованного с приложением протокола клавиатуры; аналогично старый `SendString("\n")` был жёстко привязан к CTRL+Enter/SHIFT+Enter, тоже в обход протокола. Гипотеза "Codex использует Kitty keyboard protocol" была ОПРОВЕРГНУТА живым логированием всех CSI/ESC/OSC-последовательностей: Codex ни разу не пытался согласовать Kitty (`enable_kitty_keyboard` включили по умолчанию — раньше дважды откатывали из-за другого, теперь исправленного бага). Вместо этого лог показал: Codex явно включает `Win32InputMode` через DECSET. Добавлен новый `KeyAssignment::SendEnterOrNewline(Modifiers)` и общий хелпер `encode_via_negotiated_protocol` (win32 → kitty → None), используемый и в `CopySelectionOrInterrupt`, и в `SendEnterOrNewline`; при отсутствии согласованного протокола — старое поведение (сырой байт) как фолбэк. Через диагностическое логирование подтвердили: сначала vkey был `0` вместо настоящего VK_RETURN/VK_C в синтетических `KeyEvent` — исправлено на реальные VK-коды. После фикса: Ctrl+C заработал в Codex; Shift+Enter заработал в Codex (и не сломался в Claude Code — оба шлют одинаково корректные, но РАЗНЫЕ по `dwControlKeyState` win32-input-mode-последовательности); Ctrl+Enter НЕ работает одинаково в ОБОИХ приложениях (Claude Code и Codex) несмотря на корректно закодированную и отличную от Shift+Enter последовательность — вывод: это осознанный выбор самих приложений не биндить именно эту комбинацию, не баг OnlyTerm. Вся диагностика (`log::error!("DIAG ...")` в `window.rs`, `keyevent.rs`, `performer.rs`, `keyboard.rs`, `termwindow/mod.rs`) полностью убрана перед финализацией.

## Decisions
- Ctrl+C/Ctrl+Enter/Shift+Enter должны кодироваться через СОГЛАСОВАННЫЙ приложением протокол клавиатуры (win32-input-mode/kitty) вместо хардкода сырого байта — новый общий хелпер `encode_via_negotiated_protocol`, с откатом на старый сырой байт только если протокол не согласован (строго не хуже старого поведения).
- `enable_kitty_keyboard` включён по умолчанию третий раз — предыдущие два отката были из-за бага в `CopySelectionOrInterrupt` (уже исправлен), а не в самом kitty-протоколе.
- Ctrl+Enter НЕ чинится дальше — подтверждено живыми логами, что OnlyTerm шлёт корректную, отличную от Shift+Enter последовательность; оба независимых приложения (Claude Code, Codex) одинаково её не используют — решение на стороне приложений, не наша зона.
- Круглый логотип сделан скриптом Python/Pillow напрямую поверх PNG-мастера (не трогая исходный `.svg`), поскольку продовые ассеты уже были вручную отредактированы в обход `update.sh`-пайплайна в прошлой сессии.
