**Цепочка Startup UX (#382→#383→#384→#385) полностью закрыта:**

- **#383** (двойной resize) — реализовано МНОЙ напрямую (не через
  crush/sh), пока crush ещё не был запущен в этом раунде. Причина:
  `render_pipeline.rs` брал DPI для начального расчёта размеров окна
  через `::window::default_dpi()` ДО создания окна, а Windows
  `ConnectionOps` не переопределял этот метод — всегда хардкод 96.0. На
  HiDPI-мониторе это расходилось с реальным DPI, который Windows
  сообщает после показа окна → `WM_DPICHANGED` → видимый resize. Фикс:
  `default_dpi()` для Windows теперь берёт реальный DPI основного
  монитора через уже существующую `get_primary_monitor_dpi()` (та же,
  что `create_window()` использует для рамки). Коммит `aac97ab06`.

- **#384** (лоадер вместо заливки) — делегировано через `Agent
  subagent_type=sh` (crush был в peak-hours отказе провайдера `zai` до
  12:00, см. ниже). Плоская заливка-заглушка заменена на анимированный
  GDI-спиннер (8 точек по кругу, "хвост" затухает, вращение раз в 1.4с),
  рисуется тем же лёгким GDI-путём, что и старая заливка — WebGpu не
  участвует. Таймер 30fps (`SetTimer`/`KillTimer`, id=1). Коммит
  `b4e1e8c04`. Лично перепроверено: build/clippy/fmt чисто, диф прочитан
  полностью, конфиг пользователя не тронут.

- **#385** (fade-переход) — тоже делегировано через `Agent
  subagent_type=sh`. Архитектура: отдельное `WS_EX_LAYERED` дочернее
  окно-оверлей поверх WebGpu child window (напрямую блендить GDI с
  DXGI-кадрами внутри одного HWND невозможно — flip-model presentation
  отдаёт пиксели WebGpu целиком). Оверлей красит статичный кадр спиннера
  и дальше только меняет альфу (255→0 за 320мс). Триггер fade — ПОЗДНЕЕ
  из (рендерер готов, первый непустой вывод pty — переиспользован
  существующий `MuxNotification::PaneOutput`). Коммит `67c6e6968`.

  **При личной проверке диффа найден и исправлен реальный баг** (коммит
  `44d10a6f6`, до закрытия задачи): `start_placeholder_fade` красил
  первый кадр оверлея через `UpdateWindow(overlay_hwnd)`, что синхронно
  диспатчило `WM_PAINT`/`WM_ERASEBKGND` → `paint_parent_placeholder_spinner`
  → `try_borrow()` на ТОТ ЖЕ `WindowInner`, уже мутабельно заborrowed
  вызывающим кодом (`Connection::with_window_inner` держит `borrow_mut()`
  на всё время closure). `try_borrow()` всегда падал тихо, первый кадр
  оверлея оставался непрокрашен — весь fade показывал бы GDI-мусор
  вместо последнего кадра спиннера. Тот же класс реентрантности, что уже
  описан в комментарии `wm_paint` для оригинального спиннера, но не
  учтён для нового оверлея. Исправлено рисованием напрямую через
  `GetDC`/`ReleaseDC` внутри `start_placeholder_fade`, минуя window
  proc/borrow. Это единственная находка zero-trust проверки — остальной
  диф (4 файла, ~580 строк) прочитан целиком и вопросов не вызвал.

  начинался, а фикс был уже наполовину продуман по итогам #382; решено

- crush упал по peak-hours (`zai`, до 12:00) — переключение на armed
  fallback `@sh` (задача #369) выполнено автоматически, без вопроса
  пользователю, строго по протоколу skill `crush-fallback`, с
  одноразовым cron на автовозврат.
- #385: архитектурное решение (отдельное `WS_EX_LAYERED` окно-оверлей,
  а не альфа поверх существующих окон) было предложено как сильная
  рекомендация в промпте для `sh`-агента — агент подтвердил, что это
  единственный рабочий вариант (не просто "более красивый"), после
  трассировки рендер-пайплайна.
- #385: триггер fade — более позднее из (рендерер готов, первый вывод
  pty), а не только рендерер — обоснование в самой задаче #382
  (не фейдить в ещё "мёртвый" на вид, не отвечающий терминал).
- Найденный при ревью #385 реентрантный `try_borrow()`-баг исправлен
  МНОЙ напрямую (не переделегирован обратно `sh`) — фикс маленький,
  локализованный, причина понятна с полной уверенностью по чтению кода
  (`with_window_inner`'s `borrow_mut()` + `paint_parent_placeholder_spinner`'s
  `try_borrow()` на тот же `RefCell`), переделегация добавила бы только
  задержку без выигрыша в качестве.
- Полный `dev-install.ps1` (release + UAC + install) НЕ запускался мной
  в этой сессии — headless-песочница не проходит интерактивный UAC;
  вместо этого использовался debug-билд для диагностики, а пользователь
