1. **User reported the real, live symptom**: after installing the release build, Hebrew text (generated by Claude Code inside a running pane) rendered with duplicated punctuation ("לעולם,," instead of "לעולם,") and scattered/garbled letter spacing, not just the earlier crash. Screenshots were provided at each step showing partial improvement per fix.
2. **Bug #1 found and fixed — bidi resolved per-attrs-cluster instead of per-line**: `CellCluster::make_cluster` (`crates/wezterm-surface/src/cellcluster.rs`) used to split a line into attrs-uniform pre-bidi clusters FIRST, then run bidi resolution independently within each. If a chatty program (like Claude Code, applying per-token/per-color styling) gives Hebrew characters different attrs, each character became its own isolated 1-char bidi "paragraph" with no surrounding context. Fixed by rewriting `make_cluster` to dispatch to either `make_cluster_no_bidi` (old logic, unchanged, used when bidi is off) or a new `make_cluster_with_bidi` that resolves the Unicode Bidi Algorithm across the **entire line** first (building one paragraph from all cells regardless of attrs), then splits the resulting visually-reordered runs by attrs afterward. The old per-cluster `resolve_bidi` method was deleted entirely, since clusters are now built directly via the normal `CellCluster::new`/`.add()` path (correct byte_to_cell_idx/width bookkeeping falls out for free, no separate byte-remapping math needed).
3. **Bug #2 found and fixed — `ReorderedRun::range` vs `::indices`**: after bug #1's fix, duplicated punctuation persisted. Root cause: `make_cluster_with_bidi` walked `run.range` (a `min..max+1` numeric envelope over a run's visually-contiguous codepoints) to find which cells belong to a bidi run. This envelope is NOT guaranteed to contain only that run's codepoints when multiple runs are interleaved (common with mixed Hebrew/Latin/punctuation) — it can overlap a neighboring run, visiting (and rendering) the same character twice. Fixed by using `run.indices` (the exact, deduplicated set of codepoints for the run) instead, sorted ascending to recover logical order for harfbuzz. Confirmed via a new invariant test (`bidi_clusters_do_not_duplicate_or_drop_cells`) asserting every original cell is covered by exactly one resolved cluster.
4. **Bug #3 found and fixed — THE root cause of garbled spacing/"wrong direction"**: even after bugs #1/#2, letter spacing was still wrong ("too glued" or "too wide") in real multi-word Hebrew output, and the user reported it visually reading left-to-right (wrong). Root-caused via a new diagnostic test shaping a real 4-word Hebrew phrase through the REAL default font stack (JetBrains Mono primary, zero Hebrew coverage, falling back to Noto Sans Hebrew) and asserting shaped glyphs' `num_cells` sum equals the cluster's width — this FAILED (54 vs 21 cells), revealing bogus glyph entries claiming up to 18 cells each (`only_char: None`). Traced to `crates/wezterm-font/src/shaper/rustybuzz.rs`'s `ClusterResolver`: when the "incomplete" (missing-glyph) recursive-fallback path recurses into `do_shape(font_idx+1, s, ..., first_info.cluster..first_info.cluster+first_info.len, ...)` for a sub-range starting at a NON-ZERO byte offset (e.g. a Hebrew word that isn't the very first thing on the line), rustybuzz reports `info.cluster` values 0-based **relative to the pushed substring** (`&s[range]`), but `ClusterResolver::build`/`get_mut` treated these as ABSOLUTE offsets into the full `s` — a units mismatch whose magnitude exactly equals `range.start` (verified empirically: word4 at range.start=31 → byte_len overshoot of 31; word1 at range.start=0 → no bug, which is exactly why every earlier, smaller reproduction attempt this session missed it). Fixed with a 2-line change: `ClusterResolver::build` now computes `start = info.cluster as usize + range.start` (absolute from the start), and the corresponding `get_mut` lookup adds the same `+ range.start`. Verified: the diagnostic test now passes exactly (21==21, every glyph `num_cells=1`, no `None` entries), and the full 49-test `wezterm-font` suite passes (there's also a `reproduces_the_captured_clamp_warning_input` test present in the file testing the exact ",םלועל " string from an earlier real crash log — passing).
5. **GPU/TDR crash investigation (interleaved with the above)**: mid-session the user reported ALL wezterm-gui.exe/onlyterm-gui.exe processes crashed simultaneously with a preceding black screen, and ~10 minutes of progressively worsening mouse/UI stutter beforehand. Investigated and found: (a) the app's own `do_paint()` in `crates/wezterm-gui/src/termwindow/mod.rs` already detects `gl.is_context_lost()` and calls `window.close()` (not a panic) — this is pre-existing upstream code, shared by both real WezTerm and OnlyTerm, so a driver-level TDR event would close ALL such windows simultaneously regardless of which app's content triggered it; (b) crucially, this close path was missing the `mux.kill_window(self.mux_window_id)` call that the normal `close_requested` path has, meaning panes'/shells' child processes were being orphaned on context loss — fixed by adding that call (mirrors `close_requested`'s teardown exactly). (c) Root-cause reasoning for WHY the GPU hang happened at all: bug #3 (above) caused some glyphs to falsely claim occupying far more terminal cells than they should (measured up to 18 in a small test; scales with position in the text, so worse for longer real output), and the render loop iterates `0..num_cells` per glyph for cache/quad population — so as Claude Code kept streaming more Hebrew over ~10 minutes, the per-frame rendering cost from this bug scaled worse than linearly with the growing scrollback, plausibly explaining the progressive slowdown culminating in a GPU driver TDR reset. This is presented to the user as a confident, evidence-based (not just circumstantial) explanation now that bug #3's mechanism is concretely understood.

## Decisions
- Chose to resolve bidi across the WHOLE line before splitting by attrs, rather than the reverse (original upstream order) — necessary for correctness whenever a program applies non-uniform per-character/per-token styling to RTL text.
- Chose `run.indices` (exact, sorted) over `run.range` (numeric min..max envelope) for reconstructing which codepoints belong to a bidi run — the envelope approach is unsafe whenever runs are interleaved.
- Fixed the `ClusterResolver` relative/absolute offset bug with the minimal 2-line change (`+ range.start` in `build()` and in the `get_mut` lookup) rather than a larger refactor, since this exactly restores the invariant the rest of the code already assumes (absolute offsets into `s` everywhere else).
- Kept the earlier `clamp_to_char_boundaries` defensive fix in place even though the true root cause is now fixed — it's a legitimate belt-and-suspenders safety net against any future/unknown boundary edge case, and its `log::warn!` gives an early signal if it ever fires again.
- Added `mux.kill_window(...)` to the context-lost close path (mirroring `close_requested`) rather than leaving child processes orphaned — chosen immediately once the user flagged "loss of control" as a concern.
- When asked to kill stray terminal windows, explicitly asked the user how to safely identify which PID to preserve (rather than guessing) since killing the wrong one would have silently terminated the active Claude Code session with no way to recover.
