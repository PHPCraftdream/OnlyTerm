# Checkpoint — 2026-07-23 08:38 [onlyterm-fork-setup]

## Session summary

We've spent this session investigating recurring OnlyTerm crashes on the user's Windows machine (build `20240203-110809-5046fc22`, timestamp `65be8a36`) and just finished setting up a personal fork to start real fixes.

Two distinct, unrelated bugs were found and filed upstream:

1. **Font-fallback panic** ([wezterm/wezterm#7963](https://github.com/wezterm/wezterm/issues/7963)) — `load_fallback` in `onlyterm-font/src/shaper/harfbuzz.rs` (around line 468 in the installed build) panics when a configured fallback font family (e.g. `"Cascadia Mono"`) resolves via DirectWrite to a font file that physically lives inside a Windows Store/MSIX package directory (`C:\Program Files\WindowsApps\Microsoft.WindowsTerminal_.../CascadiaMono.ttf`). That directory has restrictive ACLs, so opening the file fails with `Access is denied (os error 5)`, which isn't handled and panics instead. The panic is normally caught one layer up (`window::os::windows::window > caught Any {..}`) so it just silently closes the window — but under repeated triggering (a CLI tool's spinner glyph animating fast, cycling the same missing glyph over and over for ~3 days in one window) it eventually escalated into an *uncaught* fatal abort, `STATUS_FATAL_APP_EXIT` (`0xc000041d`), instead of the usual caught panic. We suspect (not proven — no debugger stack walk available at the time) a double-panic-during-unwind scenario, based on finding Rust's `fatal runtime error: thread local/result panicked on drop` strings embedded in the binary via `strings` on the crash dump.
   - **Local mitigation is currently ONLY in the user's live config**, `C:\Users\Computer\.config\onlyterm\wezterm.lua` — NOT yet in this repo's source. It replaces the ambiguous fonts (`JetBrains Mono`, `Cascadia Mono`) with ones verified to physically exist in `C:\Windows\Fonts` (`Lucida Console`, `Miriam Mono CLM`, `DejaVu Sans Mono`, `Segoe UI Historic`, `Segoe UI Symbol`), and sets `config.font_locator = 'ConfigDirsOnly'` + `config.font_dirs = { 'C:\Windows\Fonts' }` to fully disable DirectWrite-based system font discovery — structurally preventing OnlyTerm from ever resolving to a WindowsApps-packaged font file again. `Segoe UI Symbol` had to be added specifically because `ConfigDirsOnly` also kills onlyterm's automatic "ask DirectWrite for any installed font that covers this glyph" fallback, which had been silently covering glyphs like U+203B (`※`) and U+23F5 (`⏵`).
   - **The real fix belongs in code**: in `load_fallback`, catch the IO/Access-Denied error and skip to the next fallback candidate instead of panicking. This is the change we intend to make in this fork.

2. **Recurring stack overflow** ([wezterm/wezterm#7965](https://github.com/wezterm/wezterm/issues/7965), follow-up comment about a missing PDB) — `STATUS_STACK_OVERFLOW` (`0xc00000fd`) at a *stable* offset, `onlyterm-gui.exe+0x1032a82`, reproduced 3 times on separate days on the same build. Unrelated to bug #1 (different fault module/exception/trigger). We got a full minidump this time (Windows Error Reporting `LocalDumps` was configured earlier in the investigation) and parsed it with the pure-Python `minidump` library (no debugger was available at first). The crashing thread's captured stack was ~1MB — essentially the whole default thread stack, fully exhausted. Scanning it for repeated return addresses inside `onlyterm-gui.exe` found a strong recursive pattern: `+0x28b0f70` (1331×), `+0x1032b3d` (783×, a few bytes past the exact crash IP), `+0x1033f6c` (440×), plus clusters at `+0x18ca2a5..+0x18ca8b9` and `+0x1f30b0e` — consistent with 2–4 functions calling each other in a cycle until the stack ran out (1331 frames × ~770 bytes/frame ≈ 1MB, matches almost exactly).
   - We then installed WinDbg (via `winget install Microsoft.WinDbg`) to get a modern `dbghelp.dll`/`cdb.exe` — had to elevate + `robocopy` the DLLs out of the ACL-protected `WindowsApps` package directory (the *same* ACL class of problem as bug #1, ironically, just for a different app). Downloaded the official Windows release zip for this exact version and extracted the bundled `onlyterm.pdb`, but `cdb.exe` reported `mismatched pdb` — the exe's debug directory specifically asks for `onlyterm_gui.pdb` (matching the Rust crate name with underscore), and the zip's `onlyterm.pdb` doesn't match/cover `onlyterm-gui.exe` (most likely it's the PDB for a different binary in the workspace, e.g. `onlyterm.exe`). We posted this as a follow-up comment on #7965 for the maintainers' benefit — no real symbol names were recoverable from what's publicly published.
   - **Root cause is still unknown at the source level.** This is the main reason we're building from source now: a debug build gives us a matching PDB, so we can finally identify which function(s) are recursing and fix them.
   - Possible (unconfirmed) relation: an independent reviewer (the `fh` agent) flagged [#7527](https://github.com/wezterm/wezterm/issues/7527) ("Unbounded PDU memory allocation causes OOM crashes and stack overflow") as a plausible relative — not verified either way.

We then researched active community forks to see whether either bug is already fixed elsewhere, since waiting on upstream review could take a while:

- **wakterm** ([wakamex/wakterm](https://github.com/wakamex/wakterm)) — an active, agent-first fork with a real `CHANGELOG-FORK.md`. Notably, it **already has a merged fix for #7527** (commit `e1e8510`, adds a `MAX_PDU_SIZE` 64MiB check before allocation) — potentially relevant/overlapping with our stack-overflow bug, though not confirmed to be the same root cause. It also has fixes for: an OOM from an unbounded `SynchronizedOutput` buffer (25GB+, added a 4MB safety valve), a deadlock in `domain_was_detached` (#7661, downgraded `windows.write()` to `windows.read()`), an infinite loop on extreme window shrink (#4878), and a tmux `-CC` parser error on an empty line (#7656). No Windows-specific fixes were found there for either of our two bugs.
- **wezmux** ([vcabeli/wezmux](https://github.com/vcabeli/wezmux)) — a UI/feature fork (persistent workspace sidebar, git/PR/port status, agent notifications via a custom OSC 7777 protocol, Claude Code/Codex integration). Not a bugfix fork — no changelog of crash fixes, and Windows support is preview-only. Only relevant as a UX reference, not for our crash work.

**Intention going forward**: use this fork to (a) implement the real fix for #7963 (catch-and-skip instead of panic in `load_fallback`), (b) get a debug build with a matching PDB to finally diagnose #7965's real recursive call chain and fix it, (c) possibly cherry-pick wakterm's #7527 fix if it turns out relevant, then (d) upstream proper PRs to `wezterm/wezterm` once fixes are verified locally.

**New, separate, not-yet-scoped goal for this repo**: eliminate the C code dependency at `deps/cairo`. We just confirmed what it actually is: `deps/cairo/Cargo.toml` is `cairo-sys-rs` (FFI bindings crate from `gtk-rs-core`), which vendors the **actual C source trees** for `cairo` (under `deps/cairo/cairo/`) and `pixman` (under `deps/cairo/pixman/`), imported via `import-cairo.sh`/`import-pixman.sh` and compiled through `build.rs` using the `cc` crate. This is a substantial, real amount of vendored C code, not a thin wrapper. Nothing has been done on this yet — first real steps would be: figure out which onlyterm crates actually consume `cairo-sys`/`cairo-rs` at build time and for what (likely some 2D rendering/glyph-cache path, possibly platform-specific), whether it's reachable/necessary on the Windows target we care about, and what a pure-Rust replacement (e.g. `tiny-skia`) would need to cover before `deps/cairo` could be dropped.
