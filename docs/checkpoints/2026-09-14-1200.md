## Session summary

This stretch started as UI polish on the window-title CPU/RAM block (task #666,
centering it with space padding) and ended somewhere else entirely: diagnosing
two real OnlyTerm crashes and hardening the code path they died in.

The centering work went through four failed attempts (character-count
approximation, pixel measurement against the wrong font, a fixed button-cluster
allowance, then the correct `SPI_GETNONCLIENTMETRICS` caption font) and was
written up in `docs/investigations/2026-09-08-title-block-centering.md` before
the user told me to stop. A later session (not me) then landed `62c9817a8`
("stabilize Windows captions, resize input, and idle CPU"), which apparently
took a different route — a separately painted caption — and my uncommitted
centering work is gone from the tree. I did not review that commit.

Then the user reported crashes. I analyzed two dumps in
`C:\CrashDumps\OnlyTerm\` (`onlyterm-gui.exe.9616.dmp` @ 11:04 and
`.20976.dmp` @ 11:15) with `cdb.exe` from the Windows Kits, pointed at the PDBs
that ship next to the install in `C:\Program Files\OnlyTerm`. (`minidump-stackwalk`
alone was useless — it wants Breakpad `.sym`, so it printed raw offsets.) Both
crashes are identical and are *not* stack overruns despite the
`EXCEPTION_STACK_BUFFER_OVERRUN` label: it is `int 0x29` reached from
`std::alloc::rust_oom → std::process::abort`, i.e. Rust's unconditional
abort-on-allocation-failure. The failing allocation is inside
`procinfo::windows::fresh_snapshot_entries`, converting one process's
`szExeFile` to a `PathBuf` (`Wtf8Buf::from_wide → Vec::with_capacity`). Both
logs carry `WARN procinfo::windows: process snapshot failed: The paging file is
too small (os error 1455)` immediately before the abort.

The external cause was found and is *not* OnlyTerm: a transient storm of ~1694
`cli.test` processes plus ~1720 `conhost` (~41 GB + ~21 GB working set at peak)
that had already self-resolved by the time I re-sampled minutes later — I never
captured its command line or parent, because WMI itself was failing under the
pressure. For scale, all 9 OnlyTerm windows together were ~2.2 GB. So the
terminal was a bystander whose small bookkeeping allocation happened to be the
one that hit the wall. I corrected the user's premise on this explicitly.

I then implemented three improvements (all verified, none committed):
packed exe names + reused buffers in procinfo (#667), failure backoff (#668),
and skipping the usage sample entirely on unfocused windows. Along the way I
found and fixed a latent defect from `62c9817a8`: `procinfo` calls
`FILETIME::default()` but never declared `winapi/impl-default`, so it builds
inside the workspace (feature unification via termwiz) yet `cargo test -p
procinfo` alone does not compile at all.

Verification at the time of writing: `cargo test -p procinfo -p onlyterm-gui`
= 28 + 181 passed, `cargo clippy -p procinfo -p onlyterm-gui -p mux
--all-targets -- -D warnings` clean, `cargo +nightly fmt --all -- --check`
clean. Nothing is committed; the user was asked whether to commit and has not
answered yet.

## Decisions

- Diagnosed the crashes with `cdb.exe` + the shipped PDBs rather than
  `minidump-stackwalk`, which cannot use raw PDBs and produced only offsets.
  The second dump's stack was clean; the first was polluted by identical-code
  folding (it appeared to implicate wgpu types inside `procinfo`) — I treated
  that as a symbolization artifact rather than evidence.
- Stated plainly that the crash is not "children ran out of memory and killed
  the parent": the failing allocation was OnlyTerm's own, and Rust aborts the
  process on allocation failure by design.
- Rejected making the failing allocation fallible (`try_reserve`): the failure
  is inside std's `Wtf8Buf::from_wide`, which has no fallible variant, so it
  would mean hand-rolling UTF-16 decoding. Also rejected a custom
  alloc-error-hook (unstable, still aborts). Chose to reduce how often and how
  much that path allocates instead — probability reduction, not immunity, and I
  said so.
- Chose to have unfocused windows skip sampling entirely rather than merely
  lengthen their interval, so a window regaining focus still produces a figure
  within one 5s interval, and dropped the stale baseline so the first sample
  after an idle gap is not a CPU average smeared over that gap.
- Preserved the "a partially filled walk is never published" invariant when
  introducing buffer reuse: a failed refill keeps its buffer private as scratch
  and callers keep getting the last complete snapshot. Covered by tests.
