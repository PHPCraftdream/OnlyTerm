**Shell-immune cwd-based tab titles + cascading config title (`79e36c6e2`).** User
asked why the tab title (derived from cwd basename) could flicker rapidly during work.
Root cause: `LocalPane::get_current_working_dir` sourced the directory purely from the
shell's own OSC 7 escape sequence (`crates/term/src/terminalstate/performer/osc.rs`),
which any process in the pane can print arbitrarily -- a build script that `cd`s
internally and back, or a prompt framework re-emitting OSC 7 on every render, desyncs
the displayed title from reality. Follow-up ask: eliminate shell control entirely --
title should always be exactly one of: explicit rename, config-provided title
(cascading), or the real (OS-observed) directory. Implemented:
- `get_current_working_dir` now calls `divine_current_working_dir` (already existed as
  a cache-miss fallback; walks the real foreground process's cwd via the OS, not the
  shell's self-report) FIRST, OSC 7 only as a last-resort fallback. This is a
  `Pane`-trait-level change, so it also fixes cwd for mux-server-served panes for free
  -- the server populates `GetPaneRenderChangesResponse.working_dir` from this same
  method (`wezterm-mux-server-impl/src/sessionhandler/per_pane.rs:75`).
- `LocalPane::new` gained a `starting_cwd: Option<Url>` param (computed from
  `CommandBuilder::get_cwd()`, falling back to `$HOME`) to seed `last_known_good.cwd` at
  spawn time -- covers the ~300ms cold-cache window before the foreground-process cache
  first warms up (`divine_process_list`'s `AllowStale` returns `None` immediately on a
  cold cache by design, to avoid blocking the GUI thread -- see task #247 commentary
  in `localpane.rs`). Required threading the new param through every `LocalPane::new`
  call site (`domain.rs` x3, `tmux_commands.rs`, `wezterm-gui/.../actions.rs` test
  helper, 5 test call sites across `mux`).
- New config surface: `SpawnCommand.title: Option<String>` (per-launch) and
  `Config.default_tab_title: Option<String>` (global fallback), resolved in
  `wezterm-gui/src/spawn.rs::resolve_spawn_title` and applied via `tab.set_title(...)`
  right after spawn -- deliberately reuses the *same* `Tab.title` field an explicit
  rename writes to, so "explicit rename always wins" falls out for free (a later rename
  just overwrites the same field) rather than needing a second priority-tracking field.
- Removed `use_cwd_basename_as_tab_title` config (its `false` branch was exactly the
  now-forbidden raw-OSC-title fallback) and the `pane.title` (OSC 0/2) fallback from
  both `compute_tab_title` (tabbar.rs) and the window-title computation (actions.rs).
  Old doc page deleted, new `docs/config/reference/config/default_tab_title.md` added,
  `SpawnCommand.md` updated with the new field. (`mkdocs.yml` and
  `docs/config/reference/config/index.md` are both gitignored/generated -- hand-edited
  them anyway for local consistency, but they don't affect what gets committed.)

**Resize/output-apply race (`9c8ba85b9`).** Separate user report: a live screenshot
showed shell output landing exactly one row below its prompt (`git checkout develop`
echoed one row low), described as intermittent ("periodically"). Diagnosed by reading
code, not by reproducing live (I do not touch the running GUI per this repo's
CLAUDE.md). Root cause, found by tracing `LocalPane::resize`
(`crates/mux/src/localpane.rs`): it called `pty.resize()` (ConPTY on Windows -- reacts
to the new geometry by writing an immediate repaint into the pty) and
`terminal.lock().resize(size)` as two *separate* steps with no shared lock held across
them. The per-pane pty-reader thread (`thread::spawn(... read_from_pane_pty ...)` in
`mux/src/lib.rs:793`) parses that repaint and applies it via
`perform_actions`/`perform_actions_chunked`, which take `terminal.lock()`
independently -- it could win the race and apply new-geometry-relative cursor moves to
a `Screen` still sized for the old geometry. Explains "periodically": `start_maximized`
defaults to `true` in this fork and isn't overridden in the user's config, so *every*
new window resizes right as its shell prints the first prompt -- a real, recurring race
window, not a rare edge case.

Fix has two parts (`resize_guard: Mutex<()>` on `LocalPane`, always acquired before
`terminal`/`pty`):
1. `resize()` now holds `terminal.lock()` across both the pty resize and the terminal
   model's resize -- the reader thread can no longer interleave between them.
2. A second, narrower window remained even with (1): `perform_actions_chunked`
   (task #147 -- splits a large batch of already-parsed actions into pieces, releasing
   `terminal.lock()` between them so keyboard/mouse/render can interleave) could still
   let a resize slice into the *middle* of one logical ConPTY repaint that chunking
   itself split apart. `resize_guard`, held for the *whole* batch (not per-chunk) in
   `perform_actions_chunked` and by `resize()`, closes this without reintroducing
   per-chunk lock-holding -- input/render, which don't touch `resize_guard`, still
   interleave between chunks exactly as before.

**Regression test went through two iterations, both empirically driven, not just
reasoned about.** First version asserted `resize()`'s and a chunked batch's *outer
call* wall-clock spans never overlap -- this is the WRONG invariant (a caller queued
waiting for a mutex has an outer span that legitimately overlaps the holder's; that's
what correct locking looks like, not a violation) and was caught failing against the
real, correct fix, not a bug. Rewrote to measure only time spent *waiting* to acquire
`resize_guard` (mirroring the file's existing `_timed` helper pattern), asserting a
concurrent chunked batch produces measurable contention. Second false start: asserted
on the *median* wait, which is near-zero by the test's own design (a fast resize loop
races far more attempts than the ~2 batches per test run, so only the one resize call
in flight when a batch acquires the guard actually blocks; all others land in the free
gaps between batches) -- switched to asserting on `max_wait` instead, which correctly
lands in the hundreds-of-ms range matching a batch's own hold time. Verified against a
real mutant (temporarily removed `resize_guard` from the chunked path): max wait
dropped from ~900ms to ~52us and the test failed as expected, confirming it has teeth
before trusting it as a merge gate.

## Decisions

- Prefer the OS-observed cwd (`divine_current_working_dir`) over the shell's OSC 7
  self-report everywhere `get_current_working_dir` is consulted, not just for titles --
  a `Pane`-trait-level fix benefits every consumer (hyperlink resolution, "spawn in same
  cwd", etc.) and reaches mux-server-relayed panes for free, at the cost of no longer
  trusting a legitimate remote-only cwd source in the rare case OS-divination is
  unavailable (falls back to OSC 7 there, same as before).
- Config-provided tab title reuses the *same* `Tab.title` field an explicit rename
  writes to, rather than a separate lower-priority field, so priority ordering falls
  out of write-ordering instead of needing an explicit priority check at read time.
- `use_cwd_basename_as_tab_title` removed outright rather than kept as a now-inert
  toggle -- its only remaining branch (raw OSC title) was exactly what this change
  exists to forbid.
- `resize_guard` is a *third* lock (alongside `terminal` and `pty`), not a widening of
  `terminal.lock()`'s scope in `perform_actions_chunked` -- holding `terminal.lock()`
  for a whole batch there would defeat task #147 (input/render starvation) entirely;
  `resize_guard` gets mutual exclusion against `resize()` specifically without touching
  that.
- Split the two features into two commits despite both touching the same two files,
  via manual hunk-level revert/restore rather than `git add -p` (no interactive TTY
  available) -- kept history matching the repo's established one-logical-change-per-
  commit convention.
