**Git Bash fix (small, closed):** the New Tab Options dialog's "bash" shell choice resolved a bare
`"bash.exe"` via PATH, which on this machine (WSL installed) actually launched WSL, not Git Bash,
because Windows' `CreateProcess`-family search checks `%SystemRoot%\System32` (which has a legacy
WSL `bash.exe` shim) *before* consulting PATH-listed directories, even though `where.exe` (which
doesn't replicate that same-directory-first precedence) reports Git Bash first. Fixed in
`crates/wezterm-gui/src/termwindow/newtab_options.rs` with a new `find_git_bash()` that probes
well-known Git-for-Windows install locations directly (`%ProgramFiles%`/`%ProgramFiles(x86)%\Git\
bin\bash.exe`, `%LOCALAPPDATA%\Programs\Git\bin\bash.exe`) instead of relying on ambiguous PATH
resolution, falling back to the bare name only if none exist. Build/clippy/fmt clean.

**Phase C: elevated tabs via a new WebSocket rendezvous transport.** The user confirmed live that
admin/elevated tabs still open a separate OS window (expected -- Phase C was never implemented).
Delegated research to `@oh` on how to solve this properly: `ShellExecuteExW("runas")` cannot pass
an inheritable handle to the elevated child the way `CreateProcess` can (confirmed via Microsoft
docs -- no `STARTUPINFO`/handle-inheritance path in `SHELLEXECUTEINFOW`, and the actual elevated
`CreateProcess` happens inside the Application Information service, not the calling process), so
the existing non-elevated single-pane transport (`proxy_command`+`socketpair()`) fundamentally
cannot be reused as-is. The research surfaced a critical, non-optional finding: **Windows Terminal
explicitly *declined* to build this exact feature** (elevated tab hosted in an existing unelevated
window) over security concerns -- any other unelevated process could potentially reach the IPC
channel and drive the elevated process. Microsoft's own `sudo for Windows` does something similar
but ships with an explicit risk warning and defaults away from it. The user, informed of this
tradeoff, chose to proceed anyway but **with a hard security requirement**: the elevated child's
mux session handler must enforce a strict PDU allow-list (reject `SpawnV2`/`SplitPane`/etc., which
would otherwise let anything reaching the channel ask the elevated process to spawn arbitrary
elevated processes -- a full UAC bypass) -- this is tracked as task #563 and is explicitly *not*
deferred to a later phase.

The user specifically directed the transport to be **WebSocket + a 64-character Base58 token**
(their explicit technical choice, not the research's own "lowest novelty" recommendation of plain
loopback TCP + token -- implemented as directed). Built a new workspace crate,
`crates/wezterm-elevated-transport`, containing: `generate_rendezvous_token()` (CSPRNG via
`getrandom::fill`, rejection-sampled Base58, avoiding modulo bias), `RendezvousListener` (binds an
ephemeral loopback port, accepts+verifies the token during the WS handshake via a `tungstenite`
`Callback`, rejecting with 403 on mismatch), `connect_and_bridge` (client-side: connects out,
completes the WS handshake presenting the token as a custom header), and
`spawn_bridge_to_local_stream`/`pump_bridge` (bridges WS binary messages onto one end of a
`filedescriptor::socketpair()` via a background polling thread, since Windows' `async-io`/`Async<T>`
only supports `AsSocket` types and a message-oriented `WebSocket<TcpStream>` isn't one -- the other
socketpair end, wrapped as `wezterm_uds::UnixStream`, is what the existing mux client/server
machinery will consume unchanged, since `Reconnectable` already accepts a pre-connected stream).
`wezterm-gui` and `wezterm-mux-server` will each depend on this new crate independently (neither
depends on the other; `wezterm-gui` is a binary crate and can't be a library dependency).

## Decisions

- WebSocket + 64-char Base58 token chosen explicitly by the user for the elevated-tab rendezvous
  transport, over the research's own "lowest novelty" recommendation (plain loopback TCP + token) --
  implemented as directed despite the extra complexity (message-to-stream bridging) it requires.
- Non-elevated transports (Phase A/B's `proxy_command`/socketpair, and the separate ACL'd
  unix-domain-socket-emulation for CLI tooling) are explicitly NOT being migrated to WS+token --
  user-confirmed decision (task #568): no real security gap exists there to justify the churn/risk
  against already-tested working code.
- PDU allow-list for the elevated channel (task #563) is mandatory, in-scope for Phase C itself, not
  deferrable to Phase E -- directly in response to the Windows-Terminal-declined-this-feature finding.
- New shared library crate (`wezterm-elevated-transport`) created rather than putting the code in
  `wezterm-gui` (can't be depended on, it's a binary crate) or bloating `wezterm-uds` (would add a
  `tungstenite` dependency to crates that don't need it).
- Delegated the current test-flakiness bug to a fresh `@oh` agent (per explicit user instruction to
  do so if stuck) rather than continuing to debug solo in a shell session with many hours of
  accumulated build-tool churn that may itself be a confounding factor.
