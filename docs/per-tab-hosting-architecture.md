# Архитектура хостинг-процессов вкладок (одна вкладка — один процесс)

Документ описывает, как вкладка OnlyTerm становится отдельным процессом, в том числе с правами администратора. Это текущее состояние системы, зафиксированное по реальному коду, а не план.

См. также модель безопасности транспортов в [per-tab-hosting-security-model.md](per-tab-hosting-security-model.md).

## Самое главное: по умолчанию всё это выключено

Прежде чем читать дальше — изоляция вкладок **не включена из коробки**.

`crates/wezterm-gui/src/spawn.rs` решает так:

```rust
let use_single_pane =
    config.per_tab_process_isolation && !matches!(spawn_where, SpawnWhere::SplitPane(_));
```

а сам флаг объявлен в `crates/config/src/config.rs` как `#[dynamic(default)] pub per_tab_process_isolation: bool`, то есть по умолчанию `false`. Пока его не включили, Ctrl+Shift+T создаёт обычную панель внутри процесса GUI (`mux::localpane`), и ни одного `onlyterm-mux-server.exe` не появляется. Проверено живым запуском: с флагом семь вкладок дали шесть хостинг-процессов (седьмая — стартовая, она поднимается через локальный домен и остаётся внутри GUI), без флага — ни одного.

Из этого правила есть одно исключение: **администраторская вкладка флага не спрашивает**. У неё отдельный путь (`spawn_elevated_single_pane_tab`), и своим процессом она становится всегда — иначе она попросту невозможна, поднятый код не может жить внутри непривилегированного GUI.

Разделение панели (`SpawnWhere::SplitPane`) изоляции не получает никогда: хостинг-процесс по построению держит ровно одну панель.

Комментарий у поля объясняет выключенное состояние тем, что домен вкладки не разрегистрируется при её закрытии. Это обоснование **устарело**: `Mux::remove_domain` появился и вызывается (см. раздел про cleanup ниже). Вопрос о смене умолчания открыт и решается не здесь.

## Обычная вкладка: end-to-end путь

Когда пользователь создаёт обычную (не администраторскую) вкладку — при включённом флаге, см. выше — запускается `spawn_single_pane_tab` в `crates/wezterm-gui/src/spawn.rs`.

### Создание домена

GUI создаёт `ClientDomain` с конфигурацией `UnixDomain`, где `proxy_command` указывает на `onlyterm-mux-server.exe --single-pane`. Основные параметры:

- `domain_name`: уникальное имя формата `single-pane-{id}`, генерируется через `alloc_domain_id()`
- `proxy_command`: вектор с путём к `onlyterm-mux-server.exe` и флагом `--single-pane`
- `connect_automatically: false`, `no_serve_automatically: true`: не создаём Unix-сокет, используем stdin/stdout
- `read_timeout`/`write_timeout`: 60 секунд

Важно: GUI сразу же регистрирует домен в Mux через `mux.add_domain(&domain)`.

### Передача параметров в хостинг-процесс

Желаемая оболочка, каталог запуска (cwd) и приоритет передаются не через RPC-вызов, а через CLI-аргументы:

- `--cwd <directory>`: рабочий каталог для оболочки
- `--priority <name>`: класс приоритета процесса (Idle/BelowNormal/Normal/AboveNormal/High/Realtime)
- `--supervise-pid <pid>`: PID GUI-процесса для сторожа смерти родителя
- После `--` следуют аргументы самой оболочки (например, `cmd.exe` или `powershell.exe`)

### Защита от дубликатного спавна: `pending_single_pane_spawns`

Холодный запуск процесса занимает несколько секунд, и пользователь, не увидев отклика, вполне может нажать «новая вкладка» ещё раз. Раньше каждый такой клик создавал собственный хостинг-процесс, и они оставались висеть осиротевшими.

Защита реализована через `pending_single_pane_spawns()` — статический `Mutex<HashSet<MuxWindowId>>`. Правило: один in-flight спавн на исходное окно. Повторный запрос для того же окна тихо отбрасывается (`return Ok(())`).

`PendingSpawnGuard` реализует `Drop` и удаляет window_id из множества при завершении функции (успех или ошибка), освобождая окно для следующего спавна.

### Хостинг-процесс: `run_single_pane_mode` в mux-server

Ребёнок запускается как `onlyterm-mux-server.exe --single-pane` и сразу входит в `run_single_pane_mode`. Этот режим:

1. Принимает inherited stdin/stdout как поток mux-протокола (эмуляция Unix-сокета на Windows)
2. Спавнит свой единственный пейн самостоятельно при старте (см. `async_run_single_pane`)
3. Завершается, когда либо пейн завершается, либо мукс-клиент отключается

### Ключевой non-obvious факт: пейн уже существует при attach

Хостинг-процесс создаёт свою единственную панель сам, при старте: это не RPC-вызов от GUI, а локальное создание PTY и запуск оболочки внутри самого ребёнка.

**GUI не должен выдавать RPC-вызов spawn после attach!** Если бы это произошло, создавался бы второй пейн (и, в ранней реализации, отдельное окно). Вместо этого `client_domain.attach_with_spinner()` материализует уже существующий пейн как вкладку.

Почему это важно: по плану (см. `docs/plans/2026-08-13-per-tab-process-elevated-admin-tab.md:449-452`) изначально предполагалось, что GUI будет вызывать `SpawnV2`, но это создало бы второй пейн. Решение было найдено через live-тестирование: пейн создаётся самим ребёнком, а GUI только материализует его.

### WSAStartup: инициализация Winsock

На Windows эмуляция `socketpair()` на loopback требует инициализации Winsock. Daemon-режим получает это "бесплатно", потому что `filedescriptor::socketpair()` вызывает `WSAStartup` в родителе, но инициализация — per-process, не наследуется через хэндл.

Single-pane ребёнок никогда не вызывает `socketpair()` сам (он только наследует уже созданный хэндл), поэтому ему нужна явная инициализация: `init_winsock()` вызывает `WSAStartup` через `std::sync::Once`.

Без этого первый реальный socket I/O (внутри `dispatch::process`) падает с "Either the application has not called WSAStartup, or WSAStartup failed" (os error 10093).

### Attach: материализация пейна как вкладки

`spawn_single_pane_tab` вызывает `client_domain.attach_with_spinner(window_id)`. Это:

1. Запускает хостинг-процесс через `proxy_command`
2. Устанавливает соединение по mux-протоколу
3. Материализует пред-спавненный пейн как вкладку в указанном окне
4. Показывает тихий спиннер вместо сырого лога подключения

Если `window_id` указан, код ищет пейн через `mux.iter_panes()` и устанавливает конфигурацию терминала: `pane.set_config(term_config)`.

## Админская вкладка: почему тот же путь не работает

Админская вкладка запускается через `spawn_elevated_single_pane_tab` в `crates/wezterm-gui/src/spawn.rs`. Путь отличается фундаментально.

### Проблема: `ShellExecuteExW("runas")` не поддерживает наследование хэндлов

`CreateProcess` — единственный API, принимающий хэндл ConPTY через `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, но он не умеет запрос элевации. `ShellExecuteExW("runas")` — единственный штатный способ показать UAC, но не принимает произвольные хэндлы для наследования.

Реальный вызов `CreateProcess` с elevated-правами делает служба Application Information после UAC-консента, а не вызывающий процесс — нет таблицы хэндлов, которую можно было бы спроецировать в ребёнка.

Следствие: обычный `proxy_command`/`socketpair()` транспорт, который использует обычная вкладка, здесь недоступен.

### Решение: WebSocket-рандеву (reverse connection)

GUI связывает loopback-слушателя на `127.0.0.1:0`, генерирует токен (64 символа base58, ~375 бит) и передаёт порт+токен ребёнку CLI-аргументами:

```
--single-pane --connect-ws-port <port> --token <token> --supervise-pid <pid>
```

Ребёнок подключается обратно к GUI по WebSocket, предъявляя токен в заголовке `X-OnlyTerm-Token`. Слой WebSocket (tungstenite) затем бриджится на обычный `filedescriptor::socketpair()` через фоновый pump-поток, и существующая mux-машинерия (`dispatch::process`) работает без изменений.

Подробнее: `crates/wezterm-elevated-transport/src/lib.rs`.

### ShellExecuteExW("runas"): блокирующий UAC-пропт

`spawn_elevated_single_pane` в `crates/wezterm-gui/src/elevate.rs`:

1. Связывает `RendezvousListener::bind()` — открывает порт и генерирует токен
2. Формирует командную строку через `construct_single_pane_command_line`
3. Вызывает `ShellExecuteExW` с `lpVerb = "runas"`, `fMask = SEE_MASK_NOCLOSEPROCESS`, `nShow = SW_HIDE`
4. Ждёт подключения ребёнка через `listener.accept(deadline, child_exited)`

**Критично:** этот путь должен запускаться на реальном OS-потоке через `spawn_into_new_thread`, а не на GUI-потоке. `ShellExecuteExW("runas")` блокирует, пока пользователь отвечает на UAC-пропт, и cooperative executor GUI замёрз бы.

### Защита от нескольких UAC-проптов

`spawn_elevated_single_pane_tab` использует тот же `pending_single_pane_spawns()` механизм, что и обычная вкладка. Если для того же окна уже есть in-flight спавн, повторный запрос тихо отбрасывается.

Иначе нетерпеливые клики обернулись бы чередой запросов UAC подряд.

### Attach после WebSocket-подключения

После успешного подключения GUI создаёт `ClientDomain` (теперь без `proxy_command`, потому что поток уже существует), регистрирует его и вызывает `attach_stream_with_spinner(stream)`.

Пейн создаётся именно в этот момент (не при старте ребёнка, как в обычном пути), поэтому код сразу же ищет его через `mux.iter_panes()` и устанавливает конфигурацию.

### Флаг `set_elevated(true)`: индикатор админской вкладки

После attach код находит таб по pane_id и устанавливает флаг: `tab.set_elevated(true)`. Именно это заставляет таббар рисовать индикатор администратора (border цвета текста вкладки — `fancy_tab_bar.rs`).

Без этого вызова `Tab::is_elevated` всегда возвращает `false`, и индикатор никогда не появляется.

## Время жизни хостинг-процессов

### Обычные дети: Job Object с KILL_ON_JOB_CLOSE

`crates/wezterm-client/src/client/windows_job.rs` реализует `assign_to_kill_on_close_job(child, process_name)`:

1. Создаёт Job Object через `CreateJobObjectW`
2. Устанавливает `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` через `SetInformationJobObject`
3. Назначает ребёнка в job через `AssignProcessToJobObject`
4. Возвращает non-inheritable хэндл job как `OwnedHandle`

Когда закрывается последний хэндл к job — потому что GUI завершился или закрылась вкладка, — ядро принудительно убивает все процессы внутри. Это срабатывает и тогда, когда GUI снимают через `TerminateProcess`, то есть без единой строки пользовательского кода на выходе.

**Почему по одному job на ребёнка, а не один общий:**

1. **Время жизни.** Хэндл привязан к конкретному соединению, то есть к конкретной вкладке. Закрылась вкладка — хэндл дропнулся, job закрылся, умер ровно этот ребёнок. Общий job потребовал бы считать, сколько детей в нём ещё живо, и решать, когда его закрывать.
2. **Изоляция отказов.** Если один ребёнок сломается так, что повредит состояние своего job, остальных это не заденет.

### Elevated дети: сторож смерти родителя через `--supervise-pid`

Job Object не может пересекать границу целостности: medium-integrity родитель не может открыть high-integrity ребёнка с нужными правами.

Решение: обратное направление. Elevated ребёнок может открыть хэндл к lower-integrity родителю и ждать его завершения.

`spawn_parent_watcher` в `crates/wezterm-mux-server/src/main.rs`:

1. Вызывается для всех детей, которым передан `--supervise-pid` — и обычных, и поднятых
2. Открывает хэндл через `OpenProcess(SYNCHRONIZE, false, parent_pid)` **сразу**, на вызывающем потоке, ещё до создания потока-сторожа
3. Если `OpenProcess` не удался или родитель уже мёртв — ребёнок завершается немедленно
4. Создаёт поток, который встаёт на `WaitForSingleObject(h_parent, INFINITE)` и по `WAIT_OBJECT_0` завершает процесс

**Почему хэндл открывается сразу, а не в самом потоке.**

Windows переиспользует PID. Если отложить разрешение PID хотя бы на момент запуска потока, к этому времени номер может уже принадлежать другому процессу — и сторож будет ждать смерти постороннего. Открытие хэндла в момент запуска фиксирует ссылку именно на того родителя, который нас породил.

**Почему отдельный поток.**

Весь смысл сторожа — пережить заклинивший главный цикл. Если асинхронный исполнитель заблокирован или мёртв, этот поток всё равно доведёт дело до конца. Поэтому он намеренно не разделяет состояние с главным циклом: открыл хэндл и ждёт, больше ничего.

### `--supervise-pid` получают и обычные дети

Не только поднятые: `spawn.rs:110-112` передаёт флаг всем. Для обычного ребёнка это дублирует Job Object на случай, если тот не создался — `assign_to_kill_on_close_job` в такой ситуации возвращает `None` и лишь пишет предупреждение, а спавн продолжается. То есть основной механизм здесь Job Object, а сторож — подстраховка.

## Параметры вкладки из `--start-conf`

`crates/config/src/start_conf.rs` определяет `StartupLayout` и `StartupTab`. Разрешение работает по правилу "tab wins":

- `shell`: вкладка перекрывает layout, layout перекрывает `default_prog`
- `priority`: вкладка перекрывает layout, layout fallback на `Normal`
- `admin`: вкладка перекрывает layout, layout fallback на `false`

`StartupLayout::tab_options(&self, tab: &StartupTab)` возвращает `ResolvedTabOptions` с тремя полями: `shell: Option<Shell>`, `priority: ProcessPriority`, `admin: bool`.

Относительные пути `root_dir` разрешаются относительно каталога самого файла раскладки, а не рабочего каталога процесса. Благодаря этому файл раскладки можно хранить в репозитории и он будет работать у всех одинаково.

## Cleanup домена при закрытии вкладки

`ClientDomain::perform_detach` в `crates/wezterm-client/src/domain/mod.rs`:

1. Очищает внутреннее состояние: `self.inner.lock().unwrap().take()`
2. Удаляет домен из registration maps: `mux.remove_domain(&domain)`
3. Уведомляет mux: `mux.domain_was_detached(self.local_domain_id)`

Критично: `remove_domain` вызывается **до** `domain_was_detached`, потому что последняя функция может дропать ссылки на домен.

## Соотношение с планом

`docs/plans/2026-08-13-per-tab-process-elevated-admin-tab.md` — документ **более ранний**, чем код. Там, где он говорит о Job Object, `Mux::remove_domain` или стороже родителя как о задачах Phase D, это не расхождение: Phase D их и реализовала. Читать план как спецификацию текущего поведения не следует, для этого есть настоящий документ.

Одна деталь плана в коде расширена: `--supervise-pid` получают **все** хостинг-дети, не только поднятые (`spawn.rs:110-112`). Для обычных детей это дублирует Job Object на случай, если его создание не удалось — `assign_to_kill_on_close_job` возвращает `None` и лишь пишет предупреждение, спавн при этом продолжается.

## Что проверено живым запуском

Оба механизма завершения проверены на реальных процессах 2026-08-14, снятием GUI через `TerminateProcess` (то есть без единой строки пользовательского кода при выходе — так же, как это делает диспетчер задач):

- **Обычные дети, Job Object.** Окно с шестью хостинг-процессами; после снятия GUI все шесть исчезли в пределах трёх секунд, выживших ноль.
- **Поднятый ребёнок, сторож родителя.** Отдельный прогон с открытой админской вкладкой; ребёнок исчез вместе с GUI за те же три секунды. Именно этот случай Job Object закрыть не может — он не пересекает границу целостности.

Соответствие вкладок и процессов — один к одному, осиротевших процессов не остаётся. Двойная синхронизация домена в отладочном логе (два `ListPanes` подряд на один домен) — безобидная пересинхронизация, а не вторая вкладка; на это легко купиться при чтении лога.

Замеры цены (debug-сборка, поэтому не пользовательские цифры): около 46 МБ working set на хостинг-процесс и около 750 мс от старта процесса до готовой панели, разброс 717–773 мс на шести замерах.

### Матрица оболочка × приоритет

Прогнана раскладкой из девяти вкладок через `--start-conf`. Совпало всё:

| оболочка | приоритет | получен |
|---|---|---|
| `cmd` | idle | Idle |
| `cmd` | below_normal | BelowNormal |
| `cmd` | normal | Normal |
| `cmd` | above_normal | AboveNormal |
| `cmd` | high | High |
| `powershell` | normal | Normal |
| `powershell` | high | High |
| `bash` | normal | Normal |
| `wsl` | normal | Normal |

Что осталось **не** покрыто, и это важнее списка покрытого:

- **`realtime` не проверялся намеренно.** `REALTIME_PRIORITY_CLASS` способен задушить обработку ввода на всей машине; ради строчки в таблице рабочий стол не вешают.
- **Админские сочетания не прогонялись матрицей** — каждое требует живого согласия UAC, то есть человека у клавиатуры. Проверены отдельно и вручную: админская вкладка поднимается, получает высокий уровень целостности и рисует свою рамку.
- **Вкладки из `--start-conf` не получают изоляции вовсе**, даже при включённом `per_tab_process_isolation`: неадминская ветка `spawn_startup_layout` спавнит по локальному домену напрямую. Одно и то же окно может держать изолированные вкладки, открытые руками, и неизолированные из раскладки.

Отдельно стоит знать, как читается приоритет при проверке. Класс задаётся **только процессу оболочки** — `crates/pty/src/win/pseudocon.rs`, флаги `CreateProcessW`. Сопутствующий `OpenConsole.exe` порождает сама `CreatePseudoConsole` внутри conpty.dll, этот код его не создаёт, и класс он наследует от GUI. Поэтому в списке процессов оболочки будут с запрошенными классами, а хосты консоли — с классом самого GUI, и это норма, а не рассинхрон.

### Оговорка к цифрам выше

Все замеры в этом документе сняты с дерева процессов, работавшего с приоритетом **Idle**: их снимал агент, а его оболочка — фоновая и низкоприоритетная, что наследуется всем запущенным из неё. На незагруженной машине разница невелика, но это **нижняя оценка**, а не нейтральное измерение. Прежде чем приводить эти числа как пользовательские, их следует переснять при обычном приоритете.

Где вызывается постановка в Job Object — `crates/wezterm-client/src/client/conn.rs`, ветка `UnixTarget::Proxy`, сразу после `cmd.spawn()`; полученный хендл возвращается наверх и должен жить столько же, сколько соединение с ребёнком, потому что закрытие хендла и есть сигнал ядру убить процесс.
