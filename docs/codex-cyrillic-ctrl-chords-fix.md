# Спочинное: вывод «починить со стороны терминала нельзя» опровергнут

Дополнение к `codex-cyrillic-ctrl-chords.md` от 2026-08-16. Разбор выше установил,
что Codex перевыводит символ из `wVirtualKeyCode` через `ToUnicodeEx`, и на этом
заключил, что терминал бессилен. Ниже — найденная точная логика потребителя
(исходник, не гипотеза) и вытекающий из неё фикс на нашей стороне. Код не трогал;
этот файл — руководство к правке.

## Источник: форк crossterm, на который патчится Codex

`codex-rs/Cargo.toml` (main на момент проверки) патчит crossterm на собственный
форк OpenAI:

```
[patch.crates-io]
crossterm = { git = "https://github.com/openai-oss-forks/crossterm",
              rev = "45fecb9508105988f42fe6ff0441783ed3717f92" }
```

Файл `src/event/sys/windows/parse.rs` этого ревизии, функция разбора
`KEY_EVENT_RECORD` → `KeyEvent` (перевод из исходника, близкий к дословному):

1. Сначала запись сопоставляется по **виртуальному коду**: ESC, Enter, Tab,
   F-клавиши, модификаторы и пр. дают `KeyCode::Enter`/`Tab`/… **без всякого
   `ToUnicodeEx`** — они раскладко-независимы по построению.
2. Если `uChar.UnicodeChar` записи **≥ 0x20** (печатный символ) — он берётся
   **напрямую из записи**: `KeyCode::Char(from_u32(uChar))`. `ToUnicodeEx` не
   вызывается.
3. Если `uChar` попадает в **0x00..=0x1F** (контрольные коды; сюда же относится
   0 на key-up) и vk не распознан в п.1 — символ **перевыводится**: `ToUnicodeEx`
   с *обнулённым* 256-байтным состоянием клавиатуры (нужен базовый символ, а не
   контрольный код), vk/sc из записи, layout от `GetKeyboardLayout` потока
   foreground-окна, флаг 4 («не менять состояние ядра»). Возврат < 1 (нет
   отображения / dead key) → `None`, клавиша теряется.

Именно п.3 убивает чорды под кириллицей: для Ctrl+J запись несёт `uChar=0x0A`
(контрольный код) → перевывод `VK 0x4A` под ЙЦУКЕН → `Char('о') + CTRL` →
привязка `ctrl+j` не находится. Для Ctrl+C аналогично `0x03` → `'с'`.

Это же объясняет, почему **Shift+Enter работает при любой раскладке**: OnlyTerm
отдаёт его как `SendEnterOrNewline(SHIFT)` → запись `vk=VK_RETURN, uChar=0x0D`,
а VK_RETURN распознаётся в п.1 раскладко-независимо.

## Следствие: рычаг у терминала есть

Перевывод включается **только** контрольным значением `uChar`. Если в поле
`UnicodeChar` записи для CTRL-чорда положить **печатную латинскую букву**
(`0x6A` = `j`, `0x63` = `c`) вместо контрольного кода, сработает п.2 — потребитель
возьмёт её из записи как есть, `ToUnicodeEx` не вызывается, привязка `ctrl+j`
матчится. Под латиницей ничего менять не нужно — там перевывод и так даёт ту же
букву, байты остаются идентичными сегодняшним.

Пример: под русской раскладкой Ctrl+J должен уходить как

```
было:  ESC[74;36;10;1;8;1_     (uni=0x0A → потребитель перевыводит → 'о')
стало: ESC[74;36;106;1;8;1_    (uni=0x6A → потребитель берёт 'j' напрямую)
```

## Условие применимости (зеркалирование алгоритма потребителя)

Подставлять букву нужно **только когда перевывод расходится** с ожидаемой буквой,
иначе под латиницей и совместимыми раскладками (DE/FR и т.п.) изменится то, что
работает. Условие проверяется самим терминалом тем же вызовом, что делает
потребитель:

```
rederived = ToUnicodeEx(vk, sc, state=[0;256], флаг 4, GetKeyboardLayout(0))
заменять, если rederived != Some(намеренная строчная буква)
```

`GetKeyboardLayout(0)` нашего UI-потока равен layout потока foreground-окна
(foreground — наше окно во время нажатия), т.е. зеркалирование точное. `None`
(нет отображения / dead key) — тоже несоответствие: потребитель теряет клавишу,
подстановка буквы её возвращает.

Замечание про key-up: запись отпускания несёт `uChar=0` и перевыводится в `'о'`
в любом случае — но привязки у Codex срабатывают по Press, это безвредно.

## Границы воздействия (почему это безопасно)

- Правка живёт **только в кодировщике win32-input-mode**, т.е. затрагивает
  исключительно панели, где само приложение запросило DECSET 9001. Codex
  запрашивает (подтверждено захватом; см. `SendEnterOrNewline` комментарий в
  `actions.rs`). Claude Code (node/libuv) и cmd.exe режим не запрашивают — их
  путь (legacy-байты) не меняется вовсе.
- Приложений, читающих записи с 9001, немного (crossterm-подобные; PSReadLine).
  PSReadLine матчит чорды по VK, а Ctrl+C обрабатывает сам как chord — смена
  `uChar` с 0x03 на 'c' для него неощутима.
- Контрольный код `uChar` заведомо важен потребителям, берущим поле буквально
  (libuv). Они режим 9001 не запрашивают — см. выше.
- OS-сигнал по Ctrl+C (0x03) под кириллицей в 9001-панелях пропадает, но Codex
  и так получает Ctrl+C привязкой, а не сигналом (сейчас под кириллицей он не
  получает вообще ничего — строгого регресса нет).
- Единственный проигравший: приложение, сознательно повесившее привязку на
  **Ctrl+кириллическая буква** той же физической клавиши в 9001-режиме. Не
  обнаружено ни одного известного примера.

## План правки (места в дереве)

1. **`crates/window/src/os/windows/keyboard_layout.rs`** — добавить свободную
   функцию (и сделать модуль `pub` в `os/windows/mod.rs`, сейчас `mod`):

   ```rust
   pub fn consumer_rederived_char(vk: u32, scan_code: u32) -> Option<char> {
       let state = [0u8; 256];
       let mut out = [0u16; 16];
       let ret = unsafe {
           ToUnicodeEx(vk, scan_code, state.as_ptr(), out.as_mut_ptr(),
                       out.len() as i32, 4, GetKeyboardLayout(0))
       };
       (ret >= 1).then(|| std::char::from_u32(out[0] as u32)).flatten()
   }
   ```

   `ToUnicodeEx` в winapi присутствует (проверено по docs.rs; фича `winuser` в
   `window/Cargo.toml` уже включена). Требования: только UI-поток (читает
   thread-global состояние клавиатуры; флаг 4 не меняет его, но консультируется) —
   тот же контракт, что у `KeyboardLayoutInfo`; `// SAFETY:`-комментарий
   обязателен. Вызывается из `encode_win32_input`, т.е. всегда на UI-потоке.

2. **`crates/onlyterm-input-types/src/key_event.rs`**, `encode_win32_input_mode`
   (строки ~146–274):
   - развернуть в пару: нульаргументная обёртка (все нынешние вызовы — тесты в
     `inputmap.rs`/`lib.rs` — не меняются) + `encode_win32_input_mode_with_ctrl_uni(
     ctrl_uni: Option<char>)` с текущим телом;
   - в ветке CTRL (сейчас `ctrl_mapping(*c).map(..).unwrap_or(*c as u32)`):
     при `Some(override)` класть его в поле uni;
   - добавить чистую (тестируемую без Win32) функцию решения, например методом:

   ```rust
   pub fn win32_ctrl_uni_fallback(
       &self,
       rederive: impl FnOnce(u32, u32) -> Option<char>,
   ) -> Option<char> {
       if !self.modifiers.contains(Modifiers::CTRL) { return None; }
       let KeyCode::Char(c) = &self.key else { return None };
       if !c.is_ascii_graphic() { return None; }   // '\r' (Enter) и прочее не трогаем
       let raw = self.raw.as_ref()?;
       let intended = c.to_ascii_lowercase();
       (rederive(raw.raw_code, raw.scan_code) != Some(intended)).then_some(intended)
   }
   ```

   Замыкание держит Win32-вызов ленивым: для не-CTRL клавиш раскладка вообще не
   опрашивается. Метод под `#[cfg(windows)]` (поле `raw.scan_code` тоже
   `#[cfg(windows)]`, см. `raw_key_event.rs`).

3. **`crates/onlyterm-gui/src/termwindow/keyevent.rs`**, `encode_win32_input`
   (строка ~238) — единственный продакшн-вызов кодировщика:

   ```rust
   let ctrl_uni = key.win32_ctrl_uni_fallback(|vk, sc| {
       ::window::keyboard_layout::consumer_rederived_char(vk, sc)
   });
   // log::debug! при Some — автоповтор Ctrl даёт десятки записей в секунду,
   // info зальёт RingLog (см. комментарий у is_ctrl_chord_of_interest)
   key.encode_win32_input_mode_with_ctrl_uni(ctrl_uni)
   ```

   Этого достаточно, чтобы покрыть все три чорда из отчёта, потому что все они
   сходятся в эту точку:
   - **Ctrl+J** (реальное нажатие, без пользовательской привязки) — passthrough
     в `key_event_impl` → `encode_win32_input`;
   - **Ctrl+Enter** — перепривязан на синтетический `SendChar(CTRL, 'j')`
     (`inputmap.rs`, тест `ctrl_enter_sends_newline`) → `encode_via_negotiated_protocol`
     → `encode_win32_input`;
   - **Ctrl+C** — `CopySelectionOrInterrupt` → `encode_via_negotiated_protocol`
     → `encode_win32_input`.

   Vk/sc для синтетики уже заполнены фиксированной таблицей
   `PhysKeyCode::to_win32_key_codes` (J = 0x4A/0x24, C = 0x43/0x2E), так что
   зеркалирование работает и для них.

4. **Тесты** — в тестовый модуль `onlyterm-input-types/src/lib.rs`, рядом с
   существующим хелпером `win32_input_mode_uni_char` (стиль уже готов):
   - решение: `rederive → Some('о')` даёт `Some('j')`; `Some('j')` даёт `None`
     (латиница — байты не меняются); `None` даёт `Some('j')`; `Char('\r')+CTRL`
     и `Char('j')` без CTRL дают `None`; `'J'` нормализуется в `'j'`;
   - кодировка: с `Some('j')` последовательность несёт `uni=106`, с `None` —
     `uni=10` (побайтово сегодняшнее поведение).

## Сверка с «открытым» из старого разбора

- «Codex не использует поле `UnicodeChar`» — уточнено: не использует его **лишь
  когда оно контрольное** (0x00..=0x1F); печатное берёт напрямую. Именно эта
  оговорка и делает фикс возможным.
- «Подставить vk, дающий `j` под ЙЦУКЕН, невозможно» — верно и не нужно:
  подставляется не vk, а печатный `uChar`.
- Обходной путь №1 (раздельная раскладка на приложение) больше не требуется для
  этого дефекта; отчёт в upstream (№2) остаётся полезным — потребитель не должен
  перевыводить то, что отправитель уже разрешил.
