# Ctrl+J / Ctrl+Enter / Ctrl+C не работают в Codex CLI под кириллической раскладкой

Разбор от 2026-08-16. Дефект **не в OnlyTerm**; документ объясняет, почему, и что
измерялось, чтобы это установить.

## Симптом

При активной русской раскладке в панели с Codex CLI перестают работать:

- `Ctrl+J` — вставка перевода строки
- `Ctrl+Enter` — то же самое (в OnlyTerm привязан к чорду Ctrl+J, коммит `6f9602e6d`)
- `Ctrl+C` — прерывание

Под латинской раскладкой те же чорды работают. В **Claude Code** они работают при любой
раскладке, в том же окне OnlyTerm. **Windows Terminal воспроизводит тот же отказ**, то есть
он не специфичен для OnlyTerm.

## Причина

`codex.exe` — нативный бинарь (Rust), запускаемый обёрткой `codex.js`. В его таблице импорта
присутствуют, рядом с прочими импортами `USER32.dll`:

```
ReadConsoleInputW      читает консоль записями INPUT_RECORD, а не байтовым потоком
GetKeyboardLayout      запрашивает активную раскладку
ToUnicodeEx            переводит виртуальную клавишу в символ ПО ЭТОЙ раскладке
```

Codex не использует поле `UnicodeChar` пришедшей записи. Он берёт `wVirtualKeyCode` и
выводит символ сам, через `ToUnicodeEx` с раскладкой от `GetKeyboardLayout`. Под ЙЦУКЕН:

| Виртуальная клавиша | Латинская раскладка | Кириллическая |
|---|---|---|
| `0x4A` (VK_J) | `j` | `о` |
| `0x43` (VK_C) | `c` | `с` |

Дальше Codex ищет в своих привязках `Ctrl+о` и `Ctrl+с`, не находит и молчит.

Терминал на это повлиять не может: `wVirtualKeyCode` обязан быть настоящим кодом нажатой
физической клавиши, и Windows Terminal посылает ровно тот же `0x4A`. Символ, который Codex
переводит заново, уже лежит в той же записи корректным — `ToUnicodeEx` здесь просто лишний.

### Остаточная неопределённость

Импорты доказаны, но статически: дизассемблирования не делалось, поэтому «эти функции
вызываются именно на пути разбора клавиш» — вывод из совокупности признаков, а не прямое
наблюдение. Все измерения ниже с ним согласуются, ни одно не противоречит, и никакой другой
механизм оставшиеся факты не объясняет. Но формально это сильная гипотеза, а не
доказательство.

## Измерения

Все — на машине пользователя, 2026-08-16, сборка OnlyTerm с диагностикой (см. ниже).

### 1. Что отправляет OnlyTerm

Из журналов (`onlyterm-gui.exe-log-27684.txt`), с отметками смены раскладки:

```
08:28:12.660  layout changed to langid=0x0419   (ru-RU)
08:28:14      Ctrl+J  -> ESC[74;36;10;1;8;1_    (down)  / ESC[74;36;10;0;8;1_ (up)
08:28:16      Ctrl+C  -> ESC[67;46;3;1;8;1_     (down)  / ESC[67;46;3;0;8;1_  (up)
08:28:18.326  layout changed to langid=0x0409   (en-US)
08:28:19      Ctrl+J  -> ESC[74;36;10;1;8;1_    (побайтово то же)
08:28:21      Ctrl+C  -> ESC[67;46;3;1;8;1_     (побайтово то же)
```

Поля: `Vk;Sc;UnicodeChar;KeyDown;ControlKeyState;RepeatCount`. То есть `74`=`0x4A`=VK_J,
`36`=`0x24` скан-код, `10`=`0x0A` управляющий код Ctrl+J, `8`=LEFT_CTRL_PRESSED.

**Разницы между раскладками нет ни в одном байте.** Поиск привязки в обоих случаях
срабатывает физическим проходом (`pass=Yes`, `Physical(J)`), а не символьным.

### 2. Что доходит до потомка — байтовый поток

`docs/keyprobe.sh` запрашивает win32-input-mode сам (DECSET 9001), как Codex, и печатает
всё пришедшее через `cat -v`:

```
(русская)   ^[[74;36;10;1;8;1_^[[74;36;10;0;8;1_^[[67;46;3;1;8;1_^[[67;46;3;0;8;1_
(английская)^[[74;36;10;1;8;1_^[[74;36;10;0;8;1_^[[67;46;3;1;8;1_^[[67;46;3;0;8;1_
```

Идентично. ConPTY байтовый поток не портит.

**Это измерение было проведено первым и оказалось не тем.** Приложение, читающее консоль
через `ReadConsoleInputW`, этих байтов не видит вовсе — оно получает записи, которые conhost
собирает заново. Канал пришлось перемерить.

### 3. Что доходит до потомка — записи INPUT_RECORD

`docs/recprobe.ps1` читает `$host.UI.RawUI.ReadKey`, а это поля `KEY_EVENT_RECORD` как есть.
Под **русской** раскладкой:

```
vk=17 (0x11) ch=0  (0x0000) state=LeftCtrlPressed     <- сам Ctrl
vk=74 (0x4A) ch=10 (0x000A) state=LeftCtrlPressed     <- Ctrl+J
vk=74 (0x4A) ch=10 (0x000A) state=LeftCtrlPressed     <- Ctrl+Enter
```

Запись корректна: `UnicodeChar` = `0x0A`. **conhost её не портит.** Символ, который Codex
выводит заново, уже лежит здесь правильным.

Там же видно, что раскладка переключается Alt+Shift (`vk=18`, затем `vk=16`).

### 4. Прерывание на уровне ОС работает под кириллицей

В том же зонде `Ctrl+C` завершил PowerShell — под русской раскладкой, несмотря на
`[Console]::TreatControlCAsInput = $true`. Значит «Ctrl+C не работает в Codex» — это не сбой
доставки: сигнал доходит и исполняется, Codex его не распознаёт сам.

### 5. Голый управляющий байт вместо протокола

Запуск с `--config allow_win32_input_mode=false`: OnlyTerm шлёт один байт (`0x0A` на Ctrl+J,
`0x03` на Ctrl+C) вместо структурной записи.

| Раскладка | Ctrl+C | Ctrl+J / Ctrl+Enter |
|---|---|---|
| английская | работает | **сломались** |
| русская | не работает | не работает |

`0x03` даёт настоящее прерывание от ОС и потому проходит. `0x0A` превращается в запись без
виртуальной клавиши — Codex выводить символ не из чего, и чорд теряется даже под латиницей.
Путь тупиковый: он ломает то, что работало.

### 6. Конфиг пользователя

В `.onlyterm.ktav` блок `keys:` не содержит ни `c`, ни `j` — переопределений нет. Заданы
только `phys:v`, `phys:t`, `l`/`L`/`phys:l`, `phys:f`, `phys:1..9`, `Tab`, `=`, `-`, `phys:0`.

## Что исключено

| Подозреваемый | Чем исключён |
|---|---|
| Поиск привязки в OnlyTerm | измерение 1: совпадает физическим проходом при обеих раскладках |
| Кодирование в OnlyTerm | измерение 1: байты идентичны и корректны |
| ConPTY, байтовый канал | измерение 2 |
| conhost, канал записей | измерение 3 |
| Доставка прерывания | измерение 4 |
| Конфиг пользователя | измерение 6 |
| Специфика OnlyTerm | Windows Terminal воспроизводит |

Отдельно: пять мест в цепочке OnlyTerm были сделаны layout-независимыми более ранними
правками, и все они работают штатно —
`window.rs` (`prefer_physical_for_binding`), `os/windows/keycodes.rs` (`vkey_to_phys`),
`key_code.rs` (`KeyCode::to_phys`), `phys_key_code.rs` (`to_win32_key_codes`),
`commands/command_def.rs` (`push_with_phys_fallback`).

## Почему нельзя починить со стороны терминала

Предложение «под кириллицей подставлять английский сигнал» уже реализовано: мы отправляем
английские `vk`, скан-код и управляющий код. Codex английский `vk` получает и **сам**
переводит его в кириллицу.

Подставить `vk`, дающий `j` под ЙЦУКЕН, невозможно — такой клавиши на этой раскладке нет.
Это уже проверялось при работе над `6f9602e6d`: `VkKeyScanW('j')` под русской раскладкой
проваливается, поэтому там и появилась фиксированная таблица `to_win32_key_codes`.

Отключение win32-режима отпадает по измерению 5.

## Исход: починено со стороны терминала

Вывод «терминал бессилен», сделанный выше, **опровергнут**. Разбор потребителя
(`codex-cyrillic-ctrl-chords-fix.md`) показал, что перевывод через `ToUnicodeEx`
включается **только когда `UnicodeChar` записи меньше `0x20`**; печатный символ берётся
из записи напрямую. Значит рычаг есть: положить в это поле саму букву (`0x6A` «j»,
`0x63` «c») вместо управляющего кода.

Проверено вживую: с буквой Codex принимает Ctrl+J, Ctrl+Enter и Ctrl+C при русской
раскладке; с управляющим кодом — нет. Глобально так делать нельзя, и это тоже измерено:
Claude Code читает поле дословно и начинает печатать литеральную «j».

Реализация — `Config::win32_input_ctrl_letter_as_char_processes`, по умолчанию
`["codex.exe", "codex"]`. Подмена включается только для панели, в дереве процессов
которой есть такой исполняемый файл, и снимается сама при его завершении.

Две ошибки, допущенные при первой попытке, стоят упоминания, потому что обе выглядели
безобидно:

- **Проверялся передний процесс панели.** Он резолвится в `node_repl.exe`: Codex идёт
  цепочкой `codex.cmd` → node → `codex.exe`, а эвристика переднего процесса на Windows
  берёт самый молодой процесс в консоли. Правка была верной, а условие не срабатывало
  никогда. Теперь ищем по всему дереву — `Pane::get_process_tree_exe_names`.
- **Проверка выполнялась на каждое нажатие.** `encode_win32_input` вызывается для любой
  клавиши, дошедшей до сквозной передачи, а не только для чордов, так что обычный набор
  текста платил обходом дерева процессов. Ровно эту ошибку в этом дереве уже
  вычищали однажды из пути отрисовки (`bidi_process_override`). Теперь вопрос задаётся
  только при `Ctrl` + латинская буква.

Заплатка намеренно узкая. Правильное место починки — у потребителя: Gemini CLI, к
примеру, работает при любой раскладке именно потому, что доверяет присланному символу
и ничего не перевыводит.

## Обходные пути

1. **Раздельная раскладка на приложение** (без единой строки кода). Параметры → Время и
   язык → Ввод → Дополнительные параметры клавиатуры → «Позволить выбрать метод ввода для
   каждого окна приложения». Тогда переключение в окне OnlyTerm не меняет раскладку, которую
   видит процесс `codex.exe`. **Не проверено** — предлагается как первое к проверке.
2. **Дефект в Codex.** Материал этого документа достаточен для отчёта: Codex должен брать
   `UnicodeChar` из записи, а не выводить символ заново через `ToUnicodeEx`.
3. **Временное переключение раскладки системы на время чорда** — не рекомендуется:
   глобальный побочный эффект, гонка с переключениями пользователя, риск оставить систему в
   чужом состоянии.

## Диагностика, добавленная в ходе разбора

В рабочем дереве (на момент написания не закоммичено), всё под предикатом
`is_ctrl_chord_of_interest` — зажат CTRL и клавиша не модификатор, иначе `RingLog` пишет и
сбрасывает на диск каждую запись, а автоповтор Ctrl давал ~30 записей в секунду:

- `termwindow/keyevent.rs`, `raw_key_event_impl` — идентичность, отданная Windows:
  `key`, `phys_code`, `vk`, `sc`, модификаторы, кодировка панели;
- `termwindow/keyevent.rs`, `process_key` — прежний лог трёх «переводов строки» расширен на
  любой CTRL+символ, и показывает, какой проход сработал (`pass=Yes` физический,
  `pass=No` символьный);
- `termwindow/keyevent.rs`, `key_event_impl` — какой из трёх кодировщиков выбран при
  сквозной передаче и точные байты (раньше было под `trace`, то есть невидимо);
- `termwindow/actions.rs`, `CopySelectionOrInterrupt` — раньше не логировался вовсе;
- `window/src/os/windows/keyboard_layout.rs`, `update` — смена активной раскладки с
  `langid`. Срабатывает только при фактической смене, несколько записей за сеанс. Без неё
  журнал клавиатуры невозможно разделить на «работающую» и «отказную» половины: первая
  попытка дала шесть снимков чордов, неотличимых друг от друга.

Зонды: `docs/keyprobe.sh` (байтовый канал), `docs/recprobe.ps1` (канал записей).

Воспроизведение:

```
onlyterm-gui.exe start -- bash docs/keyprobe.sh
onlyterm-gui.exe --config exit_behavior=Hold start -- \
    powershell.exe -NoProfile -ExecutionPolicy Bypass -File docs/recprobe.ps1
onlyterm-gui.exe --config allow_win32_input_mode=false start
```
