# Модель безопасности хостинг-процессов (одна вкладка — один процесс)

Документ фиксирует итог security-ревью транспорта (Фаза E инициативы «на каждую
вкладку свой процесс»). Он существует ради одной цели: чтобы следующий, кто
займётся этим кодом, не перепроверял вслепую гипотезы, которые уже проверены
живым замером. Все цифры ниже — результат измерения на конкретной машине,
а не рассуждения о том, как Windows должна себя вести.

## От кого защищаемся

Модель нарушителя — **процесс того же пользователя со средней целостностью**
(обычное непривилегированное приложение в той же сессии). Именно этот случай
делает функцию «админская вкладка внутри обычного окна» опасной: если такой
процесс сумеет вклиниться в канал, он получит доступ к оболочке, поднятой через
UAC, — то есть повышение привилегий без запроса UAC.

Атакующий с правами администратора вне модели: он уже обладает тем, что мог бы
получить через этот канал. Атакующий-другой-пользователь вне модели: всё
взаимодействие идёт через loopback и объекты, принадлежащие текущему
пользователю.

## Два транспорта

Вкладки бывают двух видов, и каналы у них принципиально разные.

### Обычная вкладка — унаследованная пара сокетов

`crates/wezterm-client/src/client/conn.rs`, ветка `UnixTarget::Proxy`:
GUI создаёт `filedescriptor::socketpair()` и отдаёт один конец ребёнку как
stdin/stdout при спавне. Файлового объекта не создаётся вовсе.

Это и есть главный результат Фазы A. В findings Фазы A значилось, что ACL сокета
отсутствует полностью и любой процесс пользователя мог бы подключиться. Дыра
закрыта не заплаткой, а выбором транспорта: **у унаследованного хендла нет
ACL-поверхности, в которой можно ошибиться**. Подключиться к паре сокетов
снаружи нельзя — второй конец не существует нигде, кроме адресного
пространства порождённого ребёнка.

Отдельно: эмуляция `socketpair()` на Windows идёт через loopback-сокет, и там
есть окно, в которое чужой процесс мог бы успеть подключиться раньше
настоящего ребёнка. **Это уже закрыто** — `crates/filedescriptor/src/windows/socketpair.rs`
обменивается 16-байтным случайным токеном сразу после `accept()`, с общим
бюджетом 2 с и 250 мс на попытку; несовпадение даёт
`Error::SocketpairHandshake` («possible local port hijack attempt»).
`verify_handshake_token` покрыт юнит-тестами. Переделывать не нужно.

### Админская вкладка — WebSocket-рандеву

`crates/wezterm-elevated-transport/src/lib.rs`. Поднятый ребёнок не может
унаследовать хендл от непривилегированного родителя, поэтому направление
обратное: GUI открывает слушателя на `127.0.0.1:0`, генерирует токен и передаёт
порт с токеном ребёнку, а ребёнок подключается обратно и предъявляет токен в
заголовке `X-OnlyTerm-Token`.

Защита здесь четырёхслойная:

1. **Только loopback.** `TcpListener::bind("127.0.0.1:0")` — снаружи машины
   порт недоступен.
2. **Токен.** 64 символа base58, ~375 бит, из `getrandom` с отбраковкой
   (байты ≥ 232 отбрасываются, иначе `% 58` смещал бы распределение).
   Неверный токен получает 403, и слушатель продолжает ждать настоящего
   ребёнка, а не считает попытку фатальной.
3. **Слушатель живёт до первого подключения.** `RendezvousListener` — локальная
   переменная в `spawn_elevated_single_pane`; как только `accept` вернул поток,
   она дропается и порт закрывается. Даже добытый токен предъявить негде.
4. **Allow-list PDU.** `PduPolicy::ElevatedSinglePaneAllowList`
   (`crates/wezterm-mux-server-impl/src/sessionhandler/mod.rs`) пропускает
   только минимум для работы одной панели и отвергает `SpawnV2`, `SplitPane`,
   `MovePaneToNewTab`, `GetClientList`, работу со scrollback и управление
   workspace. Даже полностью захваченный канал не даёт запустить произвольный
   процесс с правами администратора.

## Замер: утекает ли токен через командную строку

Токен передаётся поднятому ребёнку аргументом командной строки —
`construct_single_pane_command_line` в `crates/wezterm-gui/src/elevate.rs`
формирует `--single-pane --connect-ws-port <port> --token <token> --supervise-pid <pid>`.

Это выглядит как утечка: командная строка процесса на Windows читается снаружи.
Гипотеза проверена живым прогоном — открыта админская вкладка, запросы сделаны
из обычной (не поднятой) сессии того же пользователя.

**Через WMI** (`Get-CimInstance Win32_Process`):

| Процесс | `CommandLine` |
|---|---|
| `onlyterm-gui.exe` (обычный, тот же пользователь) | виден полностью |
| `onlyterm-mux-server.exe` (поднятый) | пусто |

Контрольная строка здесь обязательна: без неё пустое поле можно было бы списать
на причуду WMI. Собственный GUI показывает командную строку целиком — значит
механизм работает, а упирается он именно в цель.

**Напрямую через `OpenProcess`:**

| Процесс | `PROCESS_QUERY_LIMITED_INFORMATION` | `PROCESS_QUERY_INFORMATION \| PROCESS_VM_READ` |
|---|---|---|
| `onlyterm-gui.exe` (обычный) | OK | OK |
| `onlyterm-mux-server.exe` (поднятый) | OK | **отказ, err=5 (ACCESS_DENIED)** |

Командная строка лежит в PEB, и чтобы её прочитать, нужен `PROCESS_VM_READ`.
Через границу целостности он закрыт. Отсюда и пустое поле в WMI: служба
олицетворяет вызывающего и получает тот же отказ.

**Вывод: токен наружу не виден.** Передача через argv в этой конфигурации
безопасна. Менять её на унаследованный хендл не требуется.

Условие, при котором вывод перестаёт действовать: если поднятый ребёнок когда-либо
начнёт запускаться *без* повышения (например, при отладке админского пути на
обычных правах) — тогда его командная строка станет читаемой любым процессом
пользователя. Тот, кто будет это менять, должен перечитать этот раздел.

## Осознанно оставлено без изменений

- **Сравнение токена не константно по времени.** `TokenCallback::on_request`
  сравнивает обычным `==`. Против одноразового токена в 375 бит, на loopback,
  в окне длиной в секунды, побайтовое восстановление по таймингу нереализуемо.
  Константное сравнение здесь было бы security theater, а не защитой.
- **Обычные вкладки работают под `PduPolicy::Unrestricted`.** Allow-list им не
  нужен: до их канала нельзя дотянуться, он существует только как
  унаследованный хендл. Введение allow-list и туда было бы защитой в глубину,
  но не закрывает никакого достижимого пути.

## Остаточный риск

Если в системе включена политика аудита создания процессов с командными
строками (событие 4688) либо работает Sysmon с аналогичной настройкой, токен
осядет в журнале безопасности. Читать этот журнал может только администратор —
то есть тот, кому канал и так ничего нового не даёт, — но токен при этом
попадает на диск и живёт дольше самого процесса. Повышения привилегий это не
даёт; отмечено для полноты картины.

## Смежное: время жизни, а не доступ

Фаза D добавила принудительную уборку хостинг-процессов — Job Object с
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` для обычных детей и сторож смерти родителя
для поднятых (Job Object не пересекает границу целостности, а поднятый ребёнок
открыть родителя с меньшей целостностью может). Это вопрос ресурсов и
предсказуемости, а не разграничения доступа, и здесь упомянуто только чтобы
не искали его в этом документе.
