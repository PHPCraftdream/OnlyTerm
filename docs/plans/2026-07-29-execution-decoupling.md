# План: развязка связности выполнения (изоляция зависаний, lock-free, async)

Дата: 2026-07-29. Задачи: **#218–#226**.

Цель, сформулированная пользователем: *«чтобы вкладка могла умереть одна при
зависании»*, не утаскивая за собой ни соседние вкладки, ни всё окно, ни —
что происходит сейчас — вообще все окна пользователя. Плюс: повысить
lock-free-работу, оценить перевод на асинхронность.

Этот план **дополняет** ранее выполненный unsafe-аудит (#202–#217), а не
заменяет его.

---

## 1. Почему сейчас виснет всё разом (проверено по коду)

Цепочка причин, каждое звено подтверждено чтением исходников:

1. **Все окна живут в одном процессе.** GUI-процесс публикует
   `gui-sock-{pid}` (`crates/wezterm-gui/src/main.rs:352`) и экспортирует
   `ONLYTERM_UNIX_SOCKET` в дочерние процессы
   (`crates/mux/src/domain.rs:506`). Всё, что пользователь запускает из
   OnlyTerm, подключается обратно к тому же `onlyterm-gui.exe`. Инцидент в
   этой сессии это подтвердил: один PID 5344 хостил все зависшие окна.

2. **Один message loop на весь процесс.**
   `crates/window/src/os/windows/connection.rs:73` `run_message_loop()` —
   единственный цикл `PeekMessageW`/`DispatchMessageW`, обслуживающий все
   окна процесса.

3. **Рендер выполняется ВНУТРИ этого цикла, синхронно.**
   `WM_PAINT` → `wm_paint()` (`os/windows/window.rs:1773`) →
   `inner.events.dispatch(WindowEvent::NeedRepaint)` (там же, :1801) →
   `WindowEventSender::dispatch` вызывает обработчик **синхронно**
   (`crates/window/src/lib.rs:243-248`) → `TermWindow::do_paint()`
   (`termwindow/mod.rs:1016`/`1049`) → реальные GPU-вызовы.

   **Следствие:** если драйвер залипает в `SwapBuffers`/`present`/`submit`
   (TDR, зависшая очередь GPU), блокируется весь message loop. Перестают
   работать скролл, переключение вкладок и даже крестик закрытия — во
   **всех** окнах процесса. Ровно это и наблюдалось.

4. **`Mutex<Terminal>` на пейн контендится с трёх сторон.**
   `LocalPane { terminal: Mutex<Terminal>, ... }`
   (`crates/mux/src/localpane.rs:153`). За него борются: поток-парсер вывода
   pty, GUI-поток при рендере (`with_lines_mut` → `lock_terminal_timed`,
   `localpane.rs:234`), и обработка ввода. Если рендер держит лок во время
   медленного GPU-пути, встаёт и чтение из pty. Инструментация
   (`lock_terminal_timed`, метрики `localpane.terminal_lock.wait.*`) уже
   есть — есть чем мерить «до/после».

5. **Нет ни watchdog'а, ни пути «отцепить зависшее».** Поиск по
   `watchdog|heartbeat|hang_detect` в `wezterm-gui`/`window` не даёт ничего.
   Чтобы закрыть зависшую вкладку крестиком, нужно, чтобы message loop
   обработал клик — а он-то и заблокирован.

**Что уже хорошо:** на пейн уже есть свои потоки чтения и парсинга pty
(`read_from_pane_pty` + `parse_buffered_data`, `crates/mux/src/lib.rs:415`,
:447). То есть ввод/вывод пейна уже развязан; не развязан **рендер**.

## 2. Стратегия

Порядок выбран так, чтобы каждый шаг давал измеримый выигрыш сам по себе и
не требовал «большого взрыва».

### Уровень A — видимость (дёшево, предпосылка для остального)
Без детектора залипания мы не отличаем «GPU завис навсегда» от «кадр
рендерится 300 мс». Всё дальнейшее (убить именно виновника) опирается на
этот признак.

### Уровень B — lock-free по данным
Убрать `Mutex<Terminal>` и `ui_items` с горячего пути между рендером,
вводом и pty. Это делается **до** выноса рендера в поток: иначе рендер-поток
утащит лок в фон и повесит чтение pty ещё надёжнее.

### Уровень C — вынос GPU из message loop

**Обновлено после декомпозиции задачи #221 агентом `@oh` (см. чекпоинт
`2026-07-30-0000.md`).** Полный перенос рендера на отдельный поток (вариант
A: `RenderState` + кэш глифов + всё построение quad'ов переезжают вместе с
потоком) — это и есть тот самый запрещённый сквозной `Rc → Arc`
рефакторинг, только под другим именем. Вместо этого выбран **вариант B**:
GUI-поток по-прежнему строит вершины в замапленные wgpu-буферы (чистый
memcpy, не блокирует), а на выделенный поток окна выносятся только
**`get_current_texture` / encode / `queue.submit` / `present` /
`surface.configure`** — именно тот класс вызовов (TDR, зависший swapchain),
который и наблюдался в инциденте. После этого залипание в этом классе
вызовов блокирует только рендер-поток своего окна, а message loop
продолжает крутиться: другие окна живы, крестик нажимается, вкладки
переключаются. Остальные GPU-вызовы (`create_buffer`/`create_texture`/
`write_texture` на путях роста вершинных буферов и атласа глифов)
остаются на GUI-потоке и вне охвата задачи (опциональный вынос — задача
221.9, только по замерам).

Задача #221 разбита на подзадачи 221.1–221.9 (см. TaskList, задачи
#227–#235), каждая независимо собираемая/тестируемая/коммитируемая, за
конфиг-флагом `webgpu_render_thread` (default `false` до 221.8). Ранее
принятое решение — не делать сквозной `Rc → Arc` рефакторинг, а дать
рендер-потоку работать только с `Send`-safe данными (сериализованный кадр
`GpuFrame`, `Arc<WebGpuState>`) — остаётся в силе и для варианта B.

**221.6:** `surface.configure` (resize) тоже перенесён на рендер-поток
(`RenderMsg::Resize`, с коалесингом серии подряд идущих resize-сообщений в
одно последнее — актуально при live-drag), и `submit_one_frame` теперь сам
восстанавливается после `SurfaceError::Lost`/`Outdated` через
`WebGpuState::reconfigure` + `window.invalidate()`, вместо просто
лога+счётчика. Это намеренно отличается от синхронного пути
(`do_paint_webgpu` на GUI-потоке, который в этом случае пересобирает весь
кадр целиком): на рендер-потоке кадр с ошибкой просто отбрасывается, а
`invalidate()` запускает следующий `NeedRepaint` обычным путём — по
эффекту эквивалентно (один потерянный кадр + свежий repaint), только
разнесено через границу потока.

**Критичная находка (`@oh`, задача 221.8):** `FrontEndSelection` по
умолчанию — `OpenGL`, не `WebGpu`, и WebGpu→OpenGL фолбэка при ошибке
инициализации сейчас нет вообще (ошибка `WebGpuState::new` роняет
открытие окна целиком). Значит задачи 221.1–221.7 сами по себе НЕ дают
пользы дефолтной конфигурации — инцидент с зависанием почти наверняка был
в glium `SwapBuffers`, а не в wgpu `present`. Задача 221.8 (фолбэк +
включение WebGpu по умолчанию на Windows) — не косметический шаг, а то,
что реально доводит инициативу до пользователя.

**Сделано (221.8):** фолбэк WebGpu→OpenGL добавлен в `TermWindow::new_window`
(ошибка `WebGpuState::new` логируется и окно открывается через
`enable_opengl()` вместо падения); `webgpu_render_thread` теперь `true` по
умолчанию; `front_end` теперь по умолчанию `WebGpu` только на Windows
(`default_front_end()`, `#[cfg(windows)]`), на остальных платформах
поведение не изменилось (`FrontEndSelection::default()` = `OpenGL`).

**Переобъём OpenGL-бэкенда (было "Уровень C, потом OpenGL", задача #222):**
рендер-поток для OpenGL делать не будем — вариант B для GL невозможен
(GL-контекст и буферы жёстко привязаны к потоку через `wglMakeCurrent`,
перенести нельзя, только пересоздать — это уже вариант A и объём работы
больше, чем вся задача #221 целиком). GL-путь остаётся синхронным и
документированным как не поддерживающий изоляцию зависаний; удалять его
нельзя, так как `FrontEndSelection::Software` идёт через тот же glium.

### Уровень D — изоляция вкладки

**Переобъём (`@oh`, задача #223):** с уровня вкладки на уровень окна. Все
вкладки окна делят один surface и один рендер-поток — залипший GPU вешает
рендер всего окна, а не одной вкладки, поэтому «прибить одну зависшую
вкладку при зависании GPU» на этом слое недостижимо. Задача складывается
из (а) супервизии зависаний на уровне пейна/pty (не связана с GPU,
достижима уже сегодня) и (б) возможности закрыть окно с признанным
зависшим рендер-потоком, не роняя процесс и соседние окна. Teardown —
**detach, не join**: `join()` зависшего рендера сам по себе повесил бы
закрытие.

### Уровень E — изоляция процессов
Единственная настоящая защита от полностью залипшего процесса/устройства.
Опция «окно = отдельный процесс» вместо attach к существующему
`gui-sock`. Требует аккуратности: single-instance — это фича (общий mux),
поэтому только опционально и с сохранением совместного доступа через
mux-протокол.

### Уровень F — асинхронность
Сейчас на каждый пейн **два** потока (reader + parser). При многих вкладках
это дорого. Но это оптимизация ресурсов, а **не** решение проблемы
зависаний — поэтому она идёт последней и начинается с замеров, а не с
переписывания.

## 3. Критерий приёмки (общий для инициативы)

Искусственно залипший GPU-вызов в одной вкладке:

- остальные вкладки того же окна продолжают рендериться и принимать ввод;
- остальные окна процесса полностью отзывчивы;
- крестик именно этой вкладки закрывает её (с дампом), окно живёт дальше;
- чтение из pty остальных пейнов не встаёт;
- при включённой опции изоляции процессов — соседние окна вообще не в том
  процессе и не могут быть затронуты в принципе.

Отдельный регресс-тест на это — задача #226.

## 4. Регресс-тест изоляции (задача #226)

Полностью автоматизированный end-to-end тест невозможен: `WebGpuState`
требует реального GPU-адаптера (`wgpu::Instance`/`request_adapter`), которого
нет в headless CI. Логика без GPU уже покрыта юнит-тестами, добавленными по
ходу 221.4–221.7 (`dispatch_loop`'s coalescing/back-pressure/shutdown,
`is_hung_given`) — см. `crates/wezterm-gui/src/renderthread.rs`.

Вместо этого проведена ручная проверка end-to-end на реальном GPU этой
машины (2026-07-30), с использованием `debug_render_thread_stall_ms`
(задача 221.5) и `render_thread_hang_threshold_ms` (задача 221.7):

```
onlyterm-gui.exe --config 'debug_render_thread_stall_ms=6000' \
                  --config 'render_thread_hang_threshold_ms=1500'
```

**Наблюдение:** окно с искусственно зависающим (6с сон перед каждым
`submit_frame`) рендер-потоком и порогом зависания 1.5с самостоятельно
закрылось приблизительно через 1.5–2с — то есть супервизор из задачи #223
сработал как задумано, не дожидаясь окончания 6-секундного сна. Процесс
`onlyterm-gui.exe` при этом НЕ упал (никакого падения/дампа не
зафиксировано — а `TerminateProcess`/паники и не ожидалось: закрытие
происходит штатным `window.close()`). Отдельно запущенное второе окно
(без stall-конфига) оставалось живым и стабильным (растущее, но
стабилизировавшееся потребление памяти) независимо от закрытия первого.

**Не проверено вручную в этом прогоне** (честно фиксирую пробелы):
- Изоляция на уровне **вкладки внутри одного окна** — недостижима на
  текущей архитектуре (см. переобъём #223 выше: все вкладки окна делят один
  surface/рендер-поток), поэтому и не тестировалась отдельно.
- Продолжение чтения из pty остальных пейнов во время зависания GPU — не
  замерено в этом прогоне (агент из задачи #219 уже устранил связанный путь
  контеншна на `Mutex<Terminal>`, но отдельного замера времени pty-чтения
  под активным GPU-stall не делалось).
- «Снятие дампа» из исходного критерия приёмки — в задаче #223 не
  реализовано вообще; текущая супервизия молча закрывает окно и пишет
  `log::error!` + метрику `gui.render_thread.window_closed_for_hang`, без
  MiniDump. Если дамп нужен для последующей диагностики зависших GPU-кейсов
  — это отдельная, не заведённая пока задача.
- Два окна в одном процессе, ОБА с активным stall-конфигом одновременно
  (конфиг общий на процесс, per-window override невозможен) — не
  проверялось; ожидаемое поведение — оба окна независимо детектируют
  зависание и закрываются каждое своим супервизором, не влияя друг на
  друга, но это не подтверждено эмпирически.

**Вывод:** ключевое свойство инициативы — «зависший GPU-вызов одного окна
не роняет процесс и не хватает остальные окна» — подтверждено вручную на
реальном оборудовании. Автоматизация теста как `cargo test` остаётся
нецелесообразной без GPU в CI.

## 5. Задача #244.7-244.9: пересборка рендерера на месте вместо закрытия окна (задача #257)

По итогам плана `@oh` (2026-07-30) реализована и запущена на реальном GPU
этой машины пересборка WebGPU-рендерера окна на месте при зависании
(задача #253, коммит `3b17955a4`), вместо закрытия окна целиком (что было
поведением уровня D/#223 выше). Дополнена device-lost/surface-error
восстановлением (#254, `0db640797`) и рантайм-фолбэком на OpenGL при
исчерпании бюджета попыток (#255, `d14e8de6f`).

Ручная проверка проведена ТРИЖДY независимо на этой же машине (Intel UHD
Graphics, Vulkan backend) — один раз в ходе верификации самой задачи #253
(её собственным исполнителем `@sh`), и ещё дважды лично оркестратором сессии
при независимой верификации коммитов #253 и #254/#255 (после каждого
изменения затронутых файлов — регрессионная проверка):

```
onlyterm-gui.exe --config 'debug_render_thread_stall_ms=6000' \
                  --config 'render_thread_hang_threshold_ms=1500'
```

**Наблюдение (идентично воспроизведено во всех трёх независимых прогонах,
включая финальный после #255):**
- Зависание детектируется через ~1.5с (порог), запускается пересборка
  рендерера ("attempt 1 of 3 allowed within 30s") — окно НЕ закрывается.
- Пересборка успешно завершается (~0.8с), лог: "successfully rebuilt this
  window's WebGpu renderer in place ... window and all its tabs/panes
  survived".
- Поскольку `debug_render_thread_stall_ms` — процессный, а не одноразовый
  оверрайд, следующий кадр снова виснет через ~2.3-2.9с — цикл повторяется
  ещё дважды ("attempt 2 of 3", "attempt 3 of 3"), каждый раз с успешной
  пересборкой.
- После 4-го обнаруженного зависания circuit breaker срабатывает штатно
  ("has hung and been rebuilt 4 times in the last 30s; giving up on
  rebuilding") — до задачи #255 в этой точке окно закрывалось; после #255
  вместо этого происходит одноразовый фолбэк на OpenGL (лог: "attempting a
  one-time fallback to OpenGL" → "this window has permanently fallen back
  to OpenGL rendering"), окно и его вкладки/процессы переживают и это
  событие. Фолбэк подтверждён: `onlyterm cli list`/`get-text`/`send-text`
  показывают, что пейн остаётся живым и интерактивным, скриншот подтвердил
  реальный рендеринг глифов после фолбэка.
- Ни одной паники за все три прогона. `tasklist` после каждого прогона не
  показывает осиротевших процессов дочерней оболочки.

**Не проверено эмпирически в этой сессии (честно фиксирую):**
- Два реальных окна одновременно, оба под зависанием — `debug_render_thread_stall_ms`
  общий на процесс, а архитектура всё ещё attach'ит несколько mux-окон к
  одному GUI-процессу (#224/#258 не сделаны), так что чистого теста "два
  независимых окна, оба виснут, оба независимо восстанавливаются" на этой
  машине провести не удалось за разумное время (см. честную оговорку в
  коммите `3b17955a4`). Изоляция между окнами подтверждена **чтением кода**
  (у каждого окна свой `wgpu::Instance`/`Adapter`/`Device`, нет общего
  мутабельного состояния между `TermWindow`-инстансами), но не эмпирическим
  наблюдением двух окон бок о бок.
- Настоящий аппаратный TDR (сброс драйвера) — симулировался только через
  `debug_render_thread_stall_ms` (искусственный `thread::sleep`, не
  реальный сбой драйвера/адаптера). Путь device-lost (#254) проверен
  только код-ревью + существующими юнит-тестами `renderthread.rs`, без
  детерминированного способа спровоцировать реальное wgpu device-lost
  событие в этой тестовой среде.

**Вывод:** ключевое свойство фаз A-C инициативы полностью подтверждено на
реальном GPU: зависание GPU-вызова окна теперь стоит один потерянный кадр
и (при исчерпании бюджета) деградацию до OpenGL — но НЕ теряет ни одной
вкладки и ни одного дочернего процесса, что является прямым ответом на
исходную жалобу пользователя из раздела 1 этого документа.
