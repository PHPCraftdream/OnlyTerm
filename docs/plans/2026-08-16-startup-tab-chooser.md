# План: флаг запуска, открывающий диалог New Tab Options вместо первой вкладки

Дата: 2026-08-16. Репо: OnlyTerm, ветка `main` (от `d4ea7c58c`).

## Цель

Параметр командной строки, при котором OnlyTerm стартует **без вкладки**, показывая
только диалог New Tab Options. Пользователь выбирает шелл, права и приоритет, жмёт
Run — открывается ровно одна соответствующая вкладка, и дальше окно ведёт себя как
обычное. Если вместо Run нажали `Esc` или крестик диалога — приложение завершается,
не оставляя пустого окна.

Явное требование: **плюсик в панели вкладок после этого работает как обычно** —
левый клик открывает вкладку по умолчанию, не диалог. Режим одноразовый, он не
переключает приложение в «всегда спрашивать».

## Что уже есть (проверено по коду, менять не нужно)

Три из требований закрыты существующим кодом, и это важно зафиксировать, чтобы
не «чинить» работающее:

- **Плюсик уже разделён по кнопкам мыши.** `do_new_tab_button_click`
  (`mouseevent.rs:606`): левый клик → `SpawnTab(CurrentPaneDomain)`, правый клик →
  `ActivateNewTabOptions`. То есть требование «плюсик потом открывает обычный таб»
  выполняется само собой, при условии что новый режим не трогает эту функцию.
- **Окно без вкладок предусмотрено.** `TermWindow::new_window`
  (`render_pipeline.rs:58`) прямо обрабатывает случай «вкладок ещё нет»:
  `log::debug!("new_window has no tabs... yet?")` и размер по умолчанию.
- **Пустое mux-окно доходит до создания GUI-окна.** `iter_windows_in_workspace`
  (`mux/src/lib.rs:1043`) фильтрует только по workspace, а не по наличию вкладок,
  поэтому `reconcile_workspace` создаст `TermWindow` и для пустого окна.
- **Модалка рисуется независимо от панелей.** `paint_pass`
  (`render/paint.rs:419`) вызывает `paint_modal` безусловно, после
  `paint_tab_content`; при пустом `get_panes_to_render()` содержимое вкладок
  просто ничего не рисует.

## Главный риск и его решение

Mux с нулём панелей завершает приложение: `prune_dead_windows` (`mux/src/lib.rs:898`)
находит пустое окно, удаляет его, шлёт `MuxNotification::Empty`, и обработчик во
`frontend.rs:158` при `quit_when_all_windows_are_closed` вызывает
`terminate_message_loop`. Окно с одним диалогом и без вкладок попадает ровно под
это.

Механизм защиты в коде уже есть и предназначен именно для этого случая —
`mux::activity::Activity`. `prune_dead_windows` первой же строкой выходит, если
`Activity::count() > 0`, а обработчик `Empty` дополнительно перепроверяет тот же
счётчик. Комментарий у самого типа говорит прямо: «used to keep the frontend alive
even if there may be no windows present in the mux».

Важная тонкость: `Activity`, который держит `MuxWindowBuilder`
(`mux/src/lib.rs:138`), для этого не годится — он отдаётся в `notify()` и
уничтожается сразу после рассылки `WindowCreated`. Нужен **собственный** `Activity`,
живущий всё время, пока открыт стартовый диалог.

## Порядок работ

### 1. Флаг командной строки

`crates/wezterm-gui-subcommands/src/lib.rs`, структура `GuiSubCommand`.

```rust
/// Open the New Tab Options dialog instead of the initial tab: the tab is
/// spawned only once you pick a shell and press Run. Dismissing the dialog
/// (Esc or the close cross) exits, because there is nothing behind it.
#[arg(long = "choose-tab", conflicts_with_all = ["start_conf", "cwd", "prog"])]
pub choose_tab: bool,
```

Имя `--choose-tab` — предложение, не решение; альтернативы `--pick-shell`,
`--new-tab-options`. Взаимоисключение с `--start-conf`/`--cwd`/`PROG` обязательно:
все три описывают, что именно запустить, а этот флаг именно спрашивает.

### 2. Пропустить спавн первой вкладки

`crates/wezterm-gui/src/main.rs`, `async_run_terminal_gui` (~строка 555). Ветка
`--start-conf` уже показывает нужный шаблон: она возвращается раньше, минуя
`spawn_tab_in_domain_if_mux_is_empty`.

Новая ветка должна:
1. взять `let _activity = mux::activity::Activity::new();` и **передать его дальше**,
   а не уронить на выходе из функции;
2. создать пустое окно `mux.new_empty_window(workspace, None)`;
3. взвести одноразовый флаг «первому окну открыть диалог» (см. пункт 3);
4. вернуться, не спавня вкладку.

Место хранения `Activity` — открытый вопрос реализации. Самое прямое: положить его
в тот же одноразовый слот, что и флаг, и передать во владение модалке при её
создании. Тогда время жизни `Activity` буквально совпадает со временем жизни
диалога.

### 3. Донести намерение до `TermWindow`

`TermWindow` создаётся позже и асинхронно (`frontend.rs:442`), доступа к `opts` у
него нет. Нужен одноразовый слот на уровне процесса, например
`crates/wezterm-gui/src/startup_chooser.rs`:

```rust
static PENDING: Mutex<Option<Activity>> = Mutex::new(None);

/// Arms the chooser for the next window to be constructed, taking ownership
/// of the Activity that keeps the empty mux alive until the dialog resolves.
pub fn arm(activity: Activity) { ... }

/// Consumed by the first TermWindow to finish construction; every later
/// window gets None, so a `SpawnWindow` during the dialog opens normally.
pub fn take() -> Option<Activity> { ... }
```

Статик, а не поле конфигурации: в этом форке каждый запуск — отдельный процесс
(`main.rs:610`), делегирования в чужой GUI нет, так что «состояние на процесс»
здесь честно отражает «состояние на запуск».

Потребитель — конец `TermWindow::new_window`, после успешной инициализации: если
`take()` вернул `Some`, поставить модалку через `set_modal`.

### 4. Поведение отмены

Сейчас и `Esc` (`newtab_options.rs`, `key_down`), и крестик
(`mouse_event_newtab_options_close`) ведут в `cancel_modal`. Нужен второй режим.

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum OnCancel {
    /// Ordinary invocation: dismiss and go back to the tab underneath.
    Dismiss,
    /// Startup invocation: there is no tab underneath, so dismissing the
    /// dialog means dismissing the application.
    QuitApplication,
}
```

Поле `on_cancel` задаётся при конструировании; оба пути отмены смотрят на него.
Для выхода — тот же путь, что у `QuitApplication` в `actions.rs:1478`:
`Connection::get()` → `terminate_message_loop()`. Отдельно проверить, что
`terminate_message_loop` при нулевом количестве вкладок не упирается ни в какое
подтверждение — в этом форке диалоги подтверждения выхода вырезаны (комментарий
там же), так что не должен.

### 5. Домен спавна при Run

`execute_new_tab_run_request` (`newtab_options.rs`) сейчас спавнит в
`SpawnTabDomain::CurrentPaneDomain`. **В стартовом режиме текущей панели нет** —
это, скорее всего, сломается или молча ничего не сделает. Нужно проверить
`spawn_command_impl` и, если подтвердится, в стартовом режиме использовать
`SpawnTabDomain::DefaultDomain`.

Это единственное место, где я ожидаю настоящий сюрприз при реализации. Проверять
измерением, а не рассуждением.

Второй нюанс того же пункта: `Activity` нельзя ронять раньше, чем вкладка реально
появилась в mux, иначе между «диалог закрылся» и «вкладка создалась» возникает окно,
в котором mux пуст и приложение завершится. Значит, `Activity` должен переехать
внутрь асинхронной задачи спавна и умереть после неё, а не в момент закрытия
модалки.

Для elevated-варианта путь другой (`spawn_elevated_single_pane_tab`) и он и так
принимает `window_id`, но UAC-подтверждение может занять минуты, и всё это время
mux пуст — тем более важно, чтобы `Activity` дожил до конца, включая случай отказа
от UAC. При отказе разумнее всего снова показать диалог, а не выйти молча.

### 6. Плюсик не трогать

Явно зафиксировать тестом или комментарием, что режим одноразовый:
`startup_chooser::take()` опустошает слот, поэтому второе окно и повторный
`ActivateNewTabOptions` получают обычную модалку с `OnCancel::Dismiss`.

## Чем проверять

Автотестами закрывается немногое — почти всё здесь про жизненный цикл окна.
Что реально можно:

- юнит-тест на `OnCancel`: значение по умолчанию для обычного вызова — `Dismiss`
  (защита от того, что кто-то случайно сделает выход поведением по умолчанию);
- юнит-тест на одноразовость слота: два `take()` подряд → второй `None`.

Остальное — живой прогон, по пунктам:

1. `onlyterm-gui --choose-tab start` → окно с диалогом, без вкладок, не падает и
   не закрывается само.
2. Run с `cmd`/`normal`/`Normal` → ровно одна вкладка, диалог исчез.
3. Левый клик по плюсику → обычная вкладка, диалога нет.
4. Правый клик по плюсику → диалог с обычным поведением `Esc`.
5. `Esc` в стартовом диалоге → процесс завершился, в диспетчере нет
   `onlyterm-gui.exe` от этого запуска.
6. То же крестиком.
7. Run с `admin` → UAC, вкладка elevated; отказ от UAC → диалог вернулся,
   приложение живо.

Штатные проверки: `cargo build -p wezterm-gui`,
`cargo clippy -p wezterm-gui --all-targets -- -D warnings`, `cargo fmt --check`,
`cargo test -p wezterm-gui`.

## Оценка

Каркас (флаг, пропуск спавна, слот, `OnCancel`) — небольшой и предсказуемый.
Основное время уйдёт на пункт 5: домен спавна без текущей панели и время жизни
`Activity` вокруг асинхронного спавна, особенно elevated. Это же и главный
источник риска.

## Чего этот план сознательно не делает

- Не добавляет конфиг-ключ «всегда показывать диалог при старте». Спросили про
  параметр запуска; постоянный режим — отдельное решение с другими последствиями
  (в частности, диалог начнёт появляться и при восстановлении сессии).
- Не меняет поведение плюсика.
- Не трогает `--start-conf`: это соседний механизм с той же целью «описать, что
  открыть», но декларативный, и объединять их не нужно.
