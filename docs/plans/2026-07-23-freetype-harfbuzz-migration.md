# План: миграция freetype+harfbuzz (C/C++) → rustybuzz+swash (чистый Rust)

Дата: 2026-07-23. Часть более крупной инициативы "убрать весь C/asm из wezterm"
(см. также `2026-07-23-decairo-tiny-skia.md`, `2026-07-23-ssh-russh-migration.md`).

## Контекст

Полный аудит workspace на C/asm (в рамках этой же инициативы) показал: помимо
cairo/pixman и ssh2/libssh-rs/openssl (уже в работе), крупнейший оставшийся
C/C++ след — `deps/freetype` (freetype2 ~166k строк C + libpng + zlib) и
`deps/harfbuzz` (harfbuzz, C++, сотни файлов). В отличие от cairo (узкий,
изолированный потребитель — 5 файлов рендера COLR-глифов), freetype и harfbuzz —
**ядро текстового движка**: шейпинг (harfbuzz) и хинтинг+растеризация обычных
(не цветных) глифов (freetype) для абсолютно каждого символа в терминале.
Выше риск и объём тестирования, чем у cairo — подтверждено пользователем как
осознанный выбор (см. диалог), делаем полноценно.

## Результаты исследования

### Где используются (wezterm-font)

| Файл | Строк | Роль |
|---|---|---|
| `src/hbwrap.rs` | 1195 | FFI-обёртка над HarfBuzz C API |
| `src/shaper/harfbuzz.rs` | 1242 | Реализация `FontShaper` — превращает строку в последовательность (glyph_id, x_advance, y_advance, cluster) — **шейпинг, используется для КАЖДОЙ строки текста** |
| `src/ftwrap.rs` | 1535 | FFI-обёртка над FreeType C API |
| `src/rasterizer/freetype.rs` | 910 | Реализация `FontRasterizer` — хинтинг + растеризация в grayscale-битмап обычных глифов, плюс FT_COLR paint-путь (уже мигрирует на tiny-skia в задачах #2-5) |
| `src/rasterizer/harfbuzz.rs` | 416 | Альтернативный `FontRasterizer` через HarfBuzz paint API (тоже мигрирует на tiny-skia) |

Итого ~5300 строк Rust-обвязки поверх FFI, не считая уже покрытого cairo-плана.

### Архитектура — уже пригодна для подмены (как и с cairo)

- `wezterm-font/src/shaper/mod.rs`: `pub trait FontShaper` + `pub fn new_shaper(...)`
  — единственная существующая реализация `HarfbuzzShaper` в `shaper/harfbuzz.rs`.
  Чистая точка подмены: `RustybuzzShaper: FontShaper`.
- `wezterm-font/src/rasterizer/mod.rs`: `pub trait FontRasterizer` — уже ДВЕ
  реализации (`freetype.rs`, `harfbuzz.rs`), выбираемые конфигом — паттерн
  подмены такой же, добавляем `SwashRasterizer: FontRasterizer` (или
  замещаем существующий `freetype.rs` изнутри, сохранив тот же trait impl).
- Важно: как только cairo-миграция (#2-5) заменит внутренности этих двух
  рno-растеризаторов на painter поверх tiny-skia, сама freetype-часть внутри
  `rasterizer/freetype.rs` (не-COLR путь: хинтинг+растеризация обычных
  глифов через `FT_Load_Glyph`/`FT_Render_Glyph`) останется единственным
  местом, реально завязанным на `ftwrap.rs` для рендеринга (помимо парсинга
  метрик шрифта, которым ftwrap тоже пользуется повсеместно — см. ниже).

### Кандидаты (проверено на docs.rs)

- **Шейпинг**: `rustybuzz` — "complete harfbuzz shaping algorithm port to Rust",
  0% C, использует `ttf-parser` (тот же автор, RazrFalcon). Специально
  спроектирован для побитовой совместимости вывода с HarfBuzz — самый
  безопасный кандидат из всей этой инициативы.
- **Парсинг+хинтинг+растеризация**: `swash` — чистый Rust (`skrifa`/`zeno`/`yazi`
  внутри, гугловский пул для текстового стека), активно поддерживается.
  Хинтинг и качество растеризации в деталях не проверены (доки не раскрывают
  сравнение с FreeType напрямую) — **это главный открытый риск**, требует
  визуального/метрического сравнения на этапе верификации, не только "собралось".
  Альтернативы на подстраховку, если swash не покроет что-то: `fontdue`,
  `ab_glyph` (проще, меньше фич).

### Тонкие места

1. **Хинтинг-парность.** FreeType десятилетиями тюнили под мелкие размеры
   шрифта на низком DPI (TrueType bytecode interpreter + autohinter). `swash`
   может рендерить визуально иначе на маленьких кеглях. Критерий приёмки —
   не "побитово идентично", а "читаемо и не хуже" на реальных шрифтах
   пользователя, плюс сравнение метрик (advance width, bearing) — они ДОЛЖНЫ
   совпадать точно, иначе поедет вёрстка ячеек терминала.
2. **`ftwrap.rs` используется не только для рендера** — нужно проверить (на
   этапе реализации) все остальные точки: получение метрик шрифта (line
   height, cap height), palette-данные для COLR (уже частично покрыто
   cairo-планом), font variation axes, синтетический italic/bold — все они
   должны иметь эквивалент в `swash`/`ttf-parser`, иначе миграция неполна.
3. **Кластеризация/cursor-логика** (`CellCluster`, `PresentationWidth` в
   `shaper/mod.rs`) завязана на том, что шейпер возвращает те же кластерные
   границы, что и сейчас — критично для правильного позиционирования
   emoji/ZWJ-последовательностей и combining marks.
4. **Порядок с cairo-миграцией**: логично делать ПОСЛЕ того, как cairo-план
   (#2-5) закончит паинтер на tiny-skia — тогда freetype/harfbuzz-миграция
   трогает уже упрощённый код, а не дважды переписывает одни и те же файлы.
   Явно блокируем задачи этого плана на #5/#6 (cairo-вычистка).

### Тулинг — переиспользуем, не строим с нуля

Задача #9 (dump_glyph/diff_glyph для cairo-плана) уже даёт headless dump
растеризованного глифа в PNG + метаданные — это годится и здесь без
изменений (не важно, какой рендер-бэкенд произвёл `RasterizedGlyph`).
Нужно добавить только одно новое измерение — **сравнение шейпинга**
(не рендера): `wezterm-font/examples/dump_shaping.rs` — берёт строку +
шрифт, гонит через шейпер, печатает JSON-массив (glyph_id, x_advance,
y_advance, cluster) — сравнение rustybuzz vs harfbuzz на реальных строках
(латиница, арабская вязь, деванагари, ZWJ-эмодзи-последовательности из
`test-data/emoji-test.txt`, уже есть в репо).

### Порядок работ

- **H0. Тулинг шейпинга.** `dump_shaping.rs` + скрипт сравнения (аналог
  `diff_glyph`, но для JSON glyph-рядов вместо PNG). Блокирует всё
  дальнейшее — без этого сравнивать шейпинг можно только на глаз.
- **H1. `RustybuzzShaper`.** Новая реализация `FontShaper` в
  `shaper/rustybuzz.rs`, покрывающая тот же контракт, что `HarfbuzzShaper`
  (кластеризация, OpenType-фичи, variable fonts). Тесты через H0 на наборе
  строк: латиница, арабский, деванагари, эмодзи-ZWJ, обычные лигатуры.
- **H2. `SwashRasterizer` — базовый путь (парсинг + метрики).** Покрыть все
  точки использования `ftwrap.rs`, не связанные с рендером пикселей: метрики
  шрифта, font variation axes, palette для COLR (может быть уже частично
  готово из cairo-плана). Тесты: метрики должны совпадать точно с текущими
  (advance width/bearing/line height) на референсном наборе шрифтов.
- **H3. `SwashRasterizer` — растеризация обычных (не-COLR) глифов.**
  Хинтинг+рендер в grayscale/subpixel bitmap. Верификация через #9-тулинг
  (dump_glyph/diff_glyph), допуск шире, чем у cairo (не побитово, а
  "читаемо, не хуже") — обязательно на нескольких DPI/размерах шрифта.
- **H3.5. Переключение дефолта (найдено как пробел плана, 2026-07-24).**
  H1-H3 построили `RustybuzzShaper`/`SwashRasterizer` ПАРАЛЛЕЛЬНО,
  не подключёнными по умолчанию — `new_shaper`/`new_rasterizer` (или
  как называются фабричные функции в wezterm-font, конкретно найти при
  реализации) всё ещё возвращают `HarfbuzzShaper`/`FreeTypeRasterizer`.
  Прежде чем удалять freetype/harfbuzz в H4, нужно реально переключить
  дефолт (конфиг-опция, если такая уже существует по аналогии с
  `font_colr_rasterizer`, или прямая замена в фабричной функции) и
  прогнать полный `cargo test --workspace` + живую проверку
  (`/run`/`/verify`) на новом дефолте — только после этого H4 безопасен.
- **H4. Вычистка.** Убрать `freetype`/`harfbuzz` крейты, `deps/freetype`,
  `deps/harfbuzz` из workspace. `cargo build --workspace` без единого C/C++
  компилятора в графе сборки (кроме уже запланированных к вычистке cairo/
  openssl, которые к этому моменту тоже должны быть убраны).
- **H5. Верификация.** Полный прогон `cargo test -p wezterm-font`, dump_glyph/
  dump_shaping на широком наборе шрифтов и скриптов, живая проверка через
  `/run`/`/verify` (уже есть, отдельного тулинга не нужно).

## Риски

- Хинтинг-парность на мелких кеглях — главный визуальный риск, нет
  формального критерия "готово", только "не хуже".
- `ftwrap.rs`/`hbwrap.rs` могут иметь точки использования, не выявленные при
  этом обзоре (1535+1195 строк не читались построчно) — при реализации H2
  сделать полный проход по каждой публичной функции и найти её эквивалент.
- Порядок относительно cairo-плана: если начнём параллельно, велик риск
  конфликтов в одних и тех же файлах (`rasterizer/freetype.rs`,
  `rasterizer/harfbuzz.rs`) — блокируем строго после #5/#6.
