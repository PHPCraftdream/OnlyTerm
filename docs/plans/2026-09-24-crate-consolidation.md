# План консолидации небольших crates

Дата исследования: 2026-09-24. Область этого плана — число пакетов workspace, а не переименование или перенос каталогов. Исходный код и манифесты при исследовании не менялись.

## Проверенная картина

`cargo metadata --no-deps --locked --format-version 1` показывает 54 пакета workspace. У 21 пакета в `src/` не больше двух `.rs` (подсчёт рекурсивный); это лишь фильтр для рассмотрения, не критерий удаления. Он не учитывает `build.rs`, отдельный бинарный target, тесты/bench и цену перекомпиляции. Граф прямых обратных зависимостей ниже получен из `packages[].dependencies` того же metadata; проверен также поиск импортов по исходникам.

Подсчёт прямых потребителей включает normal, build и dev dependencies. У `frecency` и `bintree` ровно по одному рабочему потребителю, без собственного `build.rs`, features или отдельного bin target. У `base91` единственное использование во всём дереве — `test_pdu_ping_base91` в `codec/src/lib.rs`; в `codec/Cargo.toml` это именно dev dependency. Поэтому перенос `base91` в рабочий код `codec` был бы ошибкой.

В схеме решения учитываются границы зависимостей: у `frecency` зависимости `chrono`, `serde`, `serde_with`, у `bintree` внешних зависимостей нет. Перенос в их текущих потребителей не создаёт цикла по нынешнему графу. GUI уже зависит от `chrono` и `serde`, но для `frecency` ему понадобится `serde_with` как обычная зависимость. После каждого переноса граф нужно проверить заново через `cargo metadata` / `cargo tree`, а не полагаться на этот снимок.

## Этап 1 — `frecency` → GUI

1. Зафиксировать тестовыми фикстурами сериализацию `Frecency`: точные поля `half_life`, `last_accessed`, `frecency`, `num_accesses`, секунды вместо других единиц времени; проверить чтение старого JSON с ненулевой историей и неизменную оценку при фиксированном времени. Текущий тест в `frecency/src/lib.rs` проверяет JSON нового объекта, но не чтение уже сохранённой истории.
2. Скопировать `crates/frecency/src/lib.rs` в новый `crates/onlyterm-gui/src/window/termwindow/frecency.rs`, объявить `mod frecency` в `crates/onlyterm-gui/src/window/termwindow/mod.rs`. В существующих `crates/onlyterm-gui/src/window/termwindow/ui/palette.rs` и `crates/onlyterm-gui/src/window/termwindow/panes/charselect.rs` заменить `use frecency::Frecency` на `use super::frecency::Frecency`: оба модуля объявлены в `termwindow/mod.rs` и являются соседями нового модуля, несмотря на физические подпапки `ui/` и `panes/`. Перенести исходные unit tests вместе с реализацией.
3. В `crates/onlyterm-gui/Cargo.toml` удалить `frecency.workspace = true`, добавить `serde_with.workspace = true`; убрать `frecency` из `[workspace.dependencies]` корневого `Cargo.toml` и исключить/удалить старый пакет, проверив весь workspace на прямые упоминания. Если есть lockfile, обновить его без повышения версий библиотек.
4. Проверить оба файла данных: `recent-commands.json` (`ui/palette.rs`) и `recent-emoji.json` (`panes/charselect.rs`). Положительный оракул — старые файлы читаются, сортировка/новое сохранение сохраняют известные значения и имена. Отрицательные контроли — отсутствующий и испорченный JSON ведут себя как сейчас (загрузка возвращает ошибку, вызывающий код использует пустую историю). Не использовать реальные пользовательские файлы в тестах.

Цена: число пакетов уменьшается на один; изменение `frecency.rs` теперь инвалидирует компиляцию крупного GUI. Не обещать ускорение сборки без измерения инкрементальной сборки до/после на одинаковом профиле и чистом target. Если измерение покажет существенное замедление обычной разработки, вернуть crate отдельным шагом.

## Этап 2 — `bintree` → mux

1. Перед переносом сохранить текущие тесты `bintree`: перемещение zipper cursor, split/итерация и преобразование обратно в дерево. Добавить к `mux` тесты краёв: пустое дерево, один лист, левый/правый split, переход за последний узел, сохранение `PathBranch` и порядка панелей. Отдельно записать эталон сериализованного `PaneNode`/PDU на фиксированном дереве: `PaneNode` явно превращает узлы в `bintree::Tree`, а комментарий в `mux/src/model/tab/codec.rs` предупреждает о версии codec.
2. Перенести файл в `crates/mux/src/model/tab/bintree.rs`, объявить модуль в `tab/mod.rs`; обновить `split_tree.rs`, `splits.rs`, `panes.rs`, `codec.rs`. Сохранить экспортируемые `mux::tab::{Tree, Cursor}` и сигнатуры `PaneNode::into_tree`; не менять структуру `PaneNode` и его формат. Внутреннюю видимость модуля выбрать так, чтобы публичные функции не раскрывали недоступный тип; проверять rustdoc/Clippy вместе с компиляцией потребителей.
3. Удалить `bintree.workspace = true` из `mux/Cargo.toml`, запись из корневого `[workspace.dependencies]` и старый пакет. Проверить сборку `mux`, `codec`, `onlyterm-client` и GUI как реальных потребителей публичного `mux::tab`. Не менять версию протокола, если сериализованные байты тождественны; при расхождении считать этап неуспешным и исследовать причину до принятия изменений.

Смена package identity публичного типа может затронуть внешнего потребителя `bintree::Tree`, хотя поиск по текущему репозиторию находит только `mux`. Пакет `publish = false`; всё равно проверить документацию/интеграции, если будет подтверждён внешний пользователь.

## Этап 3 — решение о `base91`

`base91` — 9,8 КБ исходника с уведомлением об авторском праве Joachim Henke и BSD-подобными условиями в заголовке. Единственный потребитель — тест `codec::test_pdu_ping_base91`, где он проверяет способность `Pdu::encode` писать через произвольный `Write`. Рабочий `codec` не кодирует base91 и не должен начать от него зависеть. Первые два этапа дают два обоснованных удаления пакетов; решение о третьем принять по результату, а не ради числа.

Если этот тест действительно нужен: перенести реализацию в новый `crates/codec/src/test_support/base91.rs`, объявить `#[cfg(test)]` модуль через `#[path = "test_support/base91.rs"]` в `crates/codec/src/lib.rs` и обновить импорт теста. Сохранить полный copyright/redistribution notice и существующие проверки `base91` (известный вектор `hello` с завершающим LF → `TPwJh>UA`, бинарный round-trip), а также точный вектор PDU `[60, 67, 75, 65]`. Затем убрать только `base91` из `codec` dev dependencies и workspace. Отрицательный контроль — тестовый writer, намеренно возвращающий ошибку или короткую запись, должен по-прежнему выявлять нарушение контракта `Write`; не подменять проверку одним round-trip, который может пройти при одинаковой ошибке кодера и декодера. Если перенос тестовой утилиты в `codec` усложнит сопровождение больше, чем отдельный crate, оставить `base91` и зафиксировать это решение.

Согласование с [планом именования](2026-09-24-crate-naming.md): его строка `base91` условно предлагает перенос в `codec`, но по этому исследованию перенос отложен, потому что зависимость используется лишь в тесте. Если `base91` остаётся отдельным пакетом, политика именования может позже переименовать его в `onlyterm-base91`; если тестовую утилиту всё же перенесут, пакет не нужно переименовывать перед удалением. Аналогично, сначала решить судьбу `frecency` и `bintree`, чтобы не переименовывать их дважды.

## Приёмка и откат

Каждый этап — отдельный обзор и изменение, без объединения с переименованием crates или переносом каталогов. До удаления пакета доказать отсутствие иных импортов/манифестных ссылок (`rg`, `cargo metadata`). После каждого этапа: `cargo metadata --locked --no-deps --format-version 1` (54 → 53 → 52; этап 3 при принятии → 51), проверки unit tests перемещённого кода и прямого потребителя, `cargo check` прямых downstream crates, `cargo clippy` этих же crates с `-D warnings`, rustfmt и `git diff --check`. Широкие workspace-прогоны нужны только если локальная проверка обнаружит межпакетный риск.

Критерий принятия — сохранение старых JSON-файлов, идентичные байты wire-протокола и поведение split tree, отсутствие новых циклов и внешних зависимостей, а также подтверждённый выигрыш в простоте поддержки. Если любой оракул расходится, откатить только соответствующий этап, не подгоняя фикстуру под новую реализацию. Откат не должен переписывать данные пользователя и не требует повышения версий.
