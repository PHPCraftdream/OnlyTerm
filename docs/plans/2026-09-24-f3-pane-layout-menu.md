# План: F3 — меню деления активной секции во всех режимах

Дата: 2026-09-24. Статус: план; реализация не начата.

## Принятое поведение

- F3 без модификаторов открывает нумерованное меню внутри текущего окна OnlyTerm. Как и привязка F2, это штатная привязка по умолчанию: пользовательская настройка может её переопределить или отключить.
- Если включён байпас клавиш, F3 передаётся приложению в терминале и меню не открывается. Если байпас включили при уже открытом меню F3, меню закрывается без действия; последующие клавиши проходят в pane.
- Меню показывает шесть стабильных пунктов:

| Номер | Действие |
| --- | --- |
| 1 | Разделить активную секцию на две слева/справа |
| 2 | Разделить активную секцию на две сверху/снизу |
| 3 | Разделить активную секцию на три слева/справа |
| 4 | Разделить активную секцию на три сверху/снизу |
| 5 | Закрыть активную секцию, только если в текущей вкладке есть другие |
| 6 | Закрыть меню |

- Выбор работает цифрами верхнего ряда, цифровой клавиатурой и левой кнопкой мыши по строке. Esc тоже закрывает меню. Другие клавиши не должны случайно выбирать действие или попадать в приложение за меню.
- Цель действий 1–5 — активная pane, в том числе вложенная в уже разделённую секцию. Нельзя вместо неё делить всю вкладку: запрос использует конкретный PaneId и top_level=false. Внешние секции сохраняют свою геометрию.
- При делении на три исходная pane остаётся слева или сверху; две новые располагаются после неё. С учётом двух разделителей три рабочие области отличаются размером не более чем на одну ячейку. По оси деления нужно не менее пяти ячеек.
- Предположение для реализации: фокус после успешного деления переходит в крайнюю новую секцию справа или снизу, как при обычном делении на две. Новая pane запускает новый терминальный процесс; состояние уже работающей оболочки не копируется. Уровень прав, домен и изоляция наследуются от исходной pane.
- Обычная вкладка остаётся в обычном домене. Изолированная вкладка продолжает иметь один процесс-хост на вкладку, но он может держать несколько pane. Администраторская вкладка держит все новые pane в своём повышенном процессе; смешанных по правам pane в одной такой вкладке быть не должно.

## Проверенная исходная точка и опасные места

1. Дерево Tab уже умеет рекурсивно делить выбранный лист по индексу. Тест tab_splitting в crates/session/mux/src/model/tab/test.rs делит вложенную pane. Меню может опираться на эту модель.
2. F2 сейчас показывает prompt-оверлей для переименования вкладки. Кликабельные элементы встроенного GUI-модального окна уже есть в NewTabOptions: crates/apps/onlyterm-gui/src/window/termwindow/ui/newtab_options.rs и input/mouseevent/ui_items.rs.
3. Обычные SplitHorizontal и SplitVertical вызывают spawn_command, который запускает отдельную асинхронную задачу и не возвращает результат вызывающему. KeyAssignment::Multiple с двумя такими действиями не обеспечивает порядок, правильную целевую pane и откат.
4. ClientDomain::new_single_pane устанавливает spawnable=false. Mux::resolve_spawn_tab_domain для CurrentPaneDomain поэтому подменяет такой домен доменом по умолчанию. Это уместно для новой вкладки, но недопустимо для деления существующей: оно может потерять изоляцию или повышение прав.
5. Хост --single-pane завершает процесс после PaneRemoved исходной pane и при разрыве связи убирает только её. При нескольких pane нужны ожидание опустения вкладки и очистка всех дочерних процессов, включая случай незавершённого деления.
6. Администраторский WebSocket использует ElevatedSinglePaneAllowList. Он намеренно отвергает SplitPane и SpawnV2. Без проверки безопасности открывать общий SplitPane целиком нельзя.
7. ClientDomain::split_pane игнорирует результат локального tab.split_and_insert через .ok(), а затем регистрирует pane. После успешного удалённого деления локальное дерево может остаться несогласованным.
8. Обработчик клавиатуры предлагает клавишу модальному окну до проверки bypass_lookup. Открытое меню F3 нужно явно закрывать при включении байпаса или иным узким способом гарантировать сквозную передачу; глобально менять поведение всех модальных окон без тестов нельзя.
9. Клик вне активного UIItem сейчас может попасть в терминальную pane даже при модальном окне. Для меню F3 это надо определить явно; безопасный вариант — не передавать такой клик приложению.

## Архитектура решения

### Маршрутизация и модель

- Разделить разрешение домена для новой вкладки и для деления pane. При делении CurrentPaneDomain должен выбирать домен исходной pane и возвращать ошибку, если тот действительно не поддерживает деление; молчаливый переход к default domain запрещён. Не менять spawnable на true у изолированного домена: это снова направит создание новой вкладки в старый процесс.
- Обычные и вложенные деления используют один путь по TabId и PaneId. Проверить цель снова после каждого await: вкладка или исходная pane могли закрыться.
- Для пункта 5 показывать недоступное состояние при единственной pane и повторять проверку прямо перед удалением. Не вызывать существующий CloseCurrentPane для единственной pane: он закроет последнюю секцию и вкладку.

### Изолированный процесс-хост

- Сохранить совместимость существующего CLI-флага --single-pane, но внутренний контракт перевести на «одна вкладка, несколько pane». Не создавать новый ClientDomain или новый хост для каждой подсекции.
- Запомнить TabId созданной вкладки. Закрытие исходной pane не завершает хост, если остались соседние; закрытие последней завершает его. При потере клиента завершить все pane этой вкладки и их дочерние процессы даже если настройка Windows Job Object не сработала.
- Учесть деление, уже находящееся в полёте при разрыве связи: прекратить приём новых запросов, завершить или отменить и очистить начатые операции, затем выйти. Не оставлять процесс, который был создан после снимка списка pane, но до выхода хоста.
- Домен по-прежнему не должен создавать вторую вкладку внутри этого хоста. Проверить запреты на SpawnV2 и перенос между вкладками отдельно от разрешённого деления pane.

### Повышенная вкладка и граница безопасности

- Не разрешать произвольный SplitPane в ElevatedSinglePaneAllowList и не открывать SpawnV2. Предпочтительный путь без нового wire-формата — узко валидируемый запрос деления: исходный PaneId принадлежит единственной размещённой вкладке; command, command_dir и move_pane_id отсутствуют; домен совпадает с текущей pane; top_level=false; размеры допустимы; число pane ограничено разумным пределом.
- Проверять эти условия на границе PDU и непосредственно перед выполнением. Новый процесс запускается сервером по его собственной политике, с тем же повышением прав; клиент не передаёт произвольную команду. Если аудит покажет, что такой поднабор текущего PDU нельзя безопасно отличить, спроектировать отдельный ограниченный запрос и согласовать изменение протокола до реализации.
- Отрицательные тесты должны доказывать, что произвольная команда, путь, чужой PaneId, перенос pane, новая вкладка и превышение лимитов всё ещё отвергаются. При ошибке или разрыве связи не остаётся повышенных дочерних процессов.

### Согласованность клиента и деление на три

- ClientDomain обязан проверять результат локального split_and_insert. При ошибке после успешного ответа сервера закрыть созданную удалённую pane и восстановить синхронизацию дерева; при невозможности восстановления явно разорвать неисправную сессию, а не показывать успешное действие.
- Выделить одну ожидаемую асинхронную операцию для меню; не использовать два независимых spawn_command_impl или Multiple. Захватить TabId и исходный PaneId один раз. Для двух секций использовать тот же механизм с одним шагом.
- Для трёх секций предварительно вычислить размеры по ширине или высоте именно активной pane. Если N — число ячеек по оси, распределить N − 2 рабочих ячеек между тремя pane с разницей не более одной; N < 5 отвергнуть до создания процессов.
- Сначала разделить исходную pane на первую область и правый/нижний остаток, запомнив новую PaneId. Затем разделить этот остаток на среднюю и крайнюю область. Так исходная остаётся первой, а последняя новая pane справа/снизу получает фокус по обычному правилу.
- Если второй шаг не удался, закрыть pane, созданную первым шагом, и вернуть исходную геометрию. Нельзя оставлять половину тройного деления или невидимый процесс. Ошибку показать пользователю, а не только записать в лог.

### Меню и ввод

- Добавить KeyAssignment для меню и описание команды с F3 по умолчанию; пользовательские привязки и disable_default_key_bindings продолжают работать по существующему правилу InputMap.
- Реализовать отдельное встроенное модальное окно с одним перечислением действий. Одна функция преобразует выбор клавиатурой или мышью в действие, чтобы пути не расходились. Для мыши добавить типы UIItem каждой строки и закрытия, использовать hit-test и не удерживать RefCell-заём при cancel_modal или запуске действия.
- Esc, пункт 6 и повторное F3 закрывают меню без побочных эффектов. При активации байпаса меню закрывается, а F3 и цифры затем проходят приложению. Недоступный пункт 5 и неподходящая геометрия не закрывают работающую pane.

## Задачи в порядке выполнения

Каждый этап начинается с теста, который воспроизводимо падает на прежнем поведении, затем с минимального исправления и зелёной проверки затронутых crates. Падение или флейк исправляется в том же этапе.

- [ ] F3-01. Зафиксировать тестами контракт меню, байпаса, наследования режима и геометрию 2/3 секций, включая вложенную pane, нечётные размеры и минимум пять ячеек.
- [ ] F3-02. Разделить маршрутизацию создания вкладки и деления pane; тестом доказать, что изолированная и повышенная pane не переходят в default domain, а новая вкладка всё ещё получает отдельный хост.
- [ ] F3-03. Перевести изолированный хост на жизненный цикл всей вкладки. Тесты: закрытие исходной pane при живых соседях, закрытие последней, потеря клиента, потеря клиента во время деления и очистка всех процессов.
- [ ] F3-04. Ввести ограниченное деление для повышенной вкладки без ослабления запрета произвольного запуска. Добавить позитивные и негативные тесты PDU-политики и исполнения запроса.
- [ ] F3-05. Исправить синхронизацию ClientDomain после удалённого деления и компенсирующую очистку при локальной ошибке. Проверить вложенное дерево и восстановление после отказа.
- [ ] F3-06. Реализовать ожидаемую операцию деления на две/три секции с фиксированным PaneId, точными размерами и откатом второго шага. Покрыть обычный, изолированный и повышенный пути.
- [ ] F3-07. Добавить меню F3, номера, numpad, мышь, недоступное закрытие единственной pane и корректный байпас. Проверить, что клик вне меню не отправляет ввод терминалу.
- [ ] F3-08. Пройти полный Windows CI и ручную приёмку с UAC. Проверить вложенные деления, закрытие каждой секции в разном порядке, исчезновение процесса-хоста после последней, байпас F3 и отсутствие смешения прав.

## Приёмка

- Все пункты меню выполняют ровно указанное действие клавиатурой и мышью; F3 в байпасе достигает приложения. Закрытие меню не меняет дерево.
- Деление любой вложенной pane оставляет остальные области неизменными; новая pane находится в том же домене, процессе вкладки и уровне прав. У изолированной вкладки не появляется дополнительный хост на каждую секцию.
- Ни одна ошибка второго шага, удалённого ответа или локальной вставки не оставляет невидимую pane, половину тройного деления либо осиротевший обычный/повышенный процесс.
- Повышенный канал после изменения по-прежнему отвергает произвольный запуск и перенос между вкладками. Ручной тест с UAC подтверждает реальное поведение, которое нельзя доказать только unit-тестом.
- Выполнить cargo +nightly fmt --all -- --check, cargo clippy --workspace --all-targets --locked -- -D warnings, адресные тесты затронутых crates и cargo test --workspace --locked в поддерживаемой Windows-среде; проверить соответствующие CI workflow. Не запускать искусственную нагрузку.
- Версии проекта и библиотек, релизный тег и push не менять без отдельной просьбы. Реализацию вести небольшими проверяемыми этапами, сохраняя рабочее дерево после каждого.

## Откат и границы

- Если UI ещё не принят, привязку F3 можно отключить без изменения старых команд деления. Изменения домена, сервера и клиента откатываются как согласованный слой только после проверки, что не останется pane в неверном процессе.
- Нельзя считать задачу завершённой только по зелёному cargo test: обязательны тест безопасности повышенного канала, реальный Windows-сценарий с UAC и проверка завершения всех дочерних процессов при закрытии вкладки.
