# План: единые имена пакетов OnlyTerm

Дата исследования: 2026-09-24. Это план; имена, исходники и версии пока не менялись.

## Граница и наблюдения

`cargo metadata --no-deps --format-version 1` показывает 54 пакета workspace: 28 с префиксом `onlyterm` и 26 без него. Ниже классифицированы все 26. Категории описывают рекомендуемую *политику имен*, а не юридическое происхождение каждой строки кода. Для пяти библиотек с MIT, ссылкой на репозиторий WezTerm и отдельной общей областью применения сохранение имени также защищает их возможных внешних потребителей. `window` имеет те же метаданные, но сильнее привязан к приложению: его окончательное решение требует отдельной проверки внешнего использования.

Вне этих 54 пакетов есть `crates/wgpu-hal-vendored` с именем пакета `wgpu-hal`: это `[patch.crates-io]` на одноимённую зависимость, а не кандидат на префикс. `crates/onlyterm-char-props/codegen` исключён из workspace; его отдельный статус следует проверить при общей ревизии инструментов. Путь к crate и имя пакета независимы: раскладку папок следует планировать отдельно.

## Правило

Префикс `onlyterm-` обязателен для собственных внутренних библиотек приложения. Публичные или заимствованные библиотеки сохраняют устойчивые имена до отдельного решения о fork и совместимости. Имена команд и вспомогательных инструментов сохраняются, если их вызывают напрямую. Кандидаты на объединение не переименовываются до решения об объединении; если crate остаётся отдельным, он получает префикс. Не переименовывать весь workspace механически.

У внутренних пакетов конечное состояние должно быть согласованным: `package.name = "onlyterm-foo"`, импорт `onlyterm_foo`, ключ зависимости `onlyterm-foo`. В переходном коммите допустим алиас `foo = { package = "onlyterm-foo", path = "..." }`, сохраняющий импорт `foo`, но его нужно убрать при завершении миграции. Для внутренних библиотек отдельно рассмотреть `publish = false`; отсутствие `publish` сейчас не является свидетельством опубликованного crate.

## Что меняется технически

- `package.name` — идентификатор для `cargo -p`, зависимостей и `Cargo.lock`. Переименование пакета обновит записи lockfile. Путь `crates/codec` можно оставить прежним.
- Имя `lib` по умолчанию равно имени пакета с заменой дефисов на подчёркивания; явное `[lib] name = "codec"` могло бы его сохранить, но оставит разнобой в конечном состоянии. Импорт в Rust, макросы и generated code надо искать отдельно.
- Ключ зависимости может отличаться от имени пакета через `package = "..."`. В `[workspace.dependencies]`, `dependencies`, `dev-dependencies`, `build-dependencies` и платформенных разделах проверить все места. При алиасе ссылки вида `dep:foo` и `foo/bar` используют *ключ зависимости*, что важно для features.
- Имя бинарного target отдельно от `package.name`. Здесь переименование касается библиотек; имена `onlyterm.exe`, `strip-ansi-escapes` и других команд не должны поменяться случайно.
- Имена пакетов зашиты в `cargo -p`: например, генератор `ci/generate-workflows.py` и сгенерированные `.github/workflows/gen_windows*.yml` сейчас называют `window`, `mux`, `procinfo`; `ci/dev-install.ps1` и `ci/update-derived-files.sh` называют CLI-пакеты. Проверить `Makefile`, документацию, `deny.toml`, упаковку и любые фильтры CI по имени пакета. Не редактировать только generated YAML без генератора.
- Сборка локально с alias не доказывает совместимость сторонних пользователей. Переименование опубликованного пакета фактически создаёт другое имя в registry; существующие зависимости, lockfile и ссылки на docs.rs не мигрируют автоматически. Для WezTerm-derived crates сохранить лицензии, атрибуцию, исходный API и имя, пока не проведён отдельный аудит. Не выдавать старое имя за собственный новый пакет.

## Порядок реализации

1. Зафиксировать baseline: `cargo metadata --no-deps --format-version 1`, `git status`, список `cargo -p` и импортов каждого пакета. Сверить параллельный план объединения, чтобы не переименовывать `base91`, `bintree`, `frecency` дважды. Версии не повышать.
2. Первая небольшая партия: `color-funcs` → `onlyterm-color-funcs`, `mux-funcs` → `onlyterm-mux-funcs`, `termwiz-funcs` → `onlyterm-termwiz-funcs`. Это внутренние адаптеры из `crates/api-crates`, с 2, 1 и 5 прямыми потребителями по `cargo metadata`. В рамках одного атомарного изменения каждого пакета поправить корневые и потребительские манифесты, Rust-импорты и ссылки в features, затем `Cargo.lock`. Не использовать временные алиасы, если прямой переход проходит проверки.
3. Следующая партия: `env-bootstrap`, `codec`, `lfucache`, `procinfo`, `ratelim`, `umask`; далее `config`, `mux`, `promise`, `rangeset`. Большие узлы (`config` — 19 прямых потребителей; `promise` — 10) делать отдельными изменениями. После каждой партии проверить скрипты и документацию через поиск старого имени с контекстом: обычные слова `config`, `window` и т. п. нельзя заменять глобально.
4. После решения об объединении обработать три одно-потребительских пакета. `window` решить отдельно после проверки используемости вне этого репозитория и последствий для MIT/WezTerm-идентичности. Общие библиотеки и CLI-инструменты оставить исключениями, зафиксированными здесь.
5. В конце сверить таблицу: все оставшиеся частные библиотеки должны иметь `onlyterm-` в имени пакета, ключе зависимости и Rust-импорте; исключения перечислены явно. Группировку папок выполнять после стабилизации имён или в независимом изменении.

## Проверка и откат

Для каждой партии: `cargo metadata --locked --no-deps --format-version 1` (ожидаемые имена, число пакетов и targets), поиск старых ключей в манифестах/features/CI, `cargo check --locked -p <затронутые пакеты>`, узкие тесты затронутых пакетов и `cargo clippy --locked -p <затронутые пакеты> --all-targets -- -D warnings`. Затем существующие CI-проверки Windows для затронутой области. `git diff --check`; проверить, что не поменялись версии, пути assets, имена бинарников и содержимое лицензий. При необходимости полной уверенности после всех партий выполнить workspace-check один раз.

Откат — вернуть одну партию целиком (манифесты, импорты, lockfile и CI-генератор вместе). Если уже опубликовано новое имя, одного отката в репозитории недостаточно: старый и новый registry-пакеты имеют самостоятельную историю, поэтому публичные crates исключены из автоматической миграции.
