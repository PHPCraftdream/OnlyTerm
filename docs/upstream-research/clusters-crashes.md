# Кластеры: crash/hang/deadlock/leak

Методология: из трёх файлов триажа (`triage-prs.md` — 74 важных PR, `triage-issues-part1.md` —
~230 важных issues, `triage-issues-part2.md` — 427 важных issues) выбраны все записи с классом
`crash`, `hang`, `leak`, `crash/hang`, `hang/perf`, `hang/functional`, `crash/functional`,
`perf/leak`, `perf (memory leak)`, а также записи без явного класса, но по сути описывающие
падение/зависание/утечку/гонку (deadlock, OOM, use-after-free, infinite loop). Все три файла
прочитаны целиком. Ниже — группировка по вероятному общему первопричинному механизму, а не по
формулировке заголовка.

## Кластер: Scale-factor/resize → некорректный или превышающий лимит размер GPU-поверхности

- Участники: PR #7821, Issue #2445, Issue #3687, Issue #4857, Issue #6233, Issue #6489
  (периферийно: Issue #2907 — тот же паттерн, но визуальный глюк, а не краш)
- Механизм: код вычисления пиксельного размера окна/поверхности из scale-фактора (в т.ч. деление
  на scale, как в #2445 "not divisible by scale 2") и/или пользовательские `initial_rows`/`cols`
  (#6489) иногда дают размер, который затем передаётся напрямую в `Surface::configure` (wgpu) или
  в glium-контекст без валидации против лимитов GPU (`max_texture_dimension_2d` и т.п. — на Apple
  Silicon это 16384) или без проверки на нулевые/некорректные значения. Валидационная ошибка внутри
  wgpu/GL, поднятая через FFI-границу (Objective-C→Rust на macOS, `did_resize` callback), не может
  быть размотана как обычная паника — получается abort. Проявляется на разных WM/платформах (Sway,
  GNOME 200%, macOS 15.2) с одним и тем же по сути триггером — "невалидный размер поверхности".
- Готовый фикс в апстриме: PR #7821 ("webgpu: clamp surface dimensions to
  max_texture_dimension_2d") закрывает конкретно случай превышения лимита текстуры на WebGpu-пути.
- Рекомендация: взять клэмпинг из #7821 как базу, но дополнительно (а) применить аналогичный клэмп
  на OpenGL/glium-пути (не только WebGpu), и (б) отдельно проверить арифметику деления на
  scale-фактор в коде ресайза окна (`window/`, `wezterm-gui/src/termwindow/resize.rs`) — вероятно,
  именно она первой порождает "плохой" размер, который потом обваливает создание поверхности.
- Приоритет: high — 5 независимых репортов на разных площадках (Sway/GNOME/macOS), суммарно ~45
  комментариев, все — жёсткие крэши/abort.

## Кластер: Cross-platform крэш при разрушении/потере GPU-контекста окна (teardown ordering)

- Участники: PR #7799 (macOS, window close), PR #7617 (X11, window destroy), PR #7958 (macOS,
  RefCell-реентерабельность в `draw_rect` при быстром resize/repaint — родственный, но отдельный
  баг в том же подмножестве кода жизненного цикла окна/рендера на macOS), Issue #5992 (Windows,
  "opengl context was lost; should reinit"), Issue #7291 (macOS, segfault после выхода из
  lock-screen), Issue #7703 (macOS, краш при уходе в сон в fullscreen), Issue #6480 (краш при
  отключении внешнего монитора), Issue #7519 (Windows, крэш в d3d11.dll при sleep/resume), Issue
  #7949 (Windows, крэш при maximize/minimize)
- Механизм: на всех трёх оконных бэкендах (macOS/X11/Windows) и во всех рендер-бэкендах
  (OpenGL/glium, WebGPU/wgpu, D3D11) есть один и тот же класс гонки: платформенный GPU-ресурс
  (drawable/IOSurface на macOS, EGL-surface на X11, D3D-контекст на Windows) разрушается или
  становится невалидным (закрытие окна, сон/пробуждение, отключение монитора, сброс драйвера), пока
  wezterm-сторонний `RenderState`/glium-контекст всё ещё держит на него ссылку — следующий Drop или
  попытка перерисовки трогает мёртвый хэндл → abort/segfault вместо storičnog переинициализации.
  PR #7958 — отдельный, но родственный по месту (тот же файл `window/src/os/macos/window.rs`,
  тот же "жизненный цикл окна во время resize") баг: реентерабельный `borrow_mut()` вместо
  ссылки на GPU, но эффект тот же класс (SIGABRT в отрисовке).
- Готовый фикс в апстриме: PR #7799 (`render_state.take()` в обработчике `WindowEvent::Destroyed`
  до разрушения GPU-drawable) и PR #7617 (порядок Drop полей на X11) — оба следуют одному и тому
  же рецепту "отпустить ссылку на render-state до/в момент разрушения платформенного ресурса".
  Issue #5992 явно предлагает верное направление ("should reinit" вместо краша).
- Рекомендация: не переносить #7799/#7617 как узкие точечные патчи по отдельности, а вынести общую
  дисциплину ("явно take()/drop() render-state до разрушения platform surface, плюс путь
  реинициализации при потере контекста") в разделяемый паттерн, применяемый на всех трёх
  оконных бэкендах и ко всем триггерам (close/sleep-resume/monitor-change), а не только к close.
- Приоритет: high — самый частый источник "случайных" macOS/Windows-крэшей без repro в issue-трекере.

## Кластер: BlobLease (шрифтовый glyph-кэш) — утечка / зависание / permission-error

- Участники: PR #7955, Issue #5422, Issue #7285, Issue #6426
- Механизм: `wezterm-blob-leases/src/simple_tempdir.rs` хранит glyph/image-blob'ы как
  content-addressed временные файлы с refcounting; логика store/refcount/cleanup некорректно
  обрабатывает конкурентных читателей (на Windows — блокировка файла) и не гарантирует
  своевременную очистку — один и тот же баг lifecycle проявляется тремя симптомами: перезапись
  файла с открытым читателем падает с "Access is denied" на Windows (#7955/PR), удаление лизы, пока
  она ещё используется, полностью останавливает рендер терминала (#5422 — это `hang`, не просто
  визуальный баг), а директория кэша никогда не подчищается и разрастается до 15 ГБ (#6426).
- Готовый фикс в апстриме: PR #7955 ("Fix duplicate blob storage on Windows") — переиспользовать
  существующий blob и инкрементить refcount вместо перезаписи — хорошая база, но чинит только
  Windows-специфичный overwrite-случай.
- Рекомендация: взять #7955 как основу, но провести более широкий аудит refcounting/cleanup
  семантики `SimpleTempDir`, поскольку #5422 (полная остановка рендера) и #6426 (утечка на диск)
  указывают, что проблема шире одного only-Windows edge case.
- Приоритет: high — #5422 буквально останавливает рендер всего терминала.

## Кластер: Windows conpty/pty teardown — зависание при закрытии панели/вкладки

- Участники: PR #5977, PR #7226, Issue #5882, Issue #6190, Issue #5496, Issue #5432
- Механизм: на Windows закрытие панели иногда зависает из-за документированного edge-case
  `conpty.dll` (закрытие хэндлов до завершения псевдоконсольной сессии в неверном порядке — #5977),
  а после многодневных сессий с большим scrollback зависание при закрытии таба/панели усиливается
  синхронной O(n) очисткой scrollback на GUI-потоке (#7226). Оба механизма проявляются одинаково
  для пользователя: "закрыл панель/таб — GUI встал".
- Готовый фикс в апстриме: PR #5977 (правильный порядок закрытия conpty-хэндлов,
  `pty/src/win/{mod.rs,conpty.rs,procthreadattr.rs,psuedocon.rs}`) и PR #7226 (частично — устраняет
  синхронную/O(n) часть, но тело PR обрезано и упоминает третью причину, не до конца описанную).
- Рекомендация: перенести оба PR вместе — они закрывают разные половины одного и того же
  пользовательского симптома ("зависание при закрытии после долгой сессии"), сформулированного в
  задаче почти дословно.
- Приоритет: high.

## Кластер: Mux client-server соединение — зависание/deadlock при коннекте и обслуживании

- Участники: PR #7771, PR #7929, Issue #7388, Issue #858, Issue #4283, Issue #7959, Issue #5225,
  Issue #7264 (Windows-крэш при спавне сессии на mux-сервере — тот же подузел, другой сбой), Issue
  #6513 (слабая связь: "новые окна перестают открываться со временем" — возможно тот же паттерн
  исчерпания/блокировки ресурса mux-соединения)
- Механизм: несколько разных, но архитектурно родственных точек блокировки в mux client/server
  IPC-пути — `process_async` (сервер) и `client_thread_async` (клиент) читают/пишут в одной задаче
  и взаимно блокируются при большом числе панелей (#7771); открытый synchronized-update hold-буфер
  блокирует ответы на capability-запросы (#7929); коннект/attach к недоступному домену или к
  `proxy_command` (например, `wsl.exe`), похоже, делает блокирующий вызов на потоке, от которого
  зависит весь GUI event loop, без таймаута (#4283, #7959, #5225, #858). Общий корень: mux
  connect/attach и обслуживание per-connection I/O выполняются синхронно на критичном для GUI
  потоке без таймаутов.
- Готовый фикс в апстриме: PR #7771 (развести чтение/запись по разным задачам) и PR #7929 (отдельный
  путь ответа на capability-запросы, не зависящий от hold-буфера) закрывают свои конкретные случаи,
  но не универсальны для #4283/#7959/#5225.
- Рекомендация: #7771 и #7929 взять как есть (готовые точечные фиксы), а для оставшейся части
  кластера сделать общую работу — обернуть весь connect/attach/per-connection I/O в async-задачи с
  таймаутом, никогда не блокируя поток, от которого зависит отрисовка GUI.
- Приоритет: high — единственное "плохое" соединение может полностью повесить весь GUI.

## Кластер: WebGPU/wgpu — крэши инициализации и несовместимости с драйвером/адаптером

- Участники: Issue #3425, Issue #4825, Issue #6662, Issue #7819, Issue #3229, Issue #4290, Issue
  #7528 (шире — ломает и OpenGL/Software после апдейта AMD-драйвера, не только WebGpu), Issue #6205
  (сегфолт на конкретном AMD-драйвере)
- Механизм: путь создания/конфигурации WebGpu-поверхности (`wezterm-gui/src/termwindow/webgpu.rs`)
  не валидирует и не мягко обрабатывает несовместимость адаптера/поверхности (неподдерживаемые
  форматы, лимиты размера, "виртуальные" адаптеры RDP, специфичные баги драйверов AMD/Intel) — вместо
  граceful fallback (например, на OpenGL/Software) или внятной ошибки паника/validation error из
  wgpu пробрасывается наверх и валит процесс. #7528/#6205 показывают, что проблема иногда шире
  чисто WebGpu-пути (после апдейта AMD-драйвера ломается и OpenGL) — то есть где-то есть общий слой
  детекции возможностей GPU, который тоже нужно проверить.
- Готовый фикс в апстриме: частично — PR #7821 (см. кластер выше) закрывает только подслучай
  превышения лимита размера текстуры.
- Рекомендация: нет единого готового фикса; нужно обернуть создание wgpu-адаптера/поверхности и
  `Surface::configure` в путь, возвращающий `Result` с fallback на другой front_end, вместо того
  чтобы полагаться на панику wgpu. Клэмп из #7821 использовать как один из нескольких guard'ов.
- Приоритет: high — стартовый крэш = полная невозможность запустить приложение на затронутом
  железе, повторяется на очень разных GPU-вендорах/ОС, что указывает на системный пробел, а не
  россыпь независимых платформенных багов.

## Кластер: Mux — бесконечный цикл подгонки размера панелей / панели нулевого размера

- Участники: PR #6062, Issue #7765, Issue #4878
- Механизм: алгоритм подгонки размеров панелей в `mux/src/tab.rs` (используется и программным
  `AdjustPaneSize`, и интерактивным перетаскиванием границы сплита) работает через относительные
  ("дельта") итеративные корректировки; когда размер панели достигает нуля (что #4878 показывает —
  не предотвращается) или уходит в отрицательные значения, итеративный алгоритм перераспределения
  оставшегося пространства между соседними панелями может не сходиться и крутиться бесконечно
  (#7765 — буквально dead loop, зависание) вместо того чтобы клэмпить к минимальному размеру. PR
  #6062 документирует близко родственную проблему в том же самом подузле (дельты применяются к уже
  устаревшему состоянию при быстрой серии ресайзов).
- Готовый фикс в апстриме: нет готового смёрженного фикса ни для одного из трёх; PR #6062
  предлагает архитектурное решение — перейти с дельт на абсолютные позиции в протоколе ресайза
  сплита.
- Рекомендация: если реализовать #6062 (переход на абсолютные позиции), это, вероятно, попутно
  устранит и невозможность получить нулевой/отрицательный размер панели (#4878), и как следствие —
  бесконечный цикл в #7765, поскольку все три растут из одного и того же дельта-итеративного дизайна.
- Приоритет: high — #7765 это в буквальном смысле зависший GUI-поток.

## Кластер: Windows/Unix portable-pty — крэш/abort при ошибке spawn/exec

- Участники: PR #7743, Issue #7742, Issue #6783, Issue #5107, Issue #7025, Issue #4364
- Механизм: путь обработки ошибок спавна процесса в `portable-pty` хрупок сразу в нескольких
  местах на обеих платформах: на Unix неудачный `exec()` иногда приводит к `abort()` вместо
  возврата `Result::Err` (#7742), причём диагностический pipe, по которому могла бы прийти реальная
  причина ошибки, до этого закрывается pre-exec хуком вместе со всеми fd > 2 (баг, который чинит
  #7743); на Windows — невалидный хэндл при `clone_killer` (#5107), общая регрессия спавна в
  portable-pty 0.9.0 (#6783), сбои запуска команд (#7025) и процессы, "не выходящие чисто"
  (#4364) — всё это один и тот же слабо протестированный участок кода (процесс-спавн), просто с
  разными конкретными триггерами по платформам.
- Готовый фикс в апстриме: PR #7743 (пометить унаследованные fd как `CLOEXEC` вместо закрытия,
  сохраняя диагностический канал) — трезво оформленный, с regression-тестом, закрывает Unix-половину.
- Рекомендация: #7743 переносить как готовый фикс; для Unix-половины #7742 (abort вместо
  Result::Err) в апстриме готового фикса нет — писать самостоятельно, заменив `abort()` на
  распространение ошибки. Windows-часть (#6783/#5107/#7025/#4364) не имеет единого корня —
  требует отдельного разбора по каждому репорту.
- Приоритет: high — эта же ошибка спавна лежит в основе доброй половины нечитаемых "не могу
  запустить wezterm" репортов, так как без диагностического канала причина невидима пользователю.

## Кластер: Wayland event loop — фриз на старте (Vulkan/WebGpu) и крэш по протокольной ошибке

- Участники: PR #7735, Issue #7969, Issue #7725
- Механизм: два родственных, но не идентичных механизма хрупкости Wayland-интеграции: (а)
  throttling `wl_surface.frame()`-коллбэка через SCTK рассчитан на EGL/`eglSwapBuffers`, и вступает
  в конфликт с независимым управлением commit'ами surface в Vulkan/WebGpu WSI
  (`vkQueuePresentKHR`) — окно виснет на старте или становится неотзывчивым, особенно на tiling-
  композиторах (Niri) — это чинит PR #7735; (б) диспетчер Wayland-протокола не обрабатывает
  некоторые нестандартные/большие сообщения протокола надёжно, что приводит к жёсткому краху вместо
  восстановимого отключения (#7969 — protocol error 71 на mutter/GNOME, #7725 — `wl_display`
  message length exceeds 4096 при большом выводе curl на Hyprland).
- Готовый фикс в апстриме: PR #7735 закрывает конкретно (а) — конфликт frame-callback/Vulkan WSI.
  Для (б) готового фикса нет.
- Рекомендация: #7735 переносить как есть. (а) и (б) — раздельные баги в одном подузле (Wayland
  dispatch loop), не смешивать в одном патче; для (б) нужен отдельный аудит обработки protocol
  errors/oversized-сообщений в клиенте Wayland-протокола.
- Приоритет: medium-high (полный фриз при старте на Wayland+Vulkan — весомый, но нишевый по
  сочетанию платформа+бэкенд случай).

## Кластер: Утечки памяти в image/GPU-кэшах при долгой сессии (семейство, вероятно разные фиксы)

- Участники: Issue #4826 (утечка VRAM в wgpu), Issue #7400 (утечка при kitty+gif), Issue #5128
  (imgcat не освобождает память изображения после закрытия сессии); слабая связь: Issue #7363
  ("использует 22 ГБ RAM"), Issue #6925 ("со временем всё тормозит, приходится перезапускать") —
  вероятно одни из этих трёх конкретных утечек, но без repro нельзя уверенно приписать к одной.
- Механизм: это, честно говоря, **не один и тот же код-путь** — VRAM-утечка (#4826) похожа на
  GPU-текстурный кэш, не освобождающий ресурсы при уничтожении панели/смене контента; утечка на
  kitty+gif (#7400) — это, вероятно, накопление фреймов анимации в кэше плейсментов image

## Кластер: Windows — зависание при смене раскладки клавиатуры (WM_INPUTLANGCHANGEREQUEST)

  `ActivateKeyboardLayout`, возвращает `Some(0)` — прямой, тривиальный фикс.
- Рекомендация: перенести #7066 как есть; #6786, скорее всего, закроется тем же патчем.
- Приоритет: high (deadlock от переключения раскладки — базовый сценарий для мультиязычных
  пользователей).

## Кластер: Необработанные ошибки уровня ОС валят процесс целиком

- Участники: Issue #5263, Issue #3107, слабая связь: Issue #1839 (mux-сервер молча падает при

- Приоритет: high — фриз от простого удержания клавиши это один из самых базовых пользовательских
