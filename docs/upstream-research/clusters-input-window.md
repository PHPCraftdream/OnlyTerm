# Кластеры: input/window/focus/clipboard

Методология: прочитаны целиком все три файла триажа (`triage-prs.md`, `triage-issues-part1.md`,
`triage-issues-part2.md`, ~5750 строк). Из них выбраны все PR/issues, относящиеся к категории
ввод (клавиатура/мышь) / управление окном (resize/decorations/DPI/fullscreen/focus) /
clipboard / tab-mux-lifecycle, и сгруппированы по вероятному общему первопричинному механизму,
а не по формулировке заголовка. Кластер, уже отмеченный в `triage-prs.md`
("PaneFocused notification storm"), взят как отправная точка и расширен пересекающимися issues,
которые исходные агенты по этой категории не связали друг с другом при чтении по отдельности.

## Кластер: PaneFocused notification feedback loop / focus storm
- Участники: PR #7871, PR #7763, PR #6349, PR #7590, Issue #4484, Issue #4390, Issue #3994,
  Issue #6885, Issue #7096
- Механизм: смена фокуса панели (`PaneFocused`) уведомляет mux/GUI/клиента, что порождает встречное
  уведомление, которое интерпретируется как новая смена фокуса → зацикливание/шторм. Проявляется при
  массовом уничтожении панелей, множественных mux-клиентах, задержках домена, быстром переключении
  вкладок/направлений навигации и при реконнекте к мультиплексору. Issue #4484 (постоянная смена
  фокуса без ввода), #4390 (быстрое переключение направлений → фокус "дребезжит"), #3994 и #7096
  (неконтролируемое размножение переключений/вкладок на mux-сервере) и #6885 (мигание текста и
  самопроизвольное переключение вкладок при реконнекте к мультиплексору с Linux) — все являются
  разными манифестациями одного и того же feedback loop, просто с разных сторон конвейера
  (клиент/сервер/reconciliation/навигация).
- Готовый фикс в апстриме: PR #7871 — самая зрелая, третья итерация фикса (тестирована вручную и
  через CLI на регрессию #4390/#4737), рекомендуется брать именно её, а не #7763 (superseded) или
  параллельные #6349/#7590 (конкурирующие/пересекающиеся решения того же класса — см. заметку в
  `triage-prs.md`: не портировать несколько решений параллельно).
- Приоритет: high.

## Кластер: window_decorations — флаг RESIZE трактуется как RESIZE|TITLE
- Участники: Issue #3936, Issue #6920, Issue #6578, Issue #6105, Issue #5419
- Механизм: парсинг/интерпретация битовых флагов конфигурации `window_decorations` в общем
  (платформонезависимом) config-коде трактует `"RESIZE"` как включающий также `TITLE`, либо не
  применяет флаг вовсе при передаче через CLI-override (#6105) — то есть один и тот же баг разбора
  флагов проявляется на X11/Gnome (#3936), в общей формулировке (#6920), на NixOS/предположительно
  Wayland (#6578) и как отсутствие эффекта CLI override (#6105). #5419 (заголовок по умолчанию не
  показывается на Wayland) может быть тем же кодом с противоположным симптомом (обратная сторона той
  же логики разбора флагов).
- Готовый фикс в апстриме: не найден среди PR, попавших в выборку 74 "важных" — эту группу issues
  придётся чинить с нуля, начиная с чтения кода разбора enum/bitflags `WindowDecorations` в
  `window`/`config` крейтах.
- Приоритет: medium-high (базовая, часто используемая опция конфигурации не работает предсказуемо
  на нескольких платформах одновременно).

## Кластер: Kitty keyboard protocol — потеря Composed-клавиш (CJK/emoji picker ввод)
- Участники: PR #7944, PR #7915, PR #7542, Issue #5224
- Механизм: `encode_kitty()` не имеет ветки для `KeyCode::Composed` (символ от IME/emoji picker без
  "сырого" события) — падает в catch-all, который требует `self.raw` (всегда `None` для таких
  событий), функция молча возвращает пустую строку. Отдельно #7542 показывает, что панели через mux
  идут другим кодовым путём и вовсе не кодируют kitty-протокол. Issue #5224 (нельзя ввести китайский
  иероглиф через Fcitx5 при включённом kitty keyboard) — прямая манифестация того же дефекта
  Composed-ветки.
- Готовый фикс в апстриме: PR #7944/#7915 — конкурирующие идентичные по сути реализации фикса
  (добавление match-ветки для `Composed`), портировать любую; #7542 отдельно чинит mux-путь кодирования.
- Приоритет: high (полная потеря ввода CJK-текста — серьёзная регрессия функциональности).

## Кластер: IME-переключение вызывает deadlock/зависание (WM_INPUTLANGCHANGEREQUEST)
- Участники: PR #7066, Issue #6786
- Механизм: переключение раскладки клавиатуры через `im-select` и подобные шлёт
  `WM_INPUTLANGCHANGEREQUEST` через `PostMessage` на Windows; сообщение не обрабатывается явно и
  падает в `DefWindowProcW`, вызывая deadlock. Issue #6786 ("Stuck when switching input method using
  im-select") — это именно та жалоба, для которой PR #7066 является прямым исправлением
  (добавляет case в `do_wnd_proc`, вызывает `ActivateKeyboardLayout`, возвращает `Some(0)`).
- Готовый фикс в апстриме: PR #7066 — тривиальный, прямое попадание.
- Приоритет: high.

## Кластер: IME-композиция (preedit/committed text) — хрупкий конвейер в нескольких местах
- Участники: PR #7494, PR #7556, Issue #3411, Issue #7358, Issue #6433, Issue #6222, Issue #7173,
  Issue #6228, Issue #7695
- Механизм: несколько независимых, но родственных дефектов в обработке IME-композиции — preedit-текст
  не коммитится перед движением курсора/кликом (macOS, #7494), IME-скоммиченный текст (`Composed`)
  теряется в оверлеях ввода вроде `PromptInputLine` (#7556, #7173), при удалении всей композиции
  остаётся "хвост" последнего символа (#6433), при составной compose-последовательности выводится
  только последний символ (#6222), паника при завершении ввода через IME (#7358 — самый серьёзный
  симптом этой семьи), регрессия рендера katakana-глифов через CharSelect на macOS Sequoia (#6228),
  OSC12 игнорируется после переключения IME (#7695). Общего единого фикса нет — это семейство
  дефектов в разных входных точках одного и того же конвейера (preedit-состояние, коммит текста,
  маршрутизация в активную панель/оверлей).
- Готовый фикс в апстриме: частичные — PR #7494 (macOS preedit timing), PR #7556 (маршрутизация
  Composed-текста в prompt-оверлеи); #3411/#7358/#6433/#6222/#7173/#6228/#7695 фикса не имеют.
- Приоритет: medium-high (сумма симптомов бьёт по всем CJK/сложным IME пользователям; #7358 —
  краш).

## Кластер: Wayland — дублирование клавиатурных событий с OpenGL-рендерером
- Участники: PR #7435, Issue #3609, Issue #6725
- Механизм: гонка в event loop — фиксированный порядок обработки (сначала `SPAWN_QUEUE`, затем
  Wayland dispatch) при быстрых key press/release (~200мс) приводит к дублированию клавиатурных
  событий (Ctrl+U скроллит дважды, Enter срабатывает дважды). Воспроизводится только с OpenGL, не с
  WebGPU. Issue #3609 — общая жалоба на дублирование ввода, явно отсылающая к #6725 (тот же баг на
  Wayland) как к тому же классу.
- Готовый фикс в апстриме: PR #7435 — требует анализа порядка event loop, но направление фикса ясно.
- Приоритет: high (гонка данных, дублирующая пользовательский ввод).

## Кластер: Key-repeat — таймер/state machine ломается на границах состояний
- Участники: PR #7487, Issue #4061, Issue #5942, Issue #5559
- Механизм: логика key-repeat таймера (общая для нескольких платформ) не всегда корректно
  отменяет/сбрасывает состояние на переходах: не останавливается после закрытия окна на Wayland
  (#7487, попутно течёт хэшмап окон), залипает при быстром нажатии двух клавиш подряд (#4061,
  явно регрессия — "again" в заголовке), приводит к полному зависанию (#5942) или большой задержке
  обновления GUI (#5559) при автоповторе.
- Готовый фикс в апстриме: PR #7487 — закрывает только Wayland-случай (остановка таймера при закрытии
  окна); #4061/#5942/#5559 фикса не имеют, требуют отдельного расследования state machine key-repeat.
- Приоритет: high (зависания и залипание — не просто неудобство).

## Кластер: Крэши при разрушении окна из-за порядка teardown GPU-контекста
- Участники: PR #7958, PR #7799, PR #7617, Issue #5992
- Механизм: три независимых, но однотипных бага — код разрушения окна/рендер-стейта дергает GPU-API
  (make_current/CGLUpdateContext/EGL) после того, как соответствующий нативный handle уже мёртв или
  недоступен: macOS (`RefCell` reentrancy panic в `draw_rect` при rapid resize/repaint, #7958),
  macOS SIGABRT при закрытии окна из-за неверного порядка Drop `RenderState`/IOSurface (#7799),
  X11 use-after-free — glium-контекст переживает X11-хендл (#7617). Issue #5992 (Windows: "opengl
  context was lost; should reinit" крэш вместо восстановления) — тот же класс проблемы с
  недостающей обработкой потери контекста, но на Windows/D3D пути.
- Готовый фикс в апстриме: PR #7958 (trivial — сузить время жизни borrow guard), PR #7799 (needs
  adaptation — `render_state.take()` в правильном месте), PR #7617 (needs adaptation — порядок
  Drop полей); #5992 фикса не имеет.
- Приоритет: high (крэши, один из них — потенциальный use-after-free).

## Кластер: Зависания/крэши при закрытии таба/панели + сломанная защита can_close_without_prompting
- Участники: PR #5977, PR #7226, PR #7398, Issue #5882, Issue #6190, Issue #5496, Issue #5432,
  Issue #6094, Issue #7847, Issue #6198
- Механизм: несколько независимых причин зависаний/крэшей именно в момент закрытия таба/панели —
  на Windows конкретный порядок закрытия handle'ов conpty вызывает зависание (#5977, соответствует
  жалобам #5882/#5496), синхронное удаление таб/панели в GUI-потоке плюс O(n) очистка scrollback
  после долгих сессий (#7226, соответствует #6190/#5432), гонка тайминга при вызове
  `CloseCurrentTab`/`move_to_new_window` приводит к крэшу (#6094, #7847). Отдельно #7398 — чтение
  `/proc/<pid>/exe` для привилегированного процесса без повышенных прав самого wezterm всегда
  возвращает пустой путь, из-за чего `can_close_without_prompting` неверно считает, что "опасного"
  дочернего процесса нет, и таб закрывается без подтверждения — это баг именно в safety-проверке
  того же lifecycle-пути, и он попадает прямо в модуль `procinfo`, который мы недавно рефакторили
  (коммит `0894be2c4`, iterative tree ops). #6198 (подтверждение закрытия не работает для tmux в
  единственной вкладке) — родственный дефект той же самой safety-проверки.
- Готовый фикс в апстриме: PR #5977 (needs adaptation, несколько файлов `pty/src/win`), PR #7398
  (trivial, fallback-чтение argv0 — стоит взять заодно, раз модуль уже трогали), PR #7226 (needs
  adaptation, диагностика неполная — 3-я причина обрезана в теле PR).
- Приоритет: high — совпадает буквально с формулировкой "зависания после долгих сессий" и попадает
  в код, который мы недавно рефакторили.

## Кластер: Крэш при нецелочисленном/экстремальном scale factor
- Участники: Issue #2445, Issue #3687, Issue #6233, Issue #4857, PR #7821 (частично смежный)
- Механизм: код вычисления размеров/quad'ов в рендер-пайплайне не выдерживает нецелочисленный или
  крайний scale factor — крэш при делении на нецелый scale (Sway, #2445), крэш при scale>1 с
  включёнными CSD (#3687), крэш всех окон при открытии из Gnome launcher на 200% масштабе (#6233),
  нестабильный крэш при ресайзе с neovim на тайловом WM (#4857). PR #7821 (clamp surface dimensions
  to `max_texture_dimension_2d` для wgpu на macOS+tiling WM+Retina) решает родственный, но не
  тождественный симптом того же класса — переполнение/некорректный размер поверхности при
  ретайле на многомониторных Retina-конфигурациях; вероятно смежная, но отдельная причина.
- Готовый фикс в апстриме: PR #7821 закрывает только wgpu/webgpu-specific случай; #2445/#3687/#6233/
  #4857 фикса не имеют, требуют отдельного разбора арифметики scale-factor в общем render/window коде.
- Приоритет: high (краш — независимо от того, на каком WM впервые замечен).

## Кластер: Живое перетаскивание окна между мониторами с разным DPI — resize feedback loop
- Участники: PR #7883, Issue #1983, Issue #5022, Issue #6567, Issue #3956, Issue #2907,
  Issue #3396, Issue #7281
- Механизм: при перетаскивании окна между мониторами с разным DPI посреди drag возникает feedback
  loop в resize-коде (`live_resizing → scaling_changed() → set_inner_size() → SetWindowPos`), окно
  "зацикливается" и разъезжается/зависает/дёргается. PR #7883 явно описывает Windows-механизм;
  Issue #1983 (эрратичные прыжки/ресайз между мониторами), #5022 (временное зависание при
  перетаскивании между 3840x2160 и 1920x1200 на Windows), #6567 (проблемы ресайза/titlebar в
  мультимониторе), #7281 (GlazeWM, тот же паттерн) — прямые манифестации на Windows; #3956 (125%
  scale "с ума сходит"), #2907 и #3396 (глючное/тормозное перетаскивание на 150% и на macOS) —
  вероятно тот же класс feedback loop, но на других платформах/бэкендах.
- Готовый фикс в апстриме: PR #7883 (needs adaptation — гасить один из путей ресайза во время drag),
  закрывает Windows-случай; кросс-платформенные манифестации (macOS/иные Linux WM) фикса не имеют.
- Приоритет: medium-high (не крэш, но делает мультимониторные конфигурации почти неюзабельными).

## Кластер: macOS — сон/пробуждение/блокировка экрана ломают размер и позицию окна на внешнем мониторе
- Участники: Issue #4633, Issue #6309, Issue #2958, Issue #6555
- Механизм: обработка уведомления о смене конфигурации дисплеев (sleep/wake, screen lock/unlock) на
  macOS в связке с внешними мониторами разного DPI пересчитывает размер/позицию окна неверно —
  непрошеный ресайз после выхода из сна (#4633, дубль #6309), неверный начальный размер терминала
  при нескольких экранах (#2958), окно оказывается не на своём месте после блокировки экрана в
  мультиразрешении (#6555). Отличается от кластера "живое перетаскивание" (#7883) тем, что триггер —
  системное событие reconfiguration, а не пользовательский drag.
- Готовый фикс в апстриме: не найден.
- Приоритет: medium.

## Кластер: Фундаментальная порча рендера при ресайзе во время активного вывода (давняя, нерешённая тема)
- Участники: Issue #922, Issue #1265, Issue #2659, Issue #3368, Issue #3033, Issue #6869,
  Issue #4323, Issue #2987, Issue #4265, Issue #7630, Issue #3224, PR #7177 (кандидат на общий root
  cause)
- Механизм: при ресайзе окна во время активного вывода в pty (например, `ping`, длинный лог) контент
  дублируется/пропадает/дрожит/затирает сам себя — старая (issue #922, #1265 — из самых давних в
  репозитории), стабильно воспроизводимая серия жалоб на один и тот же класс: рассинхронизация
  reflow/redraw-кода с приходящими данными PTY во время ресайза. #2987/#4265 (промпт неверно
  перерисовывается после ресайза) и #7630 (позиция скролла сбрасывается на низ при ресайзе на
  hyprland) и #3224 (неудобное поведение скролла при ресайзе) — вероятно та же корневая причина с
  разными видимыми симптомами. PR #7177 (`Align with_phys_lines()'s implementation with
  with_phys_lines_mut()`) чинит рассинхронизацию офсета второго диапазона `VecDeque` в
  `Screen::with_phys_lines()` — операция, которая читается именно при обрезании/чтении scrollback
  во время reflow, поэтому это правдоподобный (хотя не подтверждённый напрямую апстримом) кандидат
  на частичное устранение корня этого кластера.
- Готовый фикс в апстриме: нет прямого fix-PR для этого класса; PR #7177 — наиболее вероятный
  частичный кандидат (рассинхронизация чтения scrollback), стоит попробовать первым.
- Приоритет: high (потеря/порча контента при ресайзе — фундаментальный, часто воспроизводимый баг).

## Кластер: Неверная позиция курсора после ресайза+reflow в alt-screen (DECSC/DECRC)
- Участники: Issue #6669, Issue #5100, Issue #6623
- Механизм: сохранение/восстановление позиции курсора (DECSC/DECRC) не учитывает корректно reflow,
  произошедший между save и restore, особенно в alternate screen mode — курсор оказывается не там,

  ("Cursor position incorrect after DECSC, resize with reflow, then DECRC", "Bad cursor position when
  terminal is resized while in alternate mode", "Resize bug - with replication").
- Готовый фикс в апстриме: не найден.
- Приоритет: medium-high (нарушение корректности VT100-эмуляции, задевает full-screen TUI-приложения).

## Кластер: Ресайз панелей рассинхронизирован через mux/remote-domain
- Участники: Issue #5142, Issue #6666, Issue #5117, Issue #4723, Issue #3694, Issue #7331,
  Issue #6884, Issue #6052, Issue #3671, Issue #5011
- Механизм: RPC-путь ресайза панелей через mux-протокол (в отличие от локального ресайза) не
  корректно пересчитывает/распространяет пропорциональные размеры — общий паттерн: ресайз через
  unix-domain mux "имеет проблемы" (#5142), с neovim внутри (#6666), при реаттаче к домену размеры
  части панелей неверны (#5117), ресайз домена через `wezterm connect` ломается (#4723), производительность
  и расчёт размеров неверны при ресайзе через MUX-сервер (#3694), крайне медленный ресайз remote-сессий

## Кластер: Санитизация bracketed paste / порча вставляемого содержимого
- Участники: PR #7859, Issue #7784, Issue #3510, Issue #7921, Issue #7078
- Механизм: "обеззараживание" (defanging) bracketed-paste маркеров (`\x1b[200~`/`\x1b[201~`) в
  `send_paste` делает один проход `str::replace`, не ловящий вложенные конструкции — можно "убежать"
  из paste-режима внедрённой в скопированный текст escape-последовательностью (security-класс баг,
  #7859 чинит, Issue #7784 — независимо заведённая жалоба на ту же неполноту санитизации). Смежные,
  но не идентичные по источнику проблемы: менеджер буфера обмена Windows добавляет лишний
  `^[[200~` при вставке (#3510), `~` вставляется как control-символ 0x1E на Windows+WSL (#7921),
  Win+V (история буфера обмена Windows) добавляет null+newline (#7078) — все они про "мусор/лишние
  байты в пути вставки", возможно устраняемые более полным циклом defang-а из PR #7859, даже если
  их непосредственный источник — не тот же код.
- Готовый фикс в апстриме: PR #7859 — обёртывает текущую логику в цикл до fixed point, самый зрелый
  security-фикс кластера; #3510/#7921/#7078 отдельного фикса не имеют и нуждаются в проверке, решает
  ли их и цикл до fixed point.
- Приоритет: high (#7859 — настоящий injection-класс security баг, тривиален к переносу).
