# Кластеры: rendering/font/visual/perf

Методология: прочитаны целиком все три источника (`triage-prs.md`, `triage-issues-part1.md`,
`triage-issues-part2.md`, ~5750 строк). Отобраны все записи из подмножества "важное" (~886 штук),
относящиеся к рендеру/визуальным артефактам/шрифтам/цветам/гамме/DPI-масштабированию рендера/
тормозам/CPU-нагрузке — по полю `Класс:` там, где оно проставлено (`visual`, `perf`, `leak`,
комбинации типа `visual/functional`, `hang/perf`), и по содержанию там, где класс не указан
(triage-prs.md использует другой формат записи). Записи сгруппированы по вероятному общему
первопричинному коду/механизму, а не по совпадению формулировок заголовков.

Общий контекст архитектуры (из triage-prs.md): наш форк заменил freetype→swash, harfbuzz→rustybuzz,
cairo→tiny-skia (собственный `Painter` поверх tiny-skia + отдельные модули `colr.rs`/`colr_paint.rs`
для цветных шрифтов). `fontconfig` — единственная оставшаяся C-зависимость (используется как есть).
Большинство багов ниже живут в **нашем собственном коде** поверх этих библиотек (onlyterm-gui,
onlyterm-font metrics/fallback-логика, window-крейт, mux/протокол), а не внутри самих
freetype/harfbuzz/cairo — поэтому миграция сама по себе **не** автоматически чинит подавляющее
большинство этих багов; если явных оснований для "неактуально" нет, ниже стоит консервативная
пометка "требует ревалидации на новом стеке", а не "исправлено".

## Кластер: GPU-контекст lifecycle crashes при закрытии/пересоздании окна
- Участники: PR #7958 (macOS SIGABRT, RefCell reentrancy в `draw_rect`), PR #7799 (macOS SIGABRT,
  OpenGL teardown ordering при закрытии окна), PR #7617 (X11 EGL surface use-after-free при
  уничтожении окна)
- Механизм: во всех трёх — `RenderState`/GL-контекст переживает окно (или наоборот) из-за
  неверного порядка `Drop`/явного `.take()` в обработчике закрытия/ресайза окна; конкретные API
  разные (macOS CGL, X11 EGL), но природа бага одна — teardown-ordering между window handle и GPU
  render context.
- Актуально для нашего стека: да, полностью — это window/GPU-backend код (glium/OpenGL), не
  затронутый font-миграцией.
- Готовый фикс в апстриме: да, все три PR — конкретные, локальные патчи (сузить borrow guard /
  `.take()` в правильном месте / поправить порядок Drop).
- Приоритет: high.

## Кластер: Рендер-корректность при ресайзе окна/панели (jitter, потеря/дублирование содержимого)
- Участники: Issue #922 (contents jitter при ресайзе), #1265 (re-draw issue on resize), #2659
  (lines disappear when resizing), #3033 (content overwrites itself during resize while output is
  active), #3224 (unhelpful scrolling behaviour on resize), #3368 (laggy trailing effect/визуальный
  шлейф при ресайзе), #4323 (glitchy rendering when resizing), #6869 (buggy rendering resizing
  panes), #5138 (graphic glitch при маленьком размере окна — edge case той же логики), #5471
  (смена font_size во время активного вывода ломает интерпретацию новых строк — reflow race),
  #5100/#6669/#6623 (некорректная позиция курсора после ресайза/reflow в alt-screen — три разных
  репорта одного и того же класса рассинхронизации курсора с новой геометрией).
- Механизм: перерасчёт layout (reflow строк, позиция курсора, quad-буфер для отрисовки) не
  атомарен относительно самого события ресайза — новый кадр может отрисоваться до завершения
  reflow, либо reflow не пересчитывает курсор/выделение корректно, что даёт "рваный"/устаревший
  кадр, видимые артефакты или потерянные строки. Старая (issue #922 из ранних версий) и очень
  часто повторяющаяся тема.
- Актуально для нашего стека: да — это term/core reflow + onlyterm-gui repaint scheduling, код не
  трогался font/rasterizer-миграцией.
- Готовый фикс в апстриме: нет единого — судя по количеству дублей (7+ независимых репортов за
  несколько лет), апстрим тоже не закрыл эту тему одним патчем; нужен собственный root-cause анализ
  порядка reflow→repaint.
- Приоритет: high — старый, фундаментальный, у пользователя явно упомянут как раздражающий паттерн.

## Кластер: Mux-domain — задержка/некорректный размер при ресайзе
- Участники: Issue #3694 (проблемы производительности и неверный расчёт размеров при ресайзе через
  mux-сервер), #7331 (ресайз в mux-сессиях очень медленный)
- Механизм: ресайз в mux-домене требует круговой сетевой/IPC round-trip (клиент→сервер→ack) вместо
  локального пересчёта — задержка и/или временно неверный размер, отдельный механизм от чисто
  локального рендер-ресайза выше.
- Актуально для нашего стека: да — mux/onlyterm-client код не менялся миграцией.
- Готовый фикс в апстриме: нет, требуется профилирование протокола ресайза в mux.
- Приоритет: medium-high.

## Кластер: Font-fallback — silent failure / крэш на недоступном или отсутствующем шрифте
- Участники: Issue #7963 (паника при ACL-protected fallback-шрифте Windows), #6157 (паника при
  fallback-шрифте, удалённом во время работы — тот же класс, что #7963), Issue #5990 (все глифы —
  "тофу" на NixOS, вероятно тихий отказ загрузки шрифта), #4768 (не находится fallback для
  некоторых кодпоинтов), #5341 (несогласованный выбор fallback на macOS), #6465 (fallback-шрифт не
  находится из-за регистра имени), #5106 (не рендерится редкий unicode-математический символ —
  нет fallback).
- Механизм: логика выбора/загрузки fallback-шрифта (`onlyterm-font`) не устойчива к ошибкам
  доступа/отсутствия/специфики системы — либо падает с паникой, либо тихо возвращает пустой глиф
  ("тофу"), либо выбирает не тот шрифт.
- Актуально для нашего стека: **#7963 и #6157 — вероятно уже исправлены** нашим недавним коммитом
  `5752050b8` ("onlyterm-font: skip unreadable fallback font candidates instead of erroring out",
  явно фиксит #7963 и по описанию покрывает тот же код-путь, что и #6157) — стоит лишь добавить
  regression-тест на сценарий #6157 (шрифт исчез после старта, а не был недоступен с самого
  начала). Остальные (#5990, #4768, #5341, #6465, #5106) — **другие failure-моды** той же
  подсистемы (не "недоступный файл", а "неверный/отсутствующий выбор шрифта на этапе matching"),
  фикс их не закрывает, требуется отдельная проверка.
- Готовый фикс в апстриме: нет (кроме уже перенятого нами `5752050b8`, который не апстримный PR, а
  наш собственный коммит).
- Приоритет: medium-high (для непокрытых пока сценариев) / уже закрыто (для #7963, #6157).

## Кластер: Glyph/image blob-lease кэш — нестабильность и неограниченный рост
- Участники: PR #7955 (fix duplicate blob storage on Windows — access denied при повторной записи
  по content-hash пути), PR #7704 (preserve LruCache capacity в `make_all_stale`, иначе кэш растёт
  без ограничения), Issue #5422 (удаление BlobLease полностью останавливает рендер терминала),
  #7285 (Permission denied при доступе к blob-кешу), #6426 (директория blob-lease кеша разрастается
  до 15 ГБ).
- Механизм: `onlyterm-blob-leases` (дисковый кэш растеризованных глифов/картинок) и связанный
  built-in in-memory LRU (`onlyterm-client/src/pane/renderable.rs`) не гарантируют ни верхнюю
  границу размера, ни устойчивость к конкурентному доступу/ошибкам файловой системы — один и тот же
  класс "кэш без границ/без graceful degradation" проявляется и на диске (15 ГБ, permission denied,
  Windows access-denied при повторной записи), и в памяти (unbounded LruCache).
- Актуально для нашего стека: да — обе затронутые подсистемы (`onlyterm-blob-leases`,
  `onlyterm-client/src/pane/renderable.rs`) не менялись font/render-миграцией, используются как
  есть.
- Готовый фикс в апстриме: да — PR #7955 и PR #7704 оба тривиальные, точечные патчи в файлах,
  идентичных апстриму.
- Приоритет: high — включает буквальную остановку рендера (#5422) и утечку до 15 ГБ на диск.
